Мы уже знаем, что [[4. Mutex|мьютекс]] даёт `Lock()`/`Unlock()` и защищает критическую секцию. Но что физически происходит с горутиной, которая вызвала `Lock()`, а мьютекс уже занят? Она не крутится в цикле — она **ждёт**. Вопрос в том, где именно и как устроено это ожидание.

## Наивный вариант: мьютекс операционной системы

Самое простое — взять готовый системный мьютекс (`pthread_mutex`/futex), который даёт сама ОС. Но тут проблема: при захвате занятого ОС-мьютекса блокируется весь **поток (Thread)**, а не только горутина.

А поток — это ресурс, за который отвечает [[2. Scheduler|планировщик Go]], и на нём может стоять в очереди ещё сотня других горутин, вообще не связанных с этим мьютексом. Заблокировать поток целиком — значит заблокировать и их тоже, хотя они ни при чём. Это перечёркивает всю экономику M:N модели, ради которой горутины вообще существуют.

Поэтому нужен мьютекс, который работает **на уровне приложения**: блокирует конкретную горутину (переводит её в статус `Waiting`), а поток продолжает разбирать свою локальную очередь дальше как ни в чём не бывало.

## Куда класть ждущих

Раз горутину нельзя просто "заморозить" вместе с потоком, её нужно куда-то физически положить, пока мьютекс не освободится. Первый напрашивающийся вариант — хранить очередь ожидающих прямо внутри самого мьютекса. Так, например, устроен `struct mutex` в ядре Linux (`include/linux/mutex.h`):

```c
struct mutex {
    atomic_long_t       owner;
    raw_spinlock_t      wait_lock;
    struct list_head    wait_list; // <-- вот она, очередь ожидающих
    ...
};
```

Рабочий подход, но у него есть цена: каждый мьютекс в системе должен таскать с собой указатель на список, даже если его вообще никто никогда не ждёт. А `sync.Mutex` в Go специально сделан крошечным — это всего 8 байт (два `int32`), чтобы его было дёшево класть в любую структуру пачками. Полноценный `wait_list` внутри каждого экземпляра эту экономию бы перечеркнул.

## Как это сделано в Go

Go выбрал третий путь — не поток ОС и не список внутри каждого мьютекса, а **один общий пул на весь рантайм**. Загляни в `runtime/sema.go`:

```go
// A semaRoot holds a balanced tree of sudog with distinct addresses (s.elem).
// Each of those sudog may in turn point (through s.waitlink) to a list
// of other sudogs waiting on the same address.
// The operations on the inner lists of sudogs with the same address
// are all O(1). The scanning of the top-level semaRoot list is O(log n).
type semaRoot struct {
    lock  mutex
    treap *sudog        // root of balanced tree of unique waiters.
    nwait atomic.Uint32 // Number of waiters. Read w/o the lock.
}

var semtable semTable
```

Никакого отдельного списка на каждый мьютекс тут нет. Вместо этого — общий пул `semtable`, а каждый уникальный **адрес** мьютекса (или канала, или `WaitGroup`), который кто-то ждёт, становится узлом сбалансированного дерева (`treap`). Именно к этому узлу и подвешивается список горутин (`sudog`), заблокированных на этом конкретном адресе:

![[Pasted image 20260916184910.png]]

Глубоко в устройство дерева лезть не обязательно — важна идея: поиск нужного узла по адресу мьютекса стоит `O(log n)`, а сама работа со списком ждущих внутри одного узла — уже `O(1)`. Такое разделение и позволяет рантайму держать в одном общем пуле сразу все мьютексы, каналы и WaitGroup-ы программы, не тратя память на пустой `wait_list` в каждом из них по отдельности.

Хорошо, мы разобрались, куда положить ждущую горутину. Но когда мьютекс освобождается — кому его отдать: тому, кто ждал дольше всех, или тому, кто окажется быстрее прямо сейчас? Ответ не так очевиден, как кажется — разберём в [[6. Starvation Mode]].
