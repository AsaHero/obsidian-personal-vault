[[6. Starvation Mode|Предыдущая нечестность]] возникала из-за гонки: кто быстрее долетит до `lock()`. Priority Inversion — история из мира приоритетных планировщиков (классика real-time систем, но идея универсальна для любой ОС с приоритетами потоков): тут никто не гонится, высокоприоритетный поток проигрывает **по вине самих приоритетов**, а не из-за невезения.

## Что происходит

Три потока с разным приоритетом: Thread #1 (высокий), Thread #2 (средний), Thread #3 (низкий). Мьютекс делят между собой только Thread #1 и Thread #3 — Thread #2 к нему вообще не имеет отношения.

![[Pasted image 20260917171701.png]]

Хронология по шагам:

- **T0** — работает только Thread #3 (низкий приоритет), больше никто не готов.
- **T1** — Thread #3 вызывает `lock()` и захватывает мьютекс, продолжая работу внутри критической секции.
- **T2** — происходят сразу две вещи. Thread #1 (высокий приоритет) становится готов и тоже вызывает `lock()` — но мьютекс занят, поэтому Thread #1 блокируется. И тут же становится готов Thread #2 (средний приоритет) — он выше по приоритету, чем Thread #3, поэтому **вытесняет** его и начинает выполняться, хотя к мьютексу Thread #2 вообще не имеет отношения.
- **T3** — Thread #2 наконец отдаёт CPU (закончил свою работу или сам заблокировался на чём-то другом). Только теперь Thread #3 возвращается, доделывает критическую секцию и вызывает `unlock()`. И только после этого Thread #1 — тот самый, с наивысшим приоритетом — наконец получает мьютекс.

**Инверсия приоритетов** — ситуация, при которой поток с более высоким приоритетом вынужден ждать поток с более низким приоритетом дольше, чем должен бы, потому что всё это время CPU занимает третий поток со средним приоритетом, который к захваченному примитиву синхронизации вообще не имеет отношения. По факту порядок приоритетов на время оказывается перевёрнут: средний приоритет (Thread #2) обгоняет высокий (Thread #1), хотя формально должно быть наоборот.

> 💡 Классический реальный случай — марсоход Pathfinder (1997): низкоприоритетная задача держала мьютекс общей шины данных, среднеприоритетные задачи периодически её вытесняли, а высокоприоритетный поток связи с Землёй не мог дождаться мьютекса достаточно долго — из-за этого срабатывал watchdog-таймер и происходил перезапуск системы. Инженеры NASA удалённо включили priority inheritance — и проблема исчезла.

## Как решают — Priority Inheritance

Идея: пока низкоприоритетный поток держит мьютекс, за который борется кто-то более приоритетный, — **временно поднять его приоритет** до уровня самого приоритетного из ожидающих.

В нашем примере: как только Thread #1 заблокировался на мьютексе Thread #3, приоритет Thread #3 временно поднимается до уровня Thread #1. Thread #2 (средний) больше не может его вытеснить — он теперь ниже "прокачанного" Thread #3. Thread #3 быстро доделывает критическую секцию, освобождает мьютекс, и только тогда его приоритет возвращается к исходному низкому значению.

> ℹ️ Есть более строгий вариант той же идеи — **Priority Ceiling Protocol**: у каждого мьютекса заранее фиксируется "потолок" — наивысший приоритет среди всех потоков, которые вообще могут его захватить. Держатель поднимается сразу до этого потолка в момент `lock()`, не дожидаясь, пока более приоритетный поток реально придёт и заблокируется. Отдельная тема, в этом курсе не раскрывается.

Оба решения работают на уровне приоритетов потоков ОС — там же, где и живёт сама проблема. [[6. Starvation Mode|Starvation mode]] мьютекса в Go решает совсем другую нечестность: там все горутины формально равны, приоритетов нет вообще, а нечестность — чисто в порядке гонки за `lock()`.

Хватит про то, кто кого обгоняет. Следующий примитив — [[8. Once]] — про совсем другую задачу: сделать так, чтобы код выполнился ровно один раз, сколько бы горутин его ни дёргали.
