## Артефакт — сквозной проект: in-memory key-value БД

Все три домашки строят **одну растущую систему**. Это и есть артефакт курса.

### ДЗ №1 — ядро БД (~6 ч)

- [x] Многослойная архитектура: `compute` (+ parser) → `storage` (+ engine), слои за интерфейсами
- [x] Парсер языка запросов по eBNF: SET / GET / DEL, аргументы `\w+`, разделители — пробельные
- [x] In-memory engine на хэш-таблице
- [x] Обработка запроса как пайплайн: compute → storage
- [x] Логирование ключевых моментов (zap)
- [x] Тесты: обязательно parser и engine

### ДЗ №2 — сеть и конфигурация (~10 ч)

- [ ] TCP-сервер отдельным слоем, текстовый протокол
- [ ] Горутина на клиента + синхронизация доступа к хэш-таблице
- [ ] Обработка паник внутри запускаемых горутин
- [ ] Ограничитель одновременных соединений (максимум N клиентов)
- [ ] Отдельное приложение — CLI-клиент (TCP-клиент + интерфейс), конфиг через флаги
- [ ] YAML-конфиг: engine, network (address, max_connections, max_message_size, idle_timeout), logging
- [ ] Незаданный параметр → значение по умолчанию, а не падение
- [ ] Тесты: сетевой слой и конфигурирование

### ДЗ №3 — Write-Ahead Log (~15 ч и больше)

- [ ] Запись модифицирующих операций в WAL **до** применения к хэш-таблице
- [ ] Батчинг: сброс по размеру батча **или** по таймауту
- [ ] Клиент отпускается только после того, как батч записан на диск
- [ ] `fsync` после записи батча — одного `write` недостаточно
- [ ] Сегментация: файл достиг лимита → закрыть, создать новый
- [ ] Восстановление после рестарта последовательным чтением всех сегментов
- [ ] WAL по умолчанию выключен; конфиг: flushing_batch_size, flushing_batch_timeout, max_segment_size, data_directory
- [ ] Тесты: слой WAL и работа с файловой системой

### Проверки сверх требований

- [ ] Всё проходит под `-race`
- [ ] Убить БД на середине записи батча → после рестарта данные консистентны
- [ ] Нагрузить N клиентами выше лимита соединений → сервер не падает, лишние корректно отбиты
