## How to calculate frequency of the letter in the word without map?

Можем использовать [[Array and Slices#Array|array]] из 26 элементов и ASCII таблицу вместо [[Maps|map]].

```js
int freq[26] = {0};
for (char c : word) freq[c - 'a']++;
```

Каждый символ через `c - 'a'` превращается в индекс от 0 до 25. Просто, быстро, без map.

## Unicode — version 1

ASCII не вмещал все символы языков мира, поэтому придумали Unicode — сначала на 2 байта. Но сразу возникла проблема: как понять, в каком порядке байты? Big Endian или Little Endian?

Чтобы решить это, добавили в начало файла 2 специальных байта — это и есть **BOM** (Byte Order Mark). Этот формат назывался **UCS-2**:

```
FE FF — Big Endian
FF FE — Little Endian
```

Но тут же вылезла другая проблема: любой символ теперь весил минимум **2 байта**. Слово `HI` в ASCII = 2 байта, а в UCS-2 = уже 4 байта. Расточительно. Поэтому со временем появился UTF-8.

---

## UTF-8

**Unicode Transformation Format 8-bit** — кодировка, которая стала доминирующей в интернете.

Главная идея: символы **переменной длины** — от 1 до 4 байт. При этом первые 128 символов Unicode совпадают с ASCII, поэтому любой английский текст работает как раньше.

Первый байт — это маска, которая говорит сколько байт занимает символ:

```
0xxxxxxx          — 1 байт  (латиница, ASCII)
110xxxxx 10xxxxxx — 2 байта (кириллица, диакритика)
1110xxxx ...      — 3 байта (китайский, японский)
11110xxx ...      — 4 байта (эмодзи, редкие символы 🎉)
```

Если видишь `10xxxxxx` — это продолжающийся байт, а не начало символа.

**Пример:** буква `А` (кириллическая) = 2 байта: `0xD0 0x90` Буква `A` (латинская) = 1 байт: `0x41`

Но появилась новая проблема: чтобы найти N-й символ в строке, нужно **парсить каждый байт** с самого начала и считать маски. Нельзя просто взять `str[5]` — это будет 5-й байт, а не 5-й символ. Каждый раз лишний CPU-цикл. Поэтому многие языки программирования (например, Java, C#, Python 2) не стали использовать UTF-8 внутри рантайма.

---

## UTF-16

Улучшение поверх UTF-8 по скорости обработки. Символ может занимать **2 или 4 байта** (но не 1 или 3). Это упрощает парсинг: читаешь 2 байта, смотришь диапазон — если попал в `0xD800–0xDFFF`, значит это суррогатная пара и берёшь ещё 2 байта. Иначе — готовый символ.

Именно поэтому Java, JavaScript, C# используют UTF-16 внутри строк.

**Пример:** `"Hi"` в UTF-16 = 4 байта (`00 48 00 69`)

BOM здесь обязателен, потому что порядок байт важен:

```
FE FF — Big Endian
FF FE — Little Endian
```

---

## UTF-32

Самая простая кодировка: каждый символ — ровно **4 байта**. Всегда. Без исключений.

Плюс: индексирование за O(1), не нужно парсить маски. `str[5]` — это всегда пятый символ.  
Минус: `"Hi"` весит 8 байт, а не 2. Расход памяти в 4 раза больше чем ASCII.

Используется редко — только когда скорость важнее памяти (обработка текста в базах данных, некоторые внутренние форматы).

| Кодировка | Размер        | BOM | Скорость обработки |
|-----------|---------------|-----|--------------------|
| UTF-8     | От 1 до 4 байт | Нет | Медленная          |
| UTF-16    | 2 или 4 байта  | Да  | Средняя            |
| UTF-32    | 4 байта        | Да  | Быстрая            |


## Как реализовать строки?

### Null-terminated strings (C-style)

Самый старый способ — строка это просто массив байт, а в конце стоит `\0` (нулевой байт), который говорит "здесь строка заканчивается".

```c
char str[] = "hello"; // в памяти: h e l l o \0
```

Проблема: чтобы узнать длину строки нужно пройтись по всем байтам до `\0` — это O(n). Также легко получить buffer overflow если забыть про нулевой байт.

---

### Pascal strings

Вместо нулевого байта в конце — длина строки хранится **в начале**, в первом байте (или 4 байтах в современных реализациях).

```
[4 байта: длина][h][e][l][l][o]
```

Плюс: `len()` за O(1), нет проблемы с `\0` внутри строки.  
Минус: максимальная длина ограничена размером поля длины (255 символов если 1 байт).

---

### Immutable & Mutable strings

**Immutable** — строку нельзя изменить после создания. Любая "модификация" создаёт новую строку. Так работает Go, Java, Python, C#.

```go
s := "hello"
s += " world" // создаётся новая строка, старая остаётся в памяти
```

**Mutable** — строку можно менять на месте. Так работает `std::string` в C++ и `StringBuilder` в Java.

Immutable строки проще для рантайма: можно безопасно шарить указатели без копирования, не бояться гонок в многопоточке.

---

### SSO — Small String Optimization

Трюк в C++ `std::string`: короткие строки (обычно ≤ 15 символов) хранятся **прямо внутри структуры**, без heap allocation.

```
struct string {
    union {
        char* ptr;         // для длинных строк — указатель на heap
        char buf[16];      // для коротких — сами байты тут же
    };
    size_t len;
    size_t capacity;
}
```

Если строка влезает в `buf` — никакого `malloc`. Это резко ускоряет работу с короткими строками, которых в реальном коде большинство.

---

### CoW — Copy-on-Write

Оптимизация: несколько переменных могут **указывать на одни и те же данные**, пока никто их не меняет. Копирование происходит только в момент записи.

```
a = "hello"
b = a        // b просто берёт тот же указатель, копии нет

b += "!"     // вот теперь происходит реальная копия
```

Используется в Qt (`QString`), PHP строках, старых версиях `std::string`. Минус — в многопоточке нужен atomic счётчик ссылок, что добавляет overhead.

---

### String Interning

Если две строки одинаковые — зачем хранить их дважды? **Интернирование** — это кэш уникальных строк: одинаковые строковые литералы указывают на **одну и ту же область памяти**.

```python
a = "hello"
b = "hello"
a is b  # True — это один и тот же объект в памяти
```

Используется в Python, Java, Go (для строковых литералов). Экономит память и ускоряет сравнение строк: вместо посимвольного сравнения — просто сравниваем указатели.

## Strings in Go

### How strings look like under the hood?

Строка в Go — это просто **последовательность произвольных байт**. Immutable. Под капотом это структура с указателем на байты и длиной:

```go
type _string struct {
    elements *byte // указатель на байты
    len      int   // количество байт, не символов!
}
```

Важно понимать: строки в Go — **не UTF-8**. Это просто байты. Строковые литералы в исходнике компилятор кодирует в UTF-8, но сама строка об этом не знает. Читаешь файл — получаешь байты, и никто не требует чтобы они были валидным UTF-8.

```go
s := "Привет"
fmt.Println(len(s))    // 12, а не 6 — потому что кириллица по 2 байта
fmt.Println(len([]rune(s))) // 6 — вот теперь символы
```

---

### String concatenation using `+`

Компилятор умный: если в одном выражении несколько конкатенаций — он делает **одну аллокацию** для всего результата сразу.

```go
str = str1 + str2 + str3 + str4
// НЕ делает: alloc(str1+str2), потом alloc(+str3), потом alloc(+str4)
// Делает:    считает итоговую длину → одна alloc → копирует всё
```

Но если конкатенация в цикле — компилятор уже не спасёт:

```go
for _, s := range parts {
    result += s // каждая итерация = новая аллокация
}
```

---

### strings.Builder

Внутри использует `[]byte`, который растёт по стратегии как у [[Array and Slices#Slices|slice]] (x2). Это убирает O(n²) аллокаций при конкатенации в цикле.

```go
var b strings.Builder
for _, s := range parts {
    b.WriteString(s)
}
result := b.String() // одна финальная конверсия []byte → string
```

### String literals edit panic

```go
package main

import "unsafe"

func action() {}

func main() {
    var str = "go"
    newStr := str + "-go"

    strData := unsafe.StringData(str)
    newStrData := unsafe.StringData(newStr)

    println("action:", action)
    println("strData:", strData)
    println("newStrData:", newStrData)

    slice := unsafe.Slice(strData, len(str))
    newSlice := unsafe.Slice(newStrData, len(newStr))

    newSlice[0] = 'G' // no panic
    println("newStr:", newStr)

    slice[0] = 'G' // panic!
    println("str:", str)
}
```

Почему `newStr` можно изменить, а `str` — нет?

Если запустить и распечатать адреса, то адрес `str` будет **рядом с адресом функции** `action`. Это не случайность — строковые литералы, известные на этапе компиляции, кладутся компилятором в **text segment** программы (туда же где и машинный код). А text segment — **read-only**.

`newStr` же создаётся в рантайме через конкатенацию, поэтому уходит в heap — и там уже можно писать.

```
Память программы:
┌─────────────────┐
│   text segment  │ ← "go" живёт здесь (read-only)
│   (код + литер) │
├─────────────────┤
│      heap       │ ← "go-go" живёт здесь (read-write)
└─────────────────┘
```

```
High Address
┌─────────────────────────────┐  ─────────────────────
│                             │                       │ Growth
│           Stack             │  ← Stack              │         |         (downward)          | 
│                             │     Address Space     ↓
├─────────────────────────────┤
│         free space          │
├─────────────────────────────┤
│         free space          │
├─────────────────────────────┤
│          (upward)           │  ← Heap               ↑ Growth
│            Heap             │     Address Space     │
│                             │                       │
├─────────────────────────────┤  ─────────────────────
│  Uninitialized Data Segment │
│           (.bss)            │
├─────────────────────────────┤
│   Initialized Data Segment  │
│          (.data)            │
├─────────────────────────────┤
│       Code Segment          │
│          (.text)            │
└─────────────────────────────┘
Low Address
```

### String Interning in Go

Компилятор автоматически интернирует одинаковые строковые литералы — то есть кладёт их в **одно место** в text segment.

```go
var str1 string = "example"
const str2 string = "example"
const str3 string = "another example"

println(unsafe.StringData(str1)) // 0x48fe12
println(unsafe.StringData(str2)) // 0x48fe12 — тот же адрес!
println(unsafe.StringData(str3)) // 0x4910f6
```

`str1` и `str2` указывают на одни и те же байты. Никакой дублирующей аллокации.

---

### Any string conversion calls reallocation and copy

Любая конвертация `[]byte` → `string` или `string` → `[]byte` делает **полную копию** данных в новый участок памяти:

```go
str := "Hello World!!!"

byteStr := []byte(str)  // reallocation + copy
byteStr[0] = 'h'

str = string(byteStr)   // reallocation + copy
```

Это сделано намеренно: `string` immutable, `[]byte` mutable — чтобы один не мог сломать другой через общий указатель.

---

### How to convert to string without reallocation?

Через `unsafe` можно создать строку поверх существующего `[]byte` без копирования:

```go
data := []byte("Hello World!")

str := unsafe.String(unsafe.SliceData(data), len(data))
// str и data смотрят на один и тот же участок памяти
```

Но осторожно: если после этого изменить `data` — строка тоже изменится, хотя по контракту должна быть immutable. Используй только если точно знаешь что делаешь.

---

### Compiler under the hood optimization

Компилятор Go умеет в ряде случаев **пропускать аллокацию** при конвертации `[]byte` ↔ `string`. Вот когда это работает:

- `[]byte` → `string` внутри `range`
- `[]byte` → `string` как ключ словаря при **чтении**
- `[]byte` → `string` при **сравнении**
- `[]byte` → `string` при конкатенации, если хотя бы одна из строк — непустая константа

Пример где это важно:

```go
func comparisonAndConcatenation1() {
    var x = []byte{1023: 'x'}
    var y = []byte{1023: 'y'}

    if string(x) != string(y) {           // 0 аллокаций — компилятор оптимизирует
        s := (" " + string(x) + string(y))[1:] // 1 аллокация — константа " " триггерит оптимизацию
        _ = s
    }
}

func comparisonAndConcatenation2() {
    var x = []byte{1023: 'x'}
    var y = []byte{1023: 'y'}

    if string(x) != string(y) {     // 0 аллокаций
        s := string(x) + string(y)  // 2 аллокации — нет константной строки
        _ = s
    }
}

fmt.Println(testing.AllocsPerRun(1, comparisonAndConcatenation1)) // 1
fmt.Println(testing.AllocsPerRun(1, comparisonAndConcatenation2)) // 3
```

Трюк с пробелом `" " + string(x) + string(y)` — это не хак, это легальная оптимизация. Компилятор видит непустую строковую константу и делает всё за одну аллокацию.

### Passing string to function

При передаче строки в функцию копируется только **структура** (16 байт: указатель + длина), но не сами данные. Оба экземпляра смотрят на одни и те же байты:

```go
func process(s string) {
    // s — это копия структуры, но s.elements указывает туда же
}

str := "hello"
process(str) // дёшево — копируем только 2 поля структуры
```

### `unique` — standard package

В Go 1.23 появился пакет `unique` для ручного интернирования данных. Полезно когда хочешь интернировать не только литералы, но и строки собранные в рантайме:

```go
import "unique"

h1 := unique.Make("hello")
h2 := unique.Make("hello")

fmt.Println(h1 == h2) // true — одно и то же место в памяти
```

### Memory Leak with strings

Точно такая же проблема как с [[Array and Slices#GC only cleans slice wholly, no partial cleaning!| sub-slice]] у `[]byte`. Если вырезать маленький кусок из большой строки — **большая строка не освобождается**, пока жив маленький кусок:

```go
func findSequence(data string) string {
    for i := 0; i < len(data)-1; i++ {
        if data[i] == '\n' && data[i+1] == '\t' {
            return data[i+2 : i+22] // возвращаем 20 байт
        }
    }
    return ""
}

data := make([]byte, 1<<30) // 1 GB
str := unsafe.String(unsafe.SliceData(data), len(data))
sequence := findSequence(str) // держим 20 байт...
// ...но GC не может собрать 1 GB пока sequence жива
```

`sequence` — это всего 20 байт, но под капотом её указатель смотрит внутрь гигабайтного буфера. GC видит что буфер ещё referenced — и не трогает его.

**Фикс** — скопировать нужный кусок в новую строку:

```go
func findSequence(data string) string {
    for i := 0; i < len(data)-1; i++ {
        if data[i] == '\n' && data[i+1] == '\t' {
            found := data[i+2 : i+22]
            return strings.Clone(found) // новая аллокация, старый буфер свободен
        }
    }
    return ""
}
```
