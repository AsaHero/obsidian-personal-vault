## Что такое мусор?

Мусор — это неиспользуемая память программы, которую нужно освободить для дальнейшего использования.

```go
func process() {
	data := make([]byte, 1<<30) // 1 GB
	// working with data...
	_ = data
}

func main() {
	process()
	// после выхода из process() этот 1 GB нам больше не нужен —
	// вот он и есть мусор, который надо освободить
}
```

## Всегда ли нужно собирать мусор?

Нет. **Иногда можно вообще не думать о сборке мусора** — например, если приложение живёт всего несколько минут/часов и памяти ему хватает с запасом на всё время работы. Классический пример — CLI-утилита или скрипт, который отработал и завершился: ОС сама заберёт всю память процесса при его завершении, зачем тратить время на GC.

## Как вообще можно собирать мусор?

### Ручной режим

Освобождаешь объекты сам, руками, там, где явно понимаешь, что они больше не нужны.

```c
void* data = malloc(1024);
// working with data...
free(data);
```

✅ **Плюс:** минимальный overhead — никакого фонового процесса, никакой лишней работы во время выполнения. ❌ **Минусы:** вся ответственность на программисте, а с ней — классический набор проблем: use-after-free (обратился к уже освобождённой памяти), double-free (освободил дважды), memory leak (забыл освободить).

### Автоматические подходы

Их два принципиально разных:

1. **Подсчёт ссылок** (reference counting)
2. **Трассирование** (tracing)

---

## Подсчёт ссылок (Reference Counting)

Идея: у каждого объекта есть счётчик, сколько других объектов на него ссылаются. Когда счётчик доходит до нуля — объект недостижим, его можно освобождать.

| Подсчёт ссылок |                                                                                                                       |
| -------------- | --------------------------------------------------------------------------------------------------------------------- |
| ✅ Плюс         | не нужен отдельный процесс сборки мусора — освобождение происходит "по требованию", в момент когда счётчик обнуляется |
| ❌ Минус        | лишняя работа на увеличение/уменьшение счётчика при **каждом** присваивании указателя                                 |
| ❌ Минус        | нужна синхронизация счётчика между потоками (atomic-инкремент/декремент — не бесплатно)                               |
| ❌ Минус        | дополнительная память на хранение самого счётчика в каждом объекте                                                    |
| ❌ Минус        | не умеет в циклические ссылки (см. ниже)                                                                              |

### ⚠️ Подводный камень: синхронный каскад освобождений

```
Pointer → Node (refs=1) → Node (refs=1) → Node (refs=1) → Node (refs=1)
```

Если это, например, связный список, и мы обнуляем `Pointer` (последнюю внешнюю ссылку на голову списка) — первый `Node` освобождается, что уменьшает refs у второго `Node` до нуля, второй освобождается, уменьшая refs у третьего... и так по цепочке.

На первый взгляд reference counting — это "нет пауз, всё происходит по требованию". Но здесь как раз пауза и появляется: освобождение длинной цепочки объектов происходит **синхронно, в момент обнуления первого счётчика**, в том самом потоке, который до этого просто хотел обнулить один указатель. Чем длиннее цепочка — тем дольше висит вызывающий код. Получается мини-STW, только неожиданный и спрятанный внутри, казалось бы, дешёвой операции.

### Циклические ссылки — главная системная проблема

Если объект A ссылается на B, а B ссылается обратно на A — их счётчики никогда не дойдут до нуля сами по себе, даже если снаружи на них больше никто не ссылается. Чистый подсчёт ссылок эту утечку **не видит и не решает** — абстрагироваться от проблемы не получится, о циклах приходится знать и управлять ими вручную.

Классический ручной обход — разделить ссылки на **сильные** (strong) и **слабые** (weak): слабая ссылка не увеличивает счётчик и не удерживает объект живым.

```
              weak_refs = 1        weak_refs = 0
              strong_refs = 0      strong_refs = 1

Pointer  --->  ┌────────┐  ─────>  ┌────────┐
               │  Node  │          │  Node  │
               └────────┘  <─────  └────────┘
```

Первый `Node` держит **слабую** ссылку на второй (`weak_refs = 1`, `strong_refs = 0`), а второй держит **сильную** ссылку обратно на первый (`strong_refs = 1`). Раз одна из двух ссылок в цикле — слабая, цикл на счётчик не влияет, и когда внешний `Pointer` пропадёт, освобождение всё-таки произойдёт. Но это ручная дисциплина: конкретный разработчик каждый раз решает, какая ссылка в паре должна быть слабой, и если ошибётся — снова утечка.

📌 Go не использует reference counting для кучи вообще — это просто общий фон для сравнения. У Go — трассирующий сборщик, о нём и пойдёт речь дальше.

## Трассирование (Tracing)

В отличие от подсчёта ссылок, tracing занимается противоположным — **ищет живые объекты**, а не считает мёртвые.

Самый примитивный сценарий работы:

1. Останавливаются все потоки-мутаторы (потоки исполняющие код программы)
2. Без синхронизации обходится граф ссылок (можно делать это параллельно)
3. Помечаются все достижимые (используемые) объекты
4. Непомеченные объекты удаляются

### Шаг 1: остановить все потоки

Как это сделать технически? Два классических способа:

- вставить в код специальные **safepoint'ы** — места, где поток сам проверяет "а не пора ли мне остановиться" (обычно на входе в функции, в циклах)
- запретить страницу памяти для чтения через `mprotect` — поток, попытавшись прочитать защищённую страницу, получит page fault и остановится сам, а обработчик fault'а уже разберётся, что делать

### Шаг 2: обход графа — фаза Mark

Откуда вообще начинать обход? С **корней** (roots) — это глобальные переменные и стеки горутин/потоков.

```
Global var  [######]  ──────────────►  [ ... ] ───────────┐
                                                          ▼
Global var  [######]  ─────────────────────────────►   [ ... ]

Stack       [      ]
            [######]  ──────────────►  [ ... ] ───┬──►  [ ... ]
            [      ]                              └──►  [ ... ]

Stack       [      ]
            [######]  ──────────────►  [ ... ] ──────►  [ ... ]
            [      ]
            [######]  ──────────────►  [ ... ] ──────►  [ ... ]
```

Всё, до чего можно дойти по ссылкам из этих корней — живое. Всё остальное — мусор.

**DFS или BFS?** На чистой математике оба решают задачу обхода одинаково. Разница — в том, насколько легко распараллелить. BFS естественно опирается на очередь: несколько воркеров могут независимо забирать объекты из общей очереди "к посещению" и обрабатывать их параллельно, без сложной синхронизации порядка. DFS через рекурсию/стек создаёт цепочку зависимостей — обработка следующего узла логически идёт после текущего, что сложнее раздать по независимым воркерам без дополнительных трюков (work stealing и т.п.). Неслучайно реальные трассирующие GC (в том числе в Go) организуют список "серых" объектов именно как **очередь работы** (work queue) — это по сути BFS-подобное расширение фронта, которое естественно ложится на несколько параллельных воркеров.

### Красим граф в три цвета

При обходе каждый объект красится в один из трёх цветов:

1. **Чёрный** — исследованный объект: сам объект посещён, и **все** ссылки, идущие из него, тоже уже исследованы
2. **Серый** — объект известен, но исследован не до конца (не все его ссылки ещё пройдены); серые объекты и составляют ту самую очередь работы
3. **Белый** — объект, про который обходчик вообще ещё ничего не знает

> **Tri-color invariant:** не бывает ссылки из чёрного объекта в белый.

⚠️ **Важная деталь, которую легко упустить:** три цвета нужны не столько ради самого обхода циклов в графе — обычный обход с одним битом "посещено/не посещено" тоже прекрасно справляется с циклами в статичном графе, зацикливания не будет. Настоящая причина появления именно трёх состояний — это подготовка к **конкурентному** сценарию (когда GC работает одновременно с мутатором и граф ссылок может измениться прямо во время обхода). Различие между "уже полностью обработан" (чёрный) и "известен, но не обработан до конца" (серый) становится критичным именно тогда, когда мутатор может на лету добавить новую ссылку — про это дальше, в разделе про concurrent GC и барьеры.

В конце обхода остаются белые области — на них никто не ссылается, значит это и есть мусор.

### Шаг 3: что делать с непомеченным — Sweep или Copying

Дальше есть две альтернативы:

- **Sweep** ("подмести") — просто освобождаем всё, что осталось белым, память под них помечается свободной
- **Copying** ("перенести") — переносим **живые** (чёрные) объекты в новую область памяти, а всю старую область целиком освобождаем, чтобы не было фрагментации

📌 Это ровно те же две стратегии, которые мы разбирали в контексте фрагментации в прошлый раз — **Sweep = non-moving** (как в Go), **Copying = moving**. У moving-подхода фрагментация устраняется полностью, но платишь двойным потреблением памяти (нужна вторая половина, куда копировать) и стоимостью переписывания всех указателей на переехавшие объекты. Go, как мы уже выяснили, идёт по пути Sweep именно из-за `unsafe.Pointer`/cgo и concurrent-дизайна GC — здесь эта же причина всплывает снова, просто с другой стороны.

Так работает простейший **STW (Stop-The-World) сборщик**: весь цикл — от остановки потоков до Sweep — идёт с полностью остановленной программой. **Чем больше куча — тем больше живых объектов нужно обойти на шаге Mark — тем длиннее пауза.**

### Как паузы GC видны на графике response time

Резкие всплески (спайки) на графике response time — часто как раз следствие пауз сборщика мусора.

Когда GC работает в режиме STW, все потоки приложения останавливаются на время сборки. Запросы, которые в этот момент обрабатывались или ждали в очереди, получают задержку, равную длительности паузы. Это проявляется именно в верхних перцентилях (p95, p99+) отдельными резкими пиками, а не сдвигом всего графика — потому что затрагивает не все запросы, а только те, что "попали" под паузу в моменте её наступления.

## Как уменьшить паузы?

### Поколения (generational GC)

Идея: можно обходить не всю кучу, а только часть — потому что большинство объектов умирают "молодыми" (generational hypothesis). Раз так, разумно разделить объекты по времени жизни: молодые обходить часто (там больше всего мусора и обход быстрый — область маленькая), а старые, пережившие несколько сборок — редко (они с высокой вероятностью проживут ещё долго, обходить их каждый раз — трата времени).

**В Go этой концепции нет.** Причина — в разделе "Устройство GC в Go" ниже, она напрямую связана с тем, как в Go работает escape analysis.

### Concurrent GC

Можно вообще не останавливать программу на весь цикл сборки, а запустить поток(и) GC **параллельно** с мутаторами. Именно этот путь выбрал Go.

⚠️ **Важно не путать Concurrent GC с Parallel GC** — это разные вещи:

|                                                             | Concurrent GC                        | Parallel GC                                                                        |
| ----------------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------- |
| Работает одновременно с мутатором (пользовательским кодом)? | Да                                   | Нет — мутатор стоит (STW)                                                          |
| Что именно распараллелено                                   | сама сборка идёт вместе с программой | несколько потоков **самого GC** работают одновременно, но программа при этом стоит |

Parallel GC — это по-прежнему STW, просто паузу сокращают за счёт того, что несколько GC-потоков делают Mark/Sweep одновременно, а не один поток последовательно.

### Проблема конкурентного запуска: Lost Object

Если GC работает одновременно с мутатором, граф ссылок может **измениться прямо во время обхода**. Представь: GC уже прошёл через чёрный объект A (все его ссылки исследованы), а мутатор в этот момент берёт и добавляет в A новую ссылку на белый объект C, до которого никто больше не ссылается. Результат — мы **теряем объект** (Lost Object): C белый, на него никто, кроме только что появившейся ссылки из A, не указывает, но GC уже прошёл A и туда не вернётся. Заодно ломается tri-color invariant — появляется ссылка из чёрного в белый.

### Как это решают: барьеры записи

**Барьер записи (write barrier — insertion barrier):** если чёрный объект начинает ссылаться на новый объект, указатель на этот новый объект сразу красится в **серый** (и добавляется в очередь на обход). Так мы никогда не потеряем свежепойманный объект — он гарантированно будет обойдён.

**Барьер удаления (deletion barrier):** красим в серый тот объект, на который **теряется** ссылка (тоже добавляя его в очередь), — на случай если он был единственной причиной, почему объект вообще остался достижимым.

⚠️ **Для включения/отключения барьеров чаще всего нужен короткий STW** — сама фаза Mark идёт конкурентно, но переключение барьера туда-обратно требует короткой синхронизации со всеми потоками.

Если сборка мусора сейчас не идёт — мутатору вообще не нужно ничего оповещать (не нужно ничего красить), барьер просто выключен.

## Устройство GC в Go

Собираем всё вместе — вот из чего состоит GC Go:

- **Mark and Sweep** — сам алгоритм GC (non-moving, sweep, а не copying)
- **Трёхцветный** — алгоритм разметки живых объектов
- **Конкурентный** — работает параллельно с основной программой, используя барьеры записи

### Почему в Go нет поколений

В Go **сознательно не стали заимствовать у Java** концепцию поколений объектов. Причина в том, что в Go гораздо большая роль отведена аллокациям на стеке (мы подробно разбирали escape analysis в прошлый раз). Короткоживущие объекты с большой вероятностью вообще **не попадут в кучу** — они останутся на стеке и будут освобождены бесплатно, вместе с кадром стека, без всякого участия GC. А раз "молодое поколение" объектов в куче и так сильно прорежено escape analysis'ом заранее — сама идея молодого/старого поколения теряет смысл: там просто меньше материала для оптимизации по сравнению с тем же Java, где почти всё уходит в кучу по умолчанию.

### Сколько CPU ест GC

Фракция CPU, потребляемая воркерами GC, **жёстко зафиксирована на уровне 25%**. Если GC не справляется с потоком мусора — он может слегка притормозить новые аллокации, заставляя некоторые горутины тратить часть _своего_ времени на помощь в сборке.

ℹ️ Эта оптимизация называется **Mark Assist** и позволяет довести суммарную фракцию CPU, потребляемую GC, до 30%.

### Когда вообще запускается сборщик в Go

1. **Превышение динамического лимита кучи**, заданного переменной `GOGC`
2. **Прошло 2 минуты без GC** — если ничего не аллоцировалось всё это время, GC всё равно запустится раз в 2 минуты (за это отвечает фоновый `sysmon`)
3. **Ручной запуск через `runtime.GC()`** — если вызвать его, когда GC уже и так запущен, по достижении фазы Sweep он запустится заново

GC срабатывает, когда объём новых аллокаций ("новая куча") сравнивается по размеру с объёмом живых объектов, оставшихся после предыдущей сборки ("живая куча") — то есть куча **удваивается** относительно предыдущего живого объёма. Это как раз соответствует значению `GOGC=100` по умолчанию.

### Приём: ballast, чтобы реже гонять GC на маленьких кучах

```go
package main

func main() {
	ballast := make([]byte, 2<<30) // 2 GB "балласта"
	_ = ballast

	// implementation ...
}
```

Идея: раз GC срабатывает при удвоении кучи, искусственно "раздутая" стартовая куча в 2GB сдвигает следующий триггер GC аж к 3GB — то есть уменьшает **частоту** сборок для приложения, которое и так много аллоцирует по чуть-чуть.

⚠️ **Кажется, что программа сразу займёт 2GB оперативки — но нет.** Виртуальная память **выделена** сразу, а вот физическая — нет, пока мы реально не обратимся к этим байтам. Это называется **lazy allocation**.

**RSS (Resident Set Size)** — сколько памяти реально выделено процессу и находится в RAM прямо сейчас. Не включает выгруженное в swap. Включает страницы разделяемых библиотек, если они реально в памяти.

**VSZ (Virtual Memory Size)** — вся память, к которой процесс _может_ обратиться: включая то, что в swap, то, что зарезервировано, но не используется, и разделяемые библиотеки.

```
$ ps -o pid,vsz,rss | awk '{if (NR == 1 || $1 == "29375") print}'
  PID       VSZ        RSS
29375     419700592   1728
```

Видно: VSZ огромный (виртуально зарезервировано много), а RSS крошечный (реально в RAM почти ничего) — классическая картина lazy allocation в деле.

### Lazy Allocation чуть подробнее

После вызова аллокации адресное пространство процесса расширяется **немедленно**, но Linux не назначает физические страницы памяти, пока не произойдёт первая запись в эту страницу.

### Ловушка: OOM при "казалось бы, ещё есть запас"

Представим процесс в контейнере/VM с лимитом RSS в 10 GB, `GOGC = 100%`.

Допустим, после последнего прохода GC размер кучи составил **5.1 GB** — вроде до лимита ещё далеко. Но следующий триггер GC по формуле (удвоение) — это уже **10.2 GB**.

⚠️ Это выше лимита RSS в 10 GB. Иными словами, прежде чем GC сработает в следующий раз, процесс **убьёт OOM Killer** — до собственно триггера GC дело просто не дойдёт.

**Решение:** запускать GC чаще, то есть выбрать более консервативное (меньшее) значение `GOGC`. Но ручной подбор `GOGC` под конкретный сервис и конкретную нагрузку — то ещё удовольствие, потому что нагрузка меняется во времени, а число статичное.

### Death Spiral

Можно перестараться с агрессивным `GOGC` и словить **спираль смерти** — проблему, которую обнаружить сложнее, чем банальный OOM:

```
Нужно больше памяти
        │
        ▼
Чаще запускаем GC
        │
        ▼
Тратим больше CPU на GC
        │
        ▼
Throughput падает
        │
        ▼
Запросы копятся в очередях
        │
        ▼
Нужно больше памяти (по кругу)
```

### GOMEMLIMIT

Учитывает **всю** память, потребляемую приложением (не только кучу), и, ориентируясь на заданную верхнюю границу, заставляет рантайм чаще вызывать GC и более агрессивно возвращать память ОС.

```
GOMEMLIMIT=2750MiB
```

⚠️ **Чтобы GOMEMLIMIT сам не завёл GC в спираль смерти**, введено искусственное ограничение: сборщик мусора **не превысит 50% CPU** даже в самых жёстких ситуациях, когда мусора много, а памяти почти не осталось. В этом случае приложение сможет продолжить аллоцировать сверх лимита — то есть `GOMEMLIMIT` является **мягким** ограничением: он не гарантирует, что лимит никогда не будет превышен, а лишь заставляет GC стараться сильнее его соблюдать, но не ценой полной остановки прогресса программы.

## Из каких фаз состоит GC в Go?

|Фаза|Write Barrier|STW|Описание|
|---|---|---|---|
|**Off**|—|—|GC выключен. Запись указателя — просто обычная запись в память: `*slot = ptr`|
|**Stack scan**|включён|частичный STW|Собираем указатели из глобальных переменных и стеков горутин. Стеки сканируются в точках preemption|
|**Mark**|включён|—|Помечаем объекты и идём по ссылкам, пока очередь не опустеет. Write barrier отслеживает изменения указателей мутатором|
|**Mark termination**|включён|STW|Пересканируем глобальные переменные/изменившиеся стеки, дозавершаем разметку, ужимаем стеки. (В литературе есть и non-STW алгоритмы для этого шага — здесь для простоты не рассматриваем)|
|**Sweep**|—|—|Освобождаем непомеченные объекты по мере надобности. Настраиваем pacing для следующего цикла|
|**Off**|—|—|И снова по кругу|

### Три практических шага

**1. Sweep termination**

- **Stop the world**
- Завершение всех незавершённых sweep-фаз
- Удаление остатков мусора

(Происходит, если предыдущая фаза ещё не была завершена к моменту старта новой.)

**2. Mark**

- Включаем write barrier
- **Start the world**
- Сканируем глобальные переменные и стеки (при сканировании конкретной горутины она приостанавливается только на это время)
- Раскрашиваем объекты в три цвета

**3. Sweep**

- Отключаем write barrier
- **Start the world**
- Освобождаем ресурсы в фоне

### Как узнать, в какой фазе сейчас GC

Текущая стадия работы сборщика мусора хранится в глобальной переменной `gcphase`.

### Кто выполняет код сборки мусора

**M** (OS thread) может исполнять либо пользовательскую горутину, либо горутину GC — с точки зрения планировщика это просто ещё одна горутина, которая точно так же встаёт в очередь на исполнение.

### Как уменьшить нагрузку на GC

Практический вывод простой: **стараться переиспользовать выделенную память и по возможности размещать объекты на стеке, а не в куче.** Это прямая отсылка к escape analysis из прошлого конспекта — чем меньше объектов реально уходит в кучу, тем меньше работы для Mark-фазы, и тем реже вообще нужен GC.

## Finalizers

Функция, которая вызывается рантаймом непосредственно перед тем, как объект будет собран GC.

```go
package main

import (
	"fmt"
	"runtime"
	"time"
	"unsafe"
)

type Data struct {
	name string
}

func NewData(name string) *Data {
	data := &Data{
		name: name,
	}

	fmt.Println("created", name)
	runtime.SetFinalizer(data, func(ptr *Data) {
		fmt.Println("finalizer called on addr", unsafe.Pointer(ptr), "value is", ptr.name)
	})

	return data
}

func main() {
	data := NewData("__data__")
	_ = data

	runtime.GC()
	time.Sleep(time.Second) // finalizer вызывается в отдельной горутине асинхронно —
	// без этой паузы программа может завершиться раньше, чем мы увидим вывод
}
```

⚠️ **Несколько неочевидных моментов про финализаторы:**

- финализатор выполняется **асинхронно**, в отдельной горутине, в какой-то момент **после** того, как объект стал недостижим — не сразу и без гарантии конкретного времени
- если процесс завершается через `os.Exit()` или просто падает — финализаторы **не гарантированно** будут вызваны вообще (это перекликается с тем, что мы разбирали про `defer` и `os.Exit` в конспекте про ошибки — тот же принцип: аварийное завершение не даёт гарантий на cleanup-код)
- объект с финализатором **переживает лишний цикл GC**: сначала GC обнаруживает, что объект недостижим, но вместо немедленного освобождения "воскрешает" его на время выполнения финализатора, и по-настоящему освобождает уже на следующем цикле

### Практическое применение

Классика — закрывать файловые дескрипторы, если объект-обёртка над файлом был потерян программистом без явного `Close()`:

```go
func newFile(fd uintptr, name string, kind newFileKind) *File {
	...
	runtime.SetFinalizer(f.file, (*file).close)
	return f
}
```

Так же можно закрывать connection'ы, handler'ы и подобные ресурсы, у которых есть "физический" аналог за пределами управляемой Go-памяти.

### C-биндинги: не заставлять программиста освобождать память руками

Если работаешь с cgo — хорошим тоном будет не просить пользователя твоей обёртки явно вызывать free, а спрятать это в финализатор:

```go
type Cstr struct {
	cpointer *C.char
}

func AllocateAuto() *Cstr {
	answer := &Cstr{C.allocate()}
	runtime.SetFinalizer(answer, func(c *Cstr) {
		C.free_allocated(c.cpointer)
		runtime.KeepAlive(c)
	})

	return answer
}
```

⚠️ **Зачем тут `runtime.KeepAlive(c)`?** Без него компилятор Go может решить, что `c` больше не используется сразу после последнего обращения к его полям, и теоретически посчитать объект недостижимым чуть раньше, чем нужно — например, ещё во время выполнения самого `C.free_allocated`, которое работает с "сырым" C-указателем и никак не связано с Go-объектом с точки зрения GC. `runtime.KeepAlive(c)` — это просто маркер для компилятора "считай `c` живым как минимум до этой строчки", без него можно словить use-after-free на C-стороне ещё до того, как C-код успеет отработать.
