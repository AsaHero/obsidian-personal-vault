## Базовые концепты

Функция — это фрагмент кода, к которому можно обратиться из другого места программы. Иногда называют подпрограммой. Под капотом с именем функции связан адрес её первой инструкции — именно туда передаётся управление при вызове.

Сразу разберём путаницу в терминах, которая часто всплывает:

**Параметры (parameters)** — это переменные в объявлении функции:

```go
func sqr(number int) int { // number — это параметр
    return number * number
}
```

**Аргументы (arguments)** — это конкретные значения, передаваемые при вызове:

```go
sqr(100) // 100 — это аргумент
```

Аргументы вычисляются **слева направо** — это важно, если в аргументах есть функции с побочными эффектами.

> ⚠️ **Всё копируется**: и аргументы при передаче в функцию, и результаты при возврате. Это напрямую влияет на производительность, когда гоняешь большие [[Structs|структуры]].

---

## Functions are First-Class Citizens

В Go функции — это **first-class citizens**. Они ведут себя как обычные переменные: их можно присваивать, передавать в другие функции и возвращать из них.

```go
var fn func(int) int = sqr  // присваиваем функцию переменной
fn(5)                        // вызываем через переменную

// передаём функцию как аргумент
func apply(numbers []int, fn func(int) int) []int { ... }

// возвращаем функцию
func multiplier(factor int) func(int) int {
    return func(x int) int { return x * factor }
}
```

Но есть два ограничения: функции **нельзя сравнивать** между собой и **нельзя брать адрес** у функции.

**Zero value** для функции — `nil`. Вызов nil-функции вызывает панику (об этом — в разделе про defer).

## Особенности функций в Go

**Нельзя перегружать функции.** Две функции с одинаковым именем (кроме исключений ниже) — ошибка компиляции.

**Нет параметров по умолчанию.** Хочешь опциональность — используй variadic, functional options pattern или отдельные конструкторы.

**Нет RVO и NRVO (Copy Elision).** В C++ компилятор может убрать лишние копии при возврате значений из функции. В Go этой оптимизации нет — каждый `return` честно копирует значение. (Хотя escape analysis и так решает большую часть этих проблем на практике, см. также [[Array and Slices#Array always in stack ?|аллокация массивов]] и [[Array and Slices#Does array of slice always allocated in heap ?|аллокация слайсов]].)

### Специальные функции: `init` и `_`

```go
func init() {} // вызывается автоматически при первой загрузке пакета
func _() {}    // функцию нельзя вызвать вообще — она анонимна для компилятора
```

`init` можно объявить несколько штук в одном файле — все вызовутся по порядку. Используется для инициализации состояния пакета. Не злоупотребляй: `init` сложно тестировать и порядок между пакетами не всегда очевиден.

`_` — это функция-черная дыра. Нужна обычно для того, чтобы выполнить side effect при импорте (например, регистрация драйверов через `import _ "..."`) или для dead code, который нужен "для документации".

### Variadic Parameters

```go
func sum(numbers ...int) int { // numbers внутри — это [[Array and Slices#Slices|[]int]]
    total := 0
    for _, n := range numbers {
        total += n
    }
    return total
}

sum(1, 2, 3)
sum([]int{1, 2, 3}...) // распаковка слайса
```

Variadic параметр может быть **только последним** в списке параметров. Логично: иначе компилятор не поймёт, где заканчивается один и начинается другой.

### Function Prototypes и Assembler

Хоть в Go нет обязательного порядка объявления функций (можно вызвать функцию до её объявления в файле), прототипы всё равно существуют внутри компилятора. Зачем они нужны **тебе**? Чтобы объявить сигнатуру функции в Go, а реализацию написать на **Assembler**:

```go
// файл add.go
func add(a, b int) int // только сигнатура, без тела

// файл add_amd64.s — реализация на asm
```

Именно так реализованы многие низкоуровневые части runtime (например, атомарные операции, хеш-функции).

### Inlining

Компилятор Go умеет **встраивать (inline)** маленькие функции прямо в место вызова, убирая overhead на создание стек-фрейма.

```go
//go:noinline  // явно запрещаем inlining для этой функции
func add(a, b int) int {
    return a + b
}
```

**Почему нельзя инлайнить всё подряд?** Потому что при инлайнинге код функции копируется в каждое место вызова. Большая функция, которую вызывают в 100 местах — это 100 копий её кода в text-сегменте. Бинарник вырастет в размере, что плохо для icache (instruction cache).

Go использует **budget-based model (cost-based model)**: у каждой функции есть "стоимость", и если она укладывается в бюджет — инлайнится. Можно посмотреть решения компилятора через `go build -gcflags="-m"`.

## Defer

`defer` откладывает вызов функции до момента, когда окружающая функция завершится (нормально или через panic).

**Главная неочевидность**: аргументы отложенной функции вычисляются **сразу** в момент `defer`, а не когда функция реально вызывается:

```go
func one() string {
    fmt.Println(1) // выполнится СРАЗУ при defer three(one())
    return "result"
}

func three(s string) {
    fmt.Println(3)
}

func main() {
    defer three(one()) // one() вызывается здесь, three() — в конце main
    fmt.Println(2)
}

// Output:
// 1
// 2
// 3
```

---

### Panic в defer при nil-функции

```go
func main() {
    defer fmt.Println("reachable 1") // выполнится
    var f func()
    defer f() // f == nil, но паника будет только КОГДА f() попытается вызваться

    fmt.Println("reachable 2") // тоже выполнится
}

// Output:
// reachable 2
// reachable 1
// panic: runtime error: invalid memory address or nil pointer dereference
```

`defer f()` не паникует мгновенно — он только ставит вызов в очередь. Паника случается когда main завершается и все defer'ы начинают выполняться по порядку.

### Defer + Named Return Values

Это один из самых неочевидных механизмов в Go. `defer` с замыканием может **модифицировать именованные возвращаемые значения**:

```go
func Modify(value int) (result int) { // result — именованный
    defer func() {
        result += value // модифицируем result ПОСЛЕ return
    }()
    return value + value // result = 10
}
// Modify(5) → result = 10, defer делает result += 5 → возвращает 15
```

А теперь без именованного возврата:

```go
func Modify(value int) int { // безымянный возврат
    var result int
    defer func() {
        result += value // модифицируем локальную переменную result
    }()
    result = value + value
    return result // копирует result (=10) в безымянный return-слот
}
// Modify(5) → возвращает 10, потому что defer меняет локальный result,
// а не тот result-слот, который уже скопировался в return
```

> ⚠️ Разница принципиальная: `(result int)` — это **синоним для return-слота**, а просто `var result int` — это **локальная переменная**. `return result` копирует локальную переменную в безымянный return-слот, и после этого defer на локальную переменную уже ничего не влияет.

## Functional Programming

Сначала быстро по типам подходов:

**Императивный подход** — описываешь _как_ делать. Хочешь отфильтровать числа — пишешь цикл с условием.

**Декларативный подход** — описываешь _что_ делать. Пишешь `filterEvenNumbers(numbers)` или SQL `WHERE`, а реализацию не знаешь и не хочешь знать.

```go
// императивно
var result []int
for _, n := range numbers {
    if n%2 != 0 {
        result = append(result, n)
    }
}

// декларативно
result := filterEvenNumbers(numbers) // детали скрыты
```

### Базовые концепты FP

**Функция** — делает одно логическое действие и возвращает значение.

**Процедура** — вызывается ради побочных эффектов (записать в файл, отправить запрос).

**Предикат** — функция, возвращающая `bool` (`isEven`, `isEmpty`).

**Функция высшего порядка (Higher-Order Function)** — принимает функцию как аргумент или возвращает функцию:

```go
func forEach(data []int, fn func(int) int) []int {
    newData := make([]int, 0, len(data))
    for _, value := range data {
        newData = append(newData, fn(value))
    }
    return newData
}

// использование
newData := forEach([]int{1, 2, 3, 4}, func(value int) int {
    return value * value
})
```

### Pure Functions

**Чистая функция (pure function)** — детерминированная и без побочных эффектов. Одинаковые аргументы → всегда одинаковый результат, и ничего снаружи не трогает.

```go
// грязная функция — нарушает сразу несколько правил
func dirtySum(x, y *int) int {
    result := *x + *y

    *x = 0              // (1) мутирует входные данные
    *y = 0
    fmt.Println(result) // (2) side effect — I/O
    cache[result] = struct{}{} // (3) мутирует глобальное состояние
    os.Getenv("param")  // (4) зависит от внешнего окружения
    result += rand.Intn(100) // (5) недетерминированный результат

    return result
}

// чистая функция — просто считает, ничего не трогает
func pureSum(x, y int) int {
    return x + y
}
```

Чистые функции легко тестировать, легко кэшировать (memoize) и можно безопасно вызывать из нескольких goroutine без мьютексов.

### Composition

Compose — это обёртка, которая собирает несколько функций в одну, применяя их по цепочке:

```go
func compose(fn ...func(int) int) func(int) int {
    return func(value int) int {
        for _, f := range fn {
            value = f(value)
        }
        return value
    }
}

fn := compose(sqr, neg, sqr) // sqr(neg(sqr(x)))
fmt.Println(fn(4))            // sqr(neg(16)) = sqr(-16) = 256
```

---

### Decorator

Decorator — это обёртка над функцией, которая добавляет поведение (логирование, метрики, авторизацию), не меняя сигнатуру:

```go
func Calculate(x, y int, fn func(int, int) int) int {
    fmt.Printf("x=%d y=%d\n", x, y) // логирование
    return fn(x, y)
}

Calculate(10, 10, Add)
Calculate(10, 10, Mul)
```

Это и есть паттерн Decorator в функциональном стиле — оборачиваем поведение, не меняя саму функцию.

---

### Pipeline

Pipeline — последовательное применение функций к значению. По сути то же, что compose, но синтаксически читается слева направо:

```go
func pipe(value int, fn ...func(int) int) int {
    for _, f := range fn {
        value = f(value)
    }
    return value
}

func reverse(fn ...func(int) int) []func(int) int {
    for i := 0; i < len(fn)/2; i++ {
        fn[i], fn[len(fn)-i-1] = fn[len(fn)-i-1], fn[i]
    }
    return fn
}

// три способа записать одно и то же: sqr(5), затем neg, затем inc
decorationResult := inc(neg(sqr(5)))       // nested — читается справа налево
compositionResult := pipe(5, sqr, neg, inc) // pipeline — читается слева направо
reverseResult := pipe(5, reverse(inc, neg, sqr)...) // "как compose" через reverse
```

### Closure

Замыкание — функция, которая **захватывает переменные** из области видимости своей родительской функции и продолжает с ними работать после того, как родительская функция вернула управление:

```go
func Generator(start int) func() int {
    return func() int {
        r := start
        start++ // захватываем и изменяем переменную из Generator
        return r
    }
}

gen := Generator(100)
gen() // 100
gen() // 101
gen() // 102 — состояние живёт внутри замыкания
```

⚠️ Классический баг с замыканием в цикле:
 
 ```go
funcs := make([]func(), 3)

for i := 0; i < 3; i++ {
     // shadowing! 
     // Без этого все три замыкания захватят одну переменную i
	i := i	 
    
    funcs[i] = func() { fmt.Println(i) }
}

 ```

### Continuation

Continuation — это когда ты передаёшь в функцию callback-и для разных исходов вместо того, чтобы возвращать значение или паниковать:

```go
func Divide(lhs, rhs int, onSuccess func(int), onError func()) {
    if rhs == 0 {
        onError()
    } else {
        onSuccess(lhs / rhs)
    }
}

Divide(100, 10,
    func(result int) { fmt.Println(result) },
    func() { fmt.Println("деление на ноль") },
)
```

Похоже на callback-и в JavaScript. Использовать стоит когда нужно разрулить несколько исходов одной операции и не хочется городить несколько return-ов или error handling. Не злоупотребляй — при вложенных continuation-ах получается "callback hell".

### Recursion

Функция, вызывающая саму себя. Бывает двух видов:

- **Прямая** — функция вызывает себя напрямую
- **Косвенная** — A вызывает B, B вызывает A

Важный концепт — **хвостовая рекурсия (tail recursion)**. Это когда рекурсивный вызов — **последнее действие** функции, без дополнительных операторов после него. Это важно, потому что компилятор в таком случае может оптимизировать рекурсию в обычный цикл с одним стек-фреймом:

```go
// НЕ хвостовая — после рекурсивного вызова ещё есть умножение на number
func SlowFactorial(number int) int {
    if number == 0 {
        return 1
    }
    return number * SlowFactorial(number-1) // нужно хранить number в стеке!
}

// Хвостовая — последнее действие это именно рекурсивный вызов
func FastFactorial(number int) int {
    return factorial(number, 1)
}

func factorial(number, accumulator int) int {
    if number == 1 {
        return accumulator
    }
    return factorial(number-1, number*accumulator) // просто меняем аргументы
}
```

В `SlowFactorial` перед тем как вернуть результат нужно ждать рекурсию и потом умножать на `number` — поэтому `number` нужно держать на стеке для каждого вызова. В `FastFactorial` все промежуточные данные переедены в аргументах — стек-фрейм можно переиспользовать.

> ⚠️ **Важно**: компилятор Go не умеет оптимизировать хвостовую рекурсию. Так что `FastFactorial` быстрее не потому что TCO, а потому что меньше арифметики (нет умножения после рекурсии). При очень глубокой рекурсии оба варианта съедят стек — Go увеличивает goroutine stack динамически, но предел существует.

### Memoization

Memoization — кэширование результатов чистой функции. Если вызвали с теми же аргументами — возвращаем из кэша, не пересчитываем:

```go
func Fibonacci(n int) int {
    if n <= 2 {
        return 1
    }
    return Fibonacci(n-1) + Fibonacci(n-2) // O(2^n) — экспоненциально
}

func FibonacciWithMemoization(number int) int {
    cache := make([]int, number+1)
    var impl func(n int) int
    impl = func(n int) int {
        if cache[n] != 0 {
            return cache[n] // уже считали — отдаём из кэша
        }
        if n <= 2 {
            return 1
        }
        cache[n] = impl(n-1) + impl(n-2)
        return cache[n]
    }
    return impl(number)
}
```

С memoization сложность падает с O(2^n) до O(n) — каждое число Фибоначчи считается ровно один раз.

## OS Stack on Function Call

(если интересно, почему выделение памяти именно на стеке в принципе настолько быстрее кучи — см. [[Allocators#Почему выделение в стеке быстрее, чем в куче?|Allocators]])

Стек — участок памяти для хранения временных данных (локальные переменные, адреса возврата, аргументы). Стек растёт **вниз** (от старших адресов к младшим).

Три ключевых регистра:

**SP (Stack Pointer)** — указывает на вершину стека (последний добавленный элемент, то есть на наименьший адрес).

**BP (Base Pointer)** — указывает на начало текущего стек-фрейма. Статичен внутри одной функции — именно относительно него адресуются локальные переменные и аргументы.

**IP (Instruction Pointer)** — указывает на следующую инструкцию для выполнения.

```
Память (адреса растут вверх, стек растёт вниз):

  High addr │ ...                     │
            │ [данные вызывающего]    │
            │ ...                     │ <- BP (при входе в функцию)
            │ ...                     │
  Low addr  │ [вершина стека]         │ <- SP
```

---

### JMP, CALL, RET

**JMP** просто перемещает IP в другой адрес. Но для вызова функции этого мало — после функции нужно вернуться обратно.

```
jmp foo
; после foo некуда возвращаться — адрес возврата не сохранён
```

**CALL** перед прыжком **пушит адрес возврата** (адрес инструкции сразу после CALL) на стек, потом делает JMP:

```
; Было:
;   │ local vars │ <- SP
;   │ ...        │
;
; call foo:
;   1. push адрес следующей инструкции (return address)
;   2. jmp foo

; Стало:
;   │ return addr│ <- SP  ← CALL положил сюда адрес возврата
;   │ local vars │
;   │ ...        │
```

**RET** делает обратное — **попит адрес возврата** со стека и прыгает туда:

```
; ret:
;   1. pop return address → IP
;   2. SP растёт (адрес убран со стека)

; Стало:
;   │ local vars │ <- SP  ← SP вернулся к вызывающему
;   │ ...        │
```

---

### Полный вызов функции: создание стек-фрейма

После CALL мы уже внутри функции. Первое что делаем — создаём стек-фрейм:

```asm
call foo         ; push return addr, jmp foo

; Внутри foo:
push BP          ; сохраняем BP вызывающего
mov  BP, SP      ; BP теперь указывает на начало нашего фрейма

push 10          ; локальная переменная a = 10
push 20          ; локальная переменная b = 20
push 30          ; локальная переменная c = 30
```

Состояние стека после этого:

```
High addr │ ...caller data...  │
          │ return address     │ <- BP + 8 (смещение относительно BP)
          │ old BP value       │ <- BP      (начало нашего фрейма)
          │ a = 10             │ <- BP - 8
          │ b = 20             │ <- BP - 16
          │ c = 30             │ <- BP - 24  <- SP
Low addr
```

BP статичен — относительно него мы знаем, где лежат наши переменные (`BP-8`, `BP-16`, ...) и где адрес возврата (`BP+8`). SP будет двигаться при каждом push/pop.

---

### Возврат из функции

```asm
mov SP, BP   ; "освобождаем" локальные переменные — SP скакнул к началу фрейма
             ; (данные не обнуляются, там просто будет "мусор" — это нормально)
pop BP       ; восстанавливаем BP вызывающего из стека
ret          ; берём return address, кидаем IP туда, SP уменьшается
```

После этого мы снова в вызывающей функции с её BP и SP как будто ничего не было.

### Передача аргументов: STDCALL

До Go 1.17 аргументы передавались через стек по соглашению **STDCALL** — в **обратном** порядке (последний аргумент пушится первым):

```asm
; вызов foo(1, 2, 3)
push 3       ; arg3
push 2       ; arg2
push 1       ; arg1
call foo
```

Стек при входе в `foo` (после push BP; mov BP, SP):

```
High addr │ arg3 = 3          │ <- BP + 20
          │ arg2 = 2          │ <- BP + 16
          │ arg1 = 1          │ <- BP + 12  (первый аргумент ближе к BP)
          │ return address    │ <- BP + 8
          │ old BP            │ <- BP = SP
Low addr
```

Аргументы адресуются как `[BP+12]`, `[BP+16]`, `[BP+20]`. Обратный порядок нужен именно для того, чтобы первый аргумент (`arg1`) всегда был по предсказуемому смещению от BP, независимо от количества аргументов.

### ABI Change в Go 1.17

В Go 1.17 для архитектуры **AMD64** сменился **ABI (Application Binary Interface)**: вместо стека аргументы и возвращаемые значения передаются через **регистры процессора**.

Регистры — это память внутри процессора, доступ к ней на порядок быстрее, чем к RAM (и стеку в RAM). Передача через регистры убирает overhead на push/pop аргументов и в ряде случаев полностью исключает создание стек-фрейма для маленьких функций.

Это одна из причин, почему производительность Go-программ заметно выросла начиная с 1.17 без изменений в исходном коде.

## Stack Overflow

Когда рекурсия уходит слишком глубоко или на стеке выделяется слишком много памяти — стек переполняется. В Go goroutine stack растёт динамически (начинает с ~2KB и расширяется по мере необходимости), поэтому stack overflow случается реже, чем в системных языках.

> ⚠️ В Go нельзя сделать `recover()` от **OOM (Out Of Memory)**. Если программа исчерпала всю доступную память, `recover` в defer не поможет — процесс завершится.

```go
func infinite() {
    infinite() // stack overflow — goroutine stack вырастет до лимита и упадёт
}
```

При stack overflow Go выведет `runtime: goroutine stack exceeds 1000000000-byte limit` и упадёт со всей программой — это **не** [[Error Handling#Go не поддерживает исключения (но почти)|паника]], от которой можно оправиться через `recover`. Стек горутины при этом растущий и переезжает в памяти по мере надобности — подробнее в [[Allocators#Стек реально "переезжает" при росте|Allocators]] и в [[DeepGo/Goroutines|Goroutines]].
