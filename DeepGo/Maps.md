## Что такое Hash Table?

Hash table — это структура данных, которая хранит пары ключ-значение и даёт доступ к ним за **O(1)** в среднем случае. Работает как словарь: говоришь "дай мне значение по ключу X" — получаешь его почти мгновенно, без перебора всех элементов.

Внутри это просто массив бакетов (buckets). Магия в том, как именно мы решаем, в какой бакет класть значение — этим занимается hash function.

---

## Hash Function

Главная задача hash function — превратить ключ (строку, число, да что угодно) в индекс массива. Самая наивная реализация — взять сумму байтов ключа и взять остаток от деления на размер таблицы:

```go
func hash(key string, tableSize int) int {
    sum := 0
    for _, ch := range key {
        sum += int(ch)
    }
    // остаток от деления — это и есть индекс бакета
    return sum % tableSize
}
```

Проблема сразу видна: `"ab"` и `"ba"` дадут одинаковый хеш, потому что сумма байтов одна и та же. Поэтому в реальных реализациях используют серьёзные алгоритмы: **FNV**, **MurmurHash**, **SipHash**. Go, например, использует вариацию AES/SipHash.

---

## Hash Function Rules

Хорошая hash function должна быть:

- **Детерминированной** — один и тот же ключ всегда даёт один и тот же хеш
- **Быстрой** — вызывается при каждой операции, поэтому тормоза тут недопустимы
- **Равномерно распределяющей** — ключи должны равномерно разлетаться по бакетам, иначе в одном месте получим кучу коллизий, а остальные бакеты будут пустыми
- **С лавинным эффектом** — маленькое изменение ключа даёт сильно разный хеш (чтоб похожие ключи не ложились в один бакет)

> ⚠️ **Подводный камень в Go**: hash function для map рандомизирована при старте программы (random seed). Поэтому порядок итерации по `map` никогда не гарантирован и меняется от запуска к запуску. Это сделано специально — защита от **Hash DoS атак**, когда злоумышленник подбирает ключи, которые все попадают в один бакет и деградируют поиск до O(n).

---

## What is Collision?

Коллизия — это когда два разных ключа дают одинаковый хеш. Это **неизбежно**: у нас конечный массив бакетов, а ключей может быть бесконечно много. По принципу Дирихле (pigeonhole principle) — если ключей больше, чем бакетов, коллизии будут гарантированно.

```go
// Допустим tableSize = 5
hash("cat", 5) // = 2
hash("act", 5) // = 2 — коллизия! разные ключи, один бакет
```

Есть два основных способа разруливать коллизии:

- **Chaining** — каждый бакет хранит список элементов
- **Open Addressing** — ищем другой свободный слот в том же массиве

---

## Collision Resolving by Chaining Method

Идея простая: каждый бакет — не одно значение, а контейнер (обычно linked list), который может хранить несколько пар ключ-значение с одинаковым хешем.

```
Бакеты:
[0] -> nil
[1] -> ("dog", 1) -> nil
[2] -> ("cat", 42) -> ("act", 7) -> nil  // коллизия — оба в бакете 2
[3] -> nil
[4] -> ("rat", 99) -> nil
```

```go
type Node struct {
    key   string
    value any
    next  *Node // следующий элемент в цепочке (при коллизии)
}

type HashTable struct {
    buckets []*Node
    size    int // количество бакетов
    count   int // количество элементов
}

func (ht *HashTable) Set(key string, value any) {
    idx := hash(key, ht.size)
    node := ht.buckets[idx]

    // идём по цепочке — вдруг ключ уже есть, тогда просто обновляем
    for node != nil {
        if node.key == key {
            node.value = value
            return
        }
        node = node.next
    }

    // ключа нет — вставляем в начало цепочки (O(1))
    newNode := &Node{key: key, value: value, next: ht.buckets[idx]}
    ht.buckets[idx] = newNode
    ht.count++
}

func (ht *HashTable) Get(key string) (any, bool) {
    idx := hash(key, ht.size)
    node := ht.buckets[idx]

    for node != nil {
        if node.key == key {
            return node.value, true
        }
        node = node.next
    }
    return nil, false
}
```

**Проблема**: чем больше коллизий, тем длиннее цепочки, тем медленнее поиск. В худшем случае всё вырождается в O(n) — как обычный linked list. Именно для борьбы с этим придумали Load Factor.

---

### Load Factor

Load Factor — коэффициент загруженности таблицы. Показывает, насколько "заполнена" хеш-таблица:

```
load_factor = count / bucket_count
```

```go
func (ht *HashTable) loadFactor() float64 {
    return float64(ht.count) / float64(ht.size)
}
```

Когда load factor превышает порог (обычно **0.6–0.75**), таблица понимает, что бакетов не хватает, и запускает **re-indexing**. В Go порог около 6.5 элементов на бакет (у них нестандартная метрика, но суть та же).

---

### Re-indexing / Evacuation

Вот тут важный момент — **не путать с reallocation в динамических массивах ([[Array and Slices#Slices|слайсах]])!**

В слайсе при расширении мы просто выделяем новый массив побольше и байтово копируем элементы — всё, индексы те же самые.

В hash table так **нельзя**! Потому что хеш зависит от размера таблицы:

```go
// Было 4 бакета:
hash("cat", 4) // = 2 — лежит в бакете 2

// Стало 8 бакетов — тот же ключ, другой индекс!
hash("cat", 8) // = 6 — теперь должен лежать в бакете 6
```

Если просто скопируем — получим полную рассинхронизацию: ищем `"cat"`, хеш говорит "иди в бакет 6", а там пусто (потому что элемент лежит в старом бакете 2).

Поэтому re-indexing работает так:

1. Создаём новый массив бакетов (обычно в 2 раза больше)
2. Для **каждого элемента** заново считаем хеш с новым размером
3. Кладём в новый бакет по новому хешу

```go
func (ht *HashTable) reindex() {
    newSize := ht.size * 2
    newBuckets := make([]*Node, newSize)

    for _, node := range ht.buckets {
        for node != nil {
            // сохраняем next ДО переключения указателей
            next := node.next

            // заново считаем хеш для нового размера — это ключевой момент
            newIdx := hash(node.key, newSize)
            node.next = newBuckets[newIdx]
            newBuckets[newIdx] = node

            node = next
        }
    }

    ht.buckets = newBuckets
    ht.size = newSize
}
```

> ⚠️ Именно поэтому re-indexing тяжелее reallocation — мы не просто копируем байты, а пересчитываем хеш для каждого элемента. В Go это называется **evacuation** и происходит **постепенно** (incremental evacuation) — при каждой операции с map эвакуируется небольшая часть элементов. Это чтобы не было одной гигантской паузы.

---

### How to Skip Null Buckets While Iteration

**Проблема**: при `range` по таблице нам приходится проходить по всем бакетам подряд, включая пустые. Если бакетов 1000, а элементов 10 — 990 итераций вхолостую.

**Решение**: добавить doubly linked list поверх всех элементов таблицы, связывая их между собой независимо от того, в каком они бакете:

```go
type Node struct {
    key   string
    value any
    next  *Node // следующий в той же цепочке коллизий внутри бакета

    // для быстрой итерации — общий список всех элементов таблицы
    iterPrev *Node
    iterNext *Node
}

type HashTable struct {
    buckets   []*Node
    iterHead  *Node // начало общего списка для итерации
    size      int
    count     int
}
```

```
Бакеты:
[0] -> nil
[1] -> [dog]
[2] -> [cat] -> [act]
[4] -> [rat]

Iteration list (связываем все элементы):
[dog] <-> [cat] <-> [act] <-> [rat]
```

При итерации идём по `iterNext` — никаких пустых бакетов, сразу переходим к следующему элементу.

**Но как тогда работает поиск?** Ведь в iteration list все ключи перемешаны из разных бакетов...

Очень просто: поиск работает как обычно — считаем хеш ключа, идём в конкретный бакет, там ищем по ключу. Iteration list используется **только** для `range`, для `Get`/`Set` он не нужен.

При поиске происходит вот что:

1. Хешируем искомый ключ → получаем номер бакета
2. Идём в этот бакет
3. Сравниваем ключи в цепочке этого бакета

Так что даже если `iterNext` у элемента указывает на элемент из другого бакета — это не мешает поиску.

**Почему doubly, а не singly linked list?**

Потому что при удалении нам нужно вытащить элемент из середины списка. Без ссылки на предыдущий элемент — это O(n):

```go
// Удаление из doubly linked list — O(1)
func (node *Node) removeFromIterList() {
    if node.iterPrev != nil {
        node.iterPrev.iterNext = node.iterNext
    }
    if node.iterNext != nil {
        node.iterNext.iterPrev = node.iterPrev
    }
}
```

---

## Collision Resolving By Open Addressing

Второй подход — вообще не создавать цепочки и отдельные ноды. Всё хранится в **одном плоском массиве**. При коллизии ищем следующий свободный слот по какому-то алгоритму — это и есть **probing**.

```go
type Entry struct {
    key      string
    value    any
    occupied bool
    deleted  bool // tombstone флаг — объясню ниже почему он нужен
}

type HashTable struct {
    entries []Entry
    size    int
    count   int
}
```

**Плюсы**: cache-friendly — всё в одном куске памяти, процессор счастлив, меньше аллокаций.  
**Минусы**: при высоком load factor поиск деградирует, удаление хитрее.

---

### What is Probing?

Probing — это алгоритм поиска следующего свободного слота, когда текущий занят. Есть несколько видов:

---

#### Linear Probing

Самый простой: если слот занят, идём на следующий (+1, +1, +1...):

```go
func (ht *HashTable) Set(key string, value any) {
    idx := hash(key, ht.size)

    for ht.entries[idx].occupied && ht.entries[idx].key != key {
        idx = (idx + 1) % ht.size // оборачиваемся по кругу
    }

    ht.entries[idx] = Entry{key: key, value: value, occupied: true}
    ht.count++
}
```

**Проблема**: **primary clustering** — элементы собираются в длинные кластеры, и чем длиннее кластер, тем дольше поиск для всех новых элементов, которые в него попадают.

```
После вставки: "cat"(idx=2), "act"(idx=2→3), "tac"(idx=2→3→4)
[_, _, cat, act, tac, _, _, _]  // кластер растёт — все новые элементы с хешем 2,3,4 будут тормозить
```

---

#### Quadratic Probing

Прыгаем по квадратичной формуле: +1², +2², +3²... (то есть +1, +4, +9, +16):

```go
func (ht *HashTable) Set(key string, value any) {
    base := hash(key, ht.size)

    for i := 0; ; i++ {
        // квадратичный шаг: i*i
        idx := (base + i*i) % ht.size

        if !ht.entries[idx].occupied || ht.entries[idx].key == key {
            ht.entries[idx] = Entry{key: key, value: value, occupied: true}
            ht.count++
            return
        }
    }
}
```

Лучше борется с primary clustering, но появляется **secondary clustering** — разные ключи с одинаковым хешем всё равно идут по одинаковому пути.

---

#### Double Hashing

Самый продвинутый вариант: при коллизии шаг считается **второй** hash function. Разные ключи — разные шаги — разные пути:

```go
func hash2(key string, tableSize int) int {
    // важно: hash2 никогда не должна возвращать 0,
    // иначе будем вечно топтаться на месте
    return 7 - (simpleHash(key) % 7)
}

func (ht *HashTable) Set(key string, value any) {
    base := hash(key, ht.size)
    step := hash2(key, ht.size) // индивидуальный шаг для каждого ключа

    for i := 0; ; i++ {
        idx := (base + i*step) % ht.size

        if !ht.entries[idx].occupied || ht.entries[idx].key == key {
            ht.entries[idx] = Entry{key: key, value: value, occupied: true}
            ht.count++
            return
        }
    }
}
```

Самое равномерное распределение, минимум кластеризации. Но считать два хеша чуть дороже — на практике это незначительно.

---

### Removing Must Have a Tombstone Flag

Это один из самых неочевидных моментов в open addressing. Почему нельзя просто обнулить слот при удалении?

```
// Вставляем три элемента, все получили хеш 0, linear probing:
[0: "cat"] [1: "dog"] [2: "rat"] [3: _] [4: _]

// Удаляем "dog" (слот 1), просто обнуляем:
[0: "cat"] [1: EMPTY] [2: "rat"] [3: _] [4: _]

// Теперь ищем "rat":
// hash("rat") = 0 → смотрим слот 0, там "cat" — не то → идём +1
// смотрим слот 1 → ПУСТО → решаем, что "rat" нет в таблице → BUG! 🐛
```

Поиск остановился на пустом слоте и не дошёл до "rat". Поэтому удалённые слоты **помечаем tombstone флагом** — "тут что-то было, но удалено, продолжай поиск":

```go
func (ht *HashTable) Delete(key string) {
    idx := hash(key, ht.size)

    // идём пока слот занят ИЛИ помечен как удалённый (tombstone)
    for ht.entries[idx].occupied || ht.entries[idx].deleted {
        if ht.entries[idx].occupied && ht.entries[idx].key == key {
            ht.entries[idx].occupied = false
            ht.entries[idx].deleted = true // ставим tombstone — не стираем слот полностью!
            ht.count--
            return
        }
        idx = (idx + 1) % ht.size
    }
}

func (ht *HashTable) Get(key string) (any, bool) {
    idx := hash(key, ht.size)

    for ht.entries[idx].occupied || ht.entries[idx].deleted {
        // через tombstone перешагиваем, не останавливаемся
        if ht.entries[idx].occupied && ht.entries[idx].key == key {
            return ht.entries[idx].value, true
        }
        idx = (idx + 1) % ht.size
    }
    return nil, false
}
```

> ⚠️ **Подводный камень**: tombstone-ы накапливаются со временем и сами по себе замедляют поиск (всё равно приходится их проходить). Решение — при re-indexing tombstone-ы просто не копируем, они исчезают сами собой.

---

### Re-indexing / Evacuation (Open Addressing)

Принцип тот же, что и в chaining — при превышении load factor создаём новый массив побольше и перехешируем все элементы. Tombstone-ы при этом не переносим — это естественная очистка мусора.

```go
func (ht *HashTable) reindex() {
    newSize := ht.size * 2
    newEntries := make([]Entry, newSize)

    for _, entry := range ht.entries {
        // пропускаем пустые слоты и tombstone-ы
        if !entry.occupied {
            continue
        }

        // перехешируем с новым размером
        idx := hash(entry.key, newSize)
        for newEntries[idx].occupied {
            idx = (idx + 1) % newSize
        }
        newEntries[idx] = Entry{key: entry.key, value: entry.value, occupied: true}
    }

    ht.entries = newEntries
    ht.size = newSize
}
```

> Для open addressing порог load factor обычно ставят ниже, чем для chaining — около **0.5–0.7**. Потому что при высоком заполнении probing деградирует быстрее: нужно идти по цепочке шагов до первого пустого (не tombstone!) слота.

# Maps In Go

## How map looks like under the hood?

Словарь в Go — это **указатель** на структуру `hmap`. Это важно понимать сразу, потому что от этого зависит поведение мапы во всех остальных случаях.

```go
type hmap struct {
    count     int    // количество элементов, must be first (используется len())
    flags     uint8  // флаги состояния (конкурентная запись, итераторы и т.д.)
    B         uint8  // log_2 от количества бакетов (вмещает до loadFactor * 2^B элементов)
    noverflow uint16 // примерное число overflow-бакетов
    hash0     uint32 // hash seed, генерируется при создании мапы

    buckets    unsafe.Pointer // массив 2^B бакетов, может быть nil если count == 0
    oldbuckets unsafe.Pointer // старый массив (половина размера), не nil только во время роста
    nevacuate  uintptr        // счётчик прогресса evacuation/migration

    extra *mapextra // доп. поля для оптимизации памяти и GC
}
```

Главное здесь — **именно указатель**, а не сама структура, как, например, в [[Strings#How strings look like under the hood?|string]] или [[Array and Slices#Slice under the hood|slice]] (там тоже есть указатель внутри, но сама структура — значение).

Это значит, что когда мы передаём мапу в функцию, копируется только указатель на `hmap`, а сама структура — общая:

```go
func change(data map[int]int) {
	data = map[int]int{2: 20} // меняем ЛОКАЛЬНЫЙ указатель, оригинала это не касается
}

func main() {
	data := map[int]int{1: 10}
	fmt.Println(data) // map[1:10]
	change(data)
	fmt.Println(data) // map[1:10] — не изменилось
}
```

> ⚠️ Это частая путаница: люди думают, что если мапа "как указатель", то любые изменения внутри функции видны снаружи. Это правда **только** для изменений содержимого (`data[1] = 100` сработает), но не для переприсваивания самой переменной (`data = newMap` — это уже локальная подмена указателя).

---

## Each Map Object Has a Unique Hash Seed

Каждый созданный объект мапы получает свой собственный `hash0` — случайный seed. Это значит, что хеш одного и того же ключа будет **разным** в двух разных мапах:

```go
m1 := make(map[string]int)
m2 := make(map[string]int)

// hash("key") внутри m1 != hash("key") внутри m2
// потому что у каждой мапы свой hash0
```

Зачем это нужно — та же защита от Hash DoS атак, о которой говорили в общей теме про hash tables: даже если злоумышленник подберёт ключи, которые коллизят в одной мапе, в другой (с другим seed) они коллизить не будут.

---

## How Buckets Are Created While Init?

Когда вызываешь `make(map[K]V)` без хинта — создаётся **один** бакет. Но если передать хинт (`make(map[K]V, n)`), Go **не** создаёт мапу ровно на `n` элементов — он выделяет место **как минимум** для `n`, округляя вверх до степени двойки бакетов:

|Hint Range|Bucket Count|Capacity|
|---|---|---|
|0 - 8|1|8|
|9 - 13|2|16|
|14 - 26|4|32|
|27 - 52|8|64|
|53 - 104|16|128|
|105 - 208|32|256|
|209 - 416|64|512|
|417 - 832|128|1024|
|833 - 1664|256|2048|

> ⚠️ Подводный камень: `make(map[int]int, 10)` выделит память на **16** элементов, а не на 10. Если ты рассчитываешь память впритык — учитывай этот overhead.

---

## What Is a Bucket?

```go
type bmap struct {
    tophash  [8]uint8 // старшие 8 бит хеша для каждого из 8 ключей
    keys     [8]int   // 8 ключей упакованы подряд
    values   [8]int   // 8 значений упакованы подряд
    overflow *bmap    // указатель на overflow-бакет, если коллизий > 8
}
```

Под капотом бакет — это три массива по 8 элементов плюс указатель на overflow-бакет.

**Почему ключи и значения хранятся отдельными массивами, а не парами `(key, value)`?**

Это принцип **Data-Oriented Design**. Когда ключи лежат подряд и значения лежат подряд:

- Память используется компактнее за счёт правильного alignment (без padding между парами)
- Сравнение ключей быстрее — процессор просто бежит по массиву ключей, не перепрыгивая через значения (лучше cache locality)

**Зачем нужен TopHash?**

`tophash` хранит старшие 8 бит хеша каждого ключа в бакете. Это оптимизация поиска: вместо того чтобы сразу сравнивать полные ключи (что дорого для строк, структур и т.д.), Go сначала сравнивает **однобайтовые** значения tophash. Только если они совпали — переходит к полному сравнению ключей.

```
Ищем ключ "foo", его хеш начинается с 0xA3

tophash: [0x12, 0xA3, 0x05, ...]
            ↑     ↑
          мимо   совпал! → сравниваем "foo" с keys[1] полностью
```

Это сильно ускоряет случаи, когда в бакете много элементов или есть overflow-бакеты — большую часть кандидатов отсеиваем по одному байту, не трогая полные ключи.

У `tophash` есть зарезервированные значения для служебных состояний:

```go
emptyRest      = 0 // ячейка пустая, и дальше (включая overflow) тоже пусто
emptyOne       = 1 // эта ячейка пустая
evacuatedX     = 2 // ключ/значение валидны, эвакуированы в первую половину новой таблицы
evacuatedY     = 3 // то же самое, но во вторую половину
evacuatedEmpty = 4 // ячейка пуста, бакет эвакуирован
minTopHash     = 5 // минимальное значение tophash для нормальной заполненной ячейки
```

То есть реальные хеши начинаются с 5 — значения 0-4 зарезервированы под состояния, связанные с evacuation.

## Re-indexing / Evacuation

Переиндексация в Go происходит **постепенно** (incremental), а не одним большим блокирующим шагом.

Триггер: load factor достигает **~6.5 элементов на бакет** (это ~80% заполненности). Когда это происходит:

1. Создаётся новый массив бакетов **в 2 раза больше**
2. Старый массив переезжает в `oldbuckets`
3. При каждой операции записи/удаления эвакуируется **несколько бакетов** из `oldbuckets` в новые бакеты — пересчитывается хеш, элементы раскладываются по новым местам

Именно для этого в `hmap` нужно поле `oldbuckets` — пока эвакуация не закончена, старые данные ещё там.

**Плюсы и минусы такого подхода:**

- ✅ Нет одного огромного "burst"-события, который заморозит программу на заметное время
- ❌ Во время эвакуации запись и удаление становятся чуть медленнее (нужно эвакуировать попутно)
- ❌ Поиск во время эвакуации может требовать заглянуть **в оба** массива — и в новый, и в `oldbuckets`

## How Maps Work With Any Kind of Data Type?

Мапы появились в Go раньше generics, и работают они через `unsafe.Pointer`. Под капотом каждая операция с мапой превращается в вызов runtime-функции:

```go
// make(map[string]int, 5)        → runtime.makemap(...)
// data["key"]                     → runtime.mapaccess1(t, h, key) unsafe.Pointer
// value, ok := data["key"]        → runtime.mapaccess2(t, h, key) (unsafe.Pointer, bool)
// data["key"] = 100                → runtime.mapassign(t, h, key) unsafe.Pointer
// delete(data, "key")              → runtime.mapdelete(t, h, key)
```

То есть компилятор просто переписывает синтаксис мапы в вызовы этих [[Functions|функций]], передавая указатели на ключ как `unsafe.Pointer` — поэтому одна и та же функция runtime может работать с мапой любого типа.

Для этого при создании мапы создаётся объект `maptype`, который хранит всю мета-информацию о типах ключа и значения:

```go
type maptype struct {
	typ    _type
	key    *_type
	elem   *_type
	bucket *_type

	hasher     func(unsafe.Pointer, uintptr) uintptr // функция хеширования (key, seed) -> hash
	keysize    uint8
	elemsize   uint8
	bucketsize uint16
	flags      uint32
}
```

> 💡 Важный момент: `maptype` **переиспользуется**. Если ты создал три мапы типа `map[string]int`, у них будет **один общий** объект `maptype` — он описывает тип, а не конкретный инстанс.

А `_type` — это дескриптор самого типа (ключа или значения), который содержит, помимо прочего, функцию для сравнения объектов этого типа:

```go
type _type struct {
	size_      uintptr
	ptrdata    uintptr
	hash       uint32 // хеш типа — чтобы не пересчитывать каждый раз
	align      uint8

	equal func(unsafe.Pointer, unsafe.Pointer) bool // как сравнивать два объекта этого типа

	gcdata *byte // данные для GC
	str    nameOff
}
```

# Map Pitfalls in Go

## Map Key as Float

Угадай, что выведет этот код:

```go
var value1 float32 = 0.3
var value2 float32 = 0.6
data := make(map[float32]struct{})
data[value1+value2] = struct{}{}

var result float32 = 0.9
_, found := data[result]
fmt.Println(found)
```

Вывод:

```
false
```

Причина — стандартная погрешность float-арифметики. `0.3 + 0.6` и `0.9` — это **разные** битовые представления float32, а значит и разные хеши. Они выглядят одинаково при печати, но это не один и тот же ключ.

> ⚠️ Это не лечится даже прямым сравнением: `if result == value1 + value2` тоже даст `false`. Сравнивать float-ы через `==` — в принципе плохая идея, нужно использовать epsilon:

```go
const (
	EPSILON_FLOAT_64 = 1.0 / (1 << 52) // ~1.11e-16
	EPSILON_FLOAT_32 = 1.0 / (1 << 23) // ~1.19e-07
)

if abs(val1-val2) < EPSILON_FLOAT_32 {
	fmt.Println("equal")
}
```

**Вывод**: не используй float как ключ мапы, если можешь этого избежать. Если очень нужно — приводи к фиксированной точности (например, округляй до N знаков и переводи в int) перед использованием как ключа.

## Range by Map

При итерации `range` по мапе ты работаешь с **копией** значения на каждой итерации — как и в [[Array and Slices#Iteration tricks|слайсах]]. Если значение — структура, изменения внутри `for` не затронут оригинал в мапе (см. следующий пункт про "почему я не могу менять элемент мапы напрямую").

## Go Allows Edit and Delete While Iteration

Можно безопасно удалять и изменять элементы мапы прямо во время итерации по ней. Но с **добавлением** новых ключей всё интереснее:

> Если запись добавляется в мапу во время итерации, она **может** быть посещена во время этой же итерации, а может быть пропущена — и это поведение **не детерминировано** и может отличаться от запуска к запуску.

Почему так происходит — отличное объяснение есть прямо в исходниках Go:

> [!Note]
>  Go maps are hash maps — по сути это массивы под капотом. Ключи превращаются в индексы через хеш-функцию. У каждой мапы есть уникальный salt, который гарантирует, что разные мапы хранят элементы в разном порядке внутри массива.
> 
> Итерация по мапе — это просто проход по массиву. Когда ты пишешь в мапу во время итерации, новый элемент вставляется в массив. _Это может произойти как левее текущей позиции (тогда итерация его не увидит), так и правее (тогда увидит)_.
> 
> Из-за уникального salt иногда вставленный элемент окажется левее, иногда правее — отсюда недетерминированность.

**Вывод**: если тебе нужен предсказуемый результат при добавлении элементов во время обработки — собери ключи для добавления в отдельный слайс и применяй их **после** окончания `range`.

## How to Clean a Map in Go?

Есть три способа, и они принципиально разные по последствиям:

1. **`data = nil`** — мапа становится nil, GC заберёт всю старую память, когда до неё дойдут руки
2. **Итерация + `delete()`** — удаляет элементы по одному, но **бакеты остаются в памяти**, включая overflow-бакеты
3. **`clear(data)`** — по сути делает то же, что и (2) для каждого элемента — вся аллоцированная память остаётся

**Главный вывод: размер массива бакетов мапы НИКОГДА не уменьшается.** Только evacuation при росте может освободить старые массивы.

Это может привести к скрытой утечке памяти. Сценарий: у тебя была мапа с сотнями МБ данных, ты сделал `clear()` и продолжаешь использовать эту же мапу для мелких операций — но вся инфраструктура (бакеты) на сотни МБ так и висит в памяти.

Наглядный пример:

```go
func printAllocs() {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	fmt.Printf("%d MB\n", m.Alloc/1024/1024)
}

func main() {
	printAllocs() // 0 MB
	data := make(map[int][128]byte)
	printAllocs() // 0 MB

	for i := 0; i < 1_000_000; i++ {
		data[i] = [128]byte{}
	}
	printAllocs() // 406 MB

	for i := 0; i < 1_000_000; i++ {
		delete(data, i)
	}
	runtime.GC()
	printAllocs() // 288 MB — !!
	runtime.KeepAlive(data)
}
```

После удаления всех элементов память упала только до **288 МБ** из 406. Почему не до нуля? Потому что освободились только старые массивы бакетов, оставшиеся от **evacuation во время роста** — а финальный (самый большой) массив бакетов остался висеть, просто с пустыми ячейками.

> ⚠️ Если заранее указать хинт размера в `make()`, то evacuation вообще не произойдёт (сразу выделится финальный размер) — и память останется константной ~300 МБ независимо от `delete`.

**Что делать, если нужно переиспользовать мапу:**

1. Самый простой вариант — `data = nil` и создать новую мапу заново
2. Хранить **указатели** как значения: `make(map[int]*[128]byte)` вместо `make(map[int][128]byte)`

Второй вариант резко роняет потребление памяти (с 406 МБ до ~32 МБ в этом примере). Причина — правило Go:

> Если ключ или значение занимает больше **128 байт**, Go не хранит его непосредственно в бакете — вместо этого в бакете хранится только указатель на данные.

Поэтому `[128]byte` (ровно 128) хранится инлайн в бакете, а `[129]byte` (уже больше 128) автоматически переходит на хранение через указатель — и ты увидишь точно такой же эффект экономии памяти, как при ручном использовании указателя.

## Why Can't I Edit a Map Element's Object Values Directly?

Значение в мапе **нельзя изменить частично** — только перезаписать **целиком**. Для примитивов (`int`, `string`) это незаметно, но для [[Structs|структур]] и массивов всплывает неожиданно:

```go
type client struct {
	name    string
	surname string
}

func updateSurname(data map[int]client, id int, surname string) {
	object := data[id]    // копия структуры
	object.surname = surname
	data[id] = object      // перезаписываем целиком

	// data[id].surname = surname  -> compilation error!
}

func updateSurnameByPointer(data map[int]*client, id int, surname string) {
	data[id].surname = surname // ОК — меняем по указателю, без копий
}

func updateSurnamesSlice(data map[int][]string, id int, surname string) {
	data[id][5] = surname // ОК — слайс это reference type, элемент мапы не трогаем
}
```

**Почему так:**

- `data[id]` для типа-структуры — это **значение** (value type), компилятор не может дать тебе адрес на него для прямой записи, потому что технически это "временная копия", извлечённая из бакета
- `data[id]` для указателя (`*client`) или слайса (`[]string`) — сама **мапа** хранит лишь reference (указатель), а данные лежат отдельно. Поэтому через этот reference можно менять данные не трогая саму запись в мапе

**Вывод**: если планируешь часто менять отдельные поля структур-значений в мапе — храни `map[K]*V` вместо `map[K]V`. Но помни: указатели — это доп. аллокации и нагрузка на GC, так что для маленьких read-heavy структур value-тип может быть быстрее в среднем.
