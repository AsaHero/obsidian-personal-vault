## Что такое горутина?

Горутина (goroutine) — это лёгкий поток выполнения на уровне приложения, которым управляет не OS, а рантайм самого Go. По сути это функция, которая выполняется конкурентно с другими функциями в рамках одной программы.

Ключевая фишка в том, что горутина — это НЕ поток ОС (thread). Она в разы дешевле: свой стек начинается всего с ~2KB (и растёт по мере надобности — подробнее о том, как это физически устроено, в [[Allocators#Но у стека в Go есть свои накладные расходы|Allocators]]), тогда как поток ОС обычно сразу отжирает 1-8MB под стек. Именно поэтому можно спокойно запускать тысячи и даже миллионы горутин, а вот тысячи потоков ОС уже положат систему.

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	go func() {
		fmt.Println("я горутина")
	}()

	// без этого main может завершиться раньше,
	// чем горутина успеет напечатать
	time.Sleep(time.Millisecond * 100)
}
```

## Context Switching — и почему это дорого

Context switching — это переключение процессора с выполнения одной задачи на другую. Этим занимается OS scheduler на уровне потоков и процессов.

**Почему это дорого:** чтобы переключиться между процессами, ОС делает не одно переключение, а по сути два:

1. Свитч в ядро (kernel), чтобы выполнить код самого ядра
2. Свитч на другой процесс/поток

При этом происходит сброс/подгрузка кэшей памяти (TLB flush, вытеснение L1/L2 кэша) и сохранение/восстановление большого набора регистров. Всё это — не бесплатно, и если делать это слишком часто, CPU будет тратить время не на полезную работу, а на "переключения ради переключений".

Горутины же переключаются самим рантаймом Go в user space, без похода в ядро — отсюда и вся экономия.

## Thread vs Goroutine

```
THREAD
├── Goroutine #1 (registers + stack)
├── Goroutine #2 (registers + stack)
└── Goroutine #3 (registers + stack)
```

Один поток ОС (Thread) может содержать в себе несколько горутин — каждая со своим набором регистров и своим стеком. Планировщик Go сам переключает горутины на этом потоке — это называется **M:N модель** (M горутин на N потоках), и именно она делает горутины настолько дешёвыми по сравнению с обычными ОС-потоками.

> ⚠️ Важно понимать: в рамках горутины создаётся отдельный стек и свой набор регистров — это именно то, что позволяет ей иметь собственное состояние выполнения независимо от других горутин на том же потоке.

### Ключевая идея модели

1. Не даём программисту в руки поток напрямую
2. Делаем вид, что для программиста существуют только горутины
3. Всю сложность распределения горутин по потокам абстрагируем внутри рантайма

Программист просто пишет `go func() {...}()`, а как это размажется по ядрам процессора — забота рантайма.

## Panic в одной горутине не убивает другую

Так как у каждой горутины свой стек, [[Error Handling#Go не поддерживает исключения (но почти)|recover()]] работает только в рамках стека той горутины, где случился panic. Поймать panic из другой горутины **нельзя** — если он не был обработан внутри своей горутины, упадёт вся программа.

```go
package main

import (
	"fmt"
	"time"
)

func process() {
	defer func() {
		v := recover()
		fmt.Println("recovered:", v)
	}()

	go func() {
		panic("error") // этот panic НЕ поймается снаружи!
	}()

	time.Sleep(time.Second)
}

func main() {
	process()
}
```

> ⚠️ Подводный камень: `defer/recover` в `process()` тут не сработает так, как многие ожидают — recover ловит panic только в своей горутине. Если запущенная горутина запаникует, а внутри неё нет своего `recover()`, программа упадёт целиком, несмотря на то что снаружи есть defer с recover.

## Почему log.Println(), а не fmt.Println()?

Когда несколько горутин пишут в stdout одновременно через `fmt.Println()`, вывод может перемешаться — строки от разных горутин "въедут" друг в друга.

Операции в пакете `log` синхронизированы внутри (используют mutex), поэтому сообщения от разных горутин печатаются целиком, не перемешиваясь между собой.

```go
package main

import (
	"log"
	"sync"
)

func main() {
	var wg sync.WaitGroup

	for i := 0; i < 5; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			log.Println("worker", id, "done") // безопасно для конкурентного вывода
		}(i)
	}

	wg.Wait()
}
```

## Кто запускает горутины?

Планировщик Go (Go scheduler). Он решает, какая горутина, когда и на каком потоке будет выполняться.

### Состояния горутины

1. **Running** — выполняется прямо сейчас на каком-то потоке
2. **Runnable** — готова к выполнению, ждёт своей очереди
3. **Waiting** — остановлена, ждёт чего-то (I/O, канал, мьютекс, таймер)

## Как бы мы сами реализовали конкурентность в Go?

Дальше — пошаговая эволюция того, как Go пришёл к текущей модели планировщика. Это полезно понимать, потому что каждая следующая модель — это ответ на конкретную проблему предыдущей.

### N:1 модель

Выполняем N горутин на одном потоке.

```
Global queue (GRQ)
┌─────────────────────┐
│  [G]   [G]           │
│                      │
└─────────────────────┘
          ↑
      [G] │ Thread
```

Горутина забирается единственным потоком (Thread) из глобальной очереди (GRQ) и на нём же выполняется.

Когда поток хочет переключиться на другую горутину из очереди, происходит следующее:

1. Все регистры текущей горутины кладутся в её стек
2. Горутина отправляется в конец очереди
3. Из очереди достаётся следующая горутина
4. Stack Pointer и Base Pointer следующей горутины восстанавливаются
5. Регистры достаются из её стека, и выполнение продолжается

**Минус N:1:** только один поток — значит только одно ядро процессора реально работает, даже если у нас 16-ядерный сервер. Остальные ядра простаивают.

## Как и когда вытеснять горутины?

Есть два вида многозадачности:

- **Кооперативная** — сама задача решает, когда отдать управление процессору, вызывая специальную команду или уходя в ожидание I/O
- **Вытесняющая** — ОС по аппаратному таймеру принудительно забирает управление у задачи по истечении кванта времени

Go изначально работал по кооперативной схеме: **компилятор сам добавляет в исходный код места для переключения контекста**, например в момент проверки, хватает ли места в стеке горутины.

> ℹ️ Это значит, что горутина, которая никогда не доходит до такой "точки проверки" (например, крутится в чистом вычислительном цикле без вызовов функций), долгое время не отдаёт управление — привет, кооперативная многозадачность и её минусы. Об этом ниже, в разделе про asynchronous preemption.

## Как быть с многоядерными процессорами?

### N:M модель

Выполняем N горутин на M потоках.

```
              Global queue (GRQ)
              ┌─────────────────────┐
              │  [G]   [G]          │
              └─────────────────────┘
                        ↑
     ┌──────────┬──────────┬──────────┬──────────┐
   [G] Thread  [G] Thread  [G] Thread  [G] Thread
```

Несколько потоков разбирают горутины из общей глобальной очереди — теперь реально используются все ядра.

**Но тут вылезает боттлнек:** когда много потоков лезут в один общий ресурс, нужна синхронизация.

### Not scalable: Mutex на глобальной очереди

```
              Global queue (GRQ)
              ┌─────────────────────┐
              │  [G]   [G]          │
              └─────────────────────┘
                      [Mutex]
                        ↑
     ┌──────────┬──────────┬──────────┬──────────┐
   [G] Thread  [G] Thread  [G] Thread  [G] Thread
```

Все потоки обращаются к единой GRQ через **Mutex**. Из-за этого возникает конкуренция (contention) за блокировку между потоками — и чем больше ядер/потоков, тем хуже она масштабируется.

> ⚠️ Та же проблема с contention случится и с памятью/кэшем: даже если использовать lock-free queue вместо mutex, много потоков всё равно будут мешать друг другу через синхронизацию кэш-линий (cache line bouncing между ядрами) — и это тоже боттлнек, который нужно решать.

**Решение:** поделить одну большую очередь на несколько маленьких.

## Локальные очереди (LRQ)

```
Local queue (LRQ=256)   Local queue (LRQ=256)   Local queue (LRQ=256)
┌──────────┐            ┌──────────┐            ┌──────────┐
│ [G] [G]  │            │ [G]      │            │ [G] [G]  │
│ [G]      │            │          │            │          │
│  [P]     │            │  [P]     │            │  [P]     │
└──────────┘            └──────────┘            └──────────┘
    ↑                       ↑                       ↑
[G] M (thread)          [G] M (thread)          [G] M (thread)
```

У каждого потока `M` появляется свой процессор-планировщик `P` и своя локальная очередь горутин `LRQ` (вместимостью 256 штук). Больше не нужна общая блокировка — каждый поток берёт горутины из **своей** локальной очереди. Contention исчезает, модель становится масштабируемой.

Из этого и родилась знаменитая **GMP модель**.

## GMP модель

|Компонент|Что это|Расшифровка|
|---|---|---|
|**G**|Goroutine|что мы исполняем|
|**M**|Machine|где мы исполняем (обёртка над потоком ОС)|
|**P**|Processor|права и ресурсы для исполнения (локальная очередь, кэши)|

**Зачем нужен именно P**, а не просто "поток берёт горутину из очереди"? P — это тот самый контекст, который даёт горутине доступ к локальной очереди и локальным ресурсам планировщика (например, [[Allocators#Связь с планировщиком GMP|кэш аллокатора памяти]] — `mcache`). Без P у M не было бы своей изолированной очереди, и мы бы вернулись к общему mutex-у.

> ⚠️ По умолчанию количество **P** берётся из переменной окружения **GOMAXPROCS** и равно количеству логических ядер компьютера. Это важно держать в голове: если запускать контейнер с ограничением по CPU (например, в Kubernetes), а `GOMAXPROCS` не выставлен вручную, Go может "видеть" больше ядер, чем реально доступно контейнеру, и планировать горутины неэффективно.

```go
package main

import (
	"fmt"
	"runtime"
)

func main() {
	fmt.Println("GOMAXPROCS:", runtime.GOMAXPROCS(0)) // 0 — просто прочитать текущее значение
	runtime.GOMAXPROCS(4)                              // можно выставить вручную
}
```

## В какую очередь добавлять новую горутину?

В тот же **LocalQueue**, из которого её выполняет текущий Thread. Это логично — так горутина с большей вероятностью попадёт на "тёплый" P без лишних перемещений.

### А что делать, если в очереди закончились горутины?

**Work stealing** — свободный P начинает "воровать" горутины из чужих локальных очередей.

- **У какой именно очереди красть?** — выбираем рандомно
- **Что делать, если и там пусто?** — пробуем украсть ещё, всего **4 раза**
- **Сколько красть за раз?** — забираем **половину** горутин из чужой локальной очереди (а не одну — чтобы не бегать красть слишком часто)

Плюс: work-stealing ворует именно из **хвоста** чужой FIFO-очереди — и никогда не трогает специальный слот `runnext` (про него ниже). Это важно для сохранения кэш-локальности той горутины, которую только что разбудили на этом же P.

## Syscalls: почему рантайм Go их не любит

Когда горутина делает **блокирующий syscall**, поток `M`, на котором она выполняется, тоже блокируется. Пока `M` сидит в syscall, он не может выполнять другие горутины из своей локальной очереди — и они просто простаивают, хотя формально готовы к работе.

### Handoff

Чтобы это предотвратить, компилятор добавляет код в местах вызова syscall, который делает следующее:

1. Создаёт новый поток `M-new`
2. Разрывает связь между `M-old` (который уходит в syscall) и `P`
3. `M-old` уходит в syscall и кладётся в Thread Pool (не уничтожается — чтобы переиспользовать после выхода из syscall)
4. `M-new` подхватывает освободившийся `P` и продолжает разбирать локальную очередь

В следующий раз, когда нужен handoff, можно просто открепить поток и сразу пойти искать свободный поток в Thread Pool, а не создавать новый с нуля.

> ⚠️ Момент с CGO: для вызовов через CGO создаётся отдельная горутина, и handoff при syscall **не происходит** — потому что компилятор Go не видит С-шный код и не может вставить туда нужные проверки/инструкции для handoff.

### Куда девать горутину после завершения syscall?

Когда syscall завершается, горутине (`G`) нужно продолжить выполнение — но `P`, с которым она изначально работала, могли уже отдать другому `M` (через handoff). Рантайм разруливает это по трём сценариям:

1. **Старый P свободен** — `M` забирает его обратно, горутина продолжает как ни в чём не бывало
2. **Старый P занят, но есть другой свободный P** — рантайм берёт любой свободный `P` из пула, горутина встаёт в его локальную очередь
3. **Свободных P нет вообще** — горутина кладётся в **глобальную очередь** (GRQ), а поток `M` уходит "спать" в пул простаивающих потоков, пока не появится свободный `P`

Так к нам снова возвращается Global Queue с синхронизацией через Mutex — но, как увидим дальше, для этого сценария (когда P реально не хватает) это приемлемо, потому что случается редко по сравнению с основным потоком работы.

## Проблема с сетевыми syscall'ами

Handoff отлично решает проблему для CPU-bound блокирующих вызовов. Но сетевые операции (`read`/`write` на сокете) — это тоже блокирующий syscall, только их **очень много** и они могут **очень долго висеть** (например, ждём данных от клиента, который вообще молчит).

Если применять handoff к каждому такому вызову:

- 10 000 соединений → 10 000 блокирующих сетевых syscall'ов
- на каждый нужен либо существующий свободный `M`, либо создаётся новый поток ОС
- соединения держатся подолгу → потоки не освобождаются быстро → они копятся

**Итог:** мы возвращаемся туда, откуда пытались уйти — тысячи живых потоков ОС, тяжёлое переключение контекста, память, съеденная стеками потоков. Handoff решил проблему для CPU-bound блокировок, но для I/O-bound сетевой нагрузки он контрпродуктивен.

### Netpoller

Ключевая мысль: **ожидание сетевых данных — это не работа**, которую обязательно должен делать поток ОС. Значит, поток вообще не обязан блокироваться ради этого ожидания.

Как это устроено:

- сокеты переводятся в **неблокирующий режим**
- ожидание готовности (данные пришли / можно писать) делегируется ОС-специфичному механизму опроса: **epoll** (Linux), **kqueue** (BSD/macOS), **IOCP** (Windows)
- этот механизм встроен в рантайм Go как **netpoller**

Что происходит с горутиной пошагово:

1. `G` пытается сделать `read`/`write` на сокете
2. Данных нет → `G` **паркуется** (уходит в состояние ожидания), но **не блокирует** `M`
3. `M` освобождается и сразу берёт другую `G` из очереди — поток не простаивает впустую
4. Netpoller следит за сокетом через epoll/kqueue/IOCP
5. Когда данные готовы — `G` помечается как runnable и возвращается в очередь (локальную или глобальную), чтобы её подхватил любой свободный `P`/`M`

**Плюс netpoller:** можно держать десятки тысяч сетевых соединений всего на нескольких потоках ОС — именно поэтому Go так хорош для сетевых сервисов.

## Как проверяется глобальная очередь?

В рантайме Go есть комментарий, который прямо описывает порядок проверки:

```go
runtime.schedule() {
  // only 1/61 of the time, check the global runnable queue for a G.
  // if not found, check the local queue.
  // if not found,
  // try to steal from other Ps.
  // if not, check the global runnable queue.
  // if not found, poll network.
}
```

То есть глобальная очередь проверяется не при каждом планировании, а только раз в 61 итерацию — это защита от голодания горутин, которые лежат именно в глобальной очереди (иначе локальные очереди всегда бы имели приоритет, и глобальная очередь могла бы никогда не разгрестись).

## Кэши и порядок пробуждения горутин

**Проблема:** когда горутина `A` будит горутину `B` (через `unlock()` мьютекса или отправку в канал), рантайму нужно решить, куда поставить `B` в очереди на выполнение.

### Два подхода

**FIFO — честность (fairness)**

```
<- [G G G G] <-
```

`B` встаёт в конец очереди, все ждут по порядку. Никто не голодает.

**LIFO — прогретый кеш (cache locality)**

```
[G G G G] <->
```

`B` встаёт первой и выполняется сразу после `A`.

### Почему это вообще важно — при чём тут кеш

Дело **не** в том, что у самой `B` "остался" тёплый кеш с прошлого раза — за время сна он давно вымыт.

Дело в том, что **`A`** прямо перед пробуждением `B` трогала общие данные: сам объект канала, структуру мьютекса, защищённую им переменную. Эти данные **сейчас** лежат в L1/L2 кеше того ядра, где работала `A`. Если `B` выполнить сразу — она читает уже горячие данные (cache hit). Если между `A` и `B` вклинятся другие, не связанные горутины (честный FIFO) — эти данные вытеснятся, и `B` получит cache miss.

**Минус чистого LIFO:** если постоянно ставить новых разбуженных горутин в начало очереди, старые горутины в хвосте могут голодать бесконечно — fairness полностью теряется.

### Решение Go: гибрид со слотом runnext

```
<- [ G G G G ] <- [ G ] <->
         FIFO         runnext (1 слот)
```

- У каждого `P` есть обычная FIFO-очередь (LRQ) **и один дополнительный слот** `runnext`
- Планировщик перед LRQ всегда сначала смотрит в `runnext`
- Слот **всего один**: если туда кладут новую горутину, а там уже что-то лежит — старое **сдвигается в начало FIFO-очереди**, а не выбрасывается

Итог: голодание ограничено максимум одним циклом — несправедливость не может накапливаться бесконечно.

**Кто и когда кладёт горутину в runnext:** только явное пробуждение (`ready()`), когда живая горутина будит другую — [[Synchronization Primitives#Mutex|unlock() мьютекса]], отправка/приём в [[Channels|канал]], срабатывание таймера.

> ⚠️ Пока горутина заблокирована, она **не находится ни в одной очереди вообще** — она в состоянии `_Gwaiting` и лежит в wait-list объекта синхронизации (мьютекса/канала). В очередь (обычно в `runnext`) она попадает только в момент пробуждения.

> ⚠️ Сетевые/syscall-пробуждения идут по другому пути. Их обнаруживает **netpoller**, а не живая горутина, поэтому у пробуждённой `G` нет "своего" `P` с прогретым кешем, который стоило бы беречь. Такие `G` обычно уходят в глобальную очередь либо сразу подхватываются простаивающим `P`, который сам спросил netpoller о работе.

### Итоговое сравнение

|Механизм|Плюс|Минус|
|---|---|---|
|Чистый FIFO|справедливость|холодный кеш|
|Чистый LIFO|горячий кеш|возможное голодание|
|**runnext + FIFO** (то, что в Go)|горячий кеш там, где реально помогает (живое пробуждение), голодание ограничено одним слотом|небольшая доп. сложность|

**Ещё один нюанс про work-stealing и кеш:** если `B` оставить на своём ядре — она читает данные из локального L1/L2 без проблем. Если её украдёт другой `P` (work-stealing, другое физическое ядро) — данные придётся тащить через межъядерный протокол когерентности кешей (MESI и подобные), а это дороже локального hit-а, хотя всё ещё дешевле похода в оперативную память.

## Краевой случай: пинг-понг через каналы

У модели с `runnext` есть неприятный краевой случай — когда две горутины постоянно "перебрасывают" друг друга через синхронный канал (одна пишет, другая читает, и так по кругу). Каждая из них постоянно кладёт другую в `runnext`, и остальная LRQ на этом `P` может голодать сколь угодно долго.

**Решение:** Go считает время непрерывной работы горутины, и в случае превышения временного лимита — принудительно вытесняет её из LIFO-приоритета, давая шанс остальным горутинам в LRQ.

## Бесконечные циклы и CPU-bound задачи

Что если горутина вообще никогда не доходит до "точки проверки" (кооперативное вытеснение), а просто крутится в бесконечном цикле? До Go 1.14 это была реальная проблема — такая горутина могла держать `P` вечно, не давая работать остальным.

### Asynchronous preemption (с Go 1.14)

С версии 1.14 в Go появилась не только кооперативная, но и **асинхронно вытесняющая** многозадачность:

- как только `sysmon` (системный монитор рантайма) обнаруживает горутину, которая работает дольше **10мс**, потоку, на котором она выполняется, посылается сигнал `SIGURG` для её вытеснения

**Почему это называется именно _асинхронной_ преемпцией**, а не мгновенным вытеснением: горутина не снимается с выполнения мгновенно в момент сигнала. С точки зрения GC в коде существуют **unsafe points** — места, где, например, указатели временно не согласованы между собой. Если горутина в этот момент находится в такой зоне, вытеснение произойдёт не сразу, а только когда она из неё выйдет.

## Закрепление горутины за конкретным потоком

Иногда нужно жёстко привязать горутину к конкретному потоку ОС (например, для работы с некоторыми C-библиотеками, которые требуют вызовов строго с одного и того же потока):

```go
runtime.LockOSThread()
// ... код, который обязательно должен выполняться на одном потоке
runtime.UnlockOSThread()
```

## Когда завершается программа на Go?

Когда завершается **main-горутина**. И, казалось бы, логично, что вместе с ней должны умереть и все остальные горутины — так и есть, но есть один хитрый нюанс с `runtime.Goexit()`.

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

func main() {
	go func() {
		for {
			time.Sleep(time.Second)
			fmt.Println("tick")
		}
	}()

	time.Sleep(3 * time.Second)
	runtime.Goexit()
}
```

Казалось бы, мы "убили" main-горутину через `Goexit()` — значит, программа должна завершиться и фоновая горутина с `tick` тоже умрёт. **На деле она будет бесконечно печатать `tick`, и программа не завершится.**

> ⚠️ Это официально задокументированная особенность `Goexit()`, а не баг:
> 
> - вызов `Goexit()` внутри main-горутины завершает **именно эту горутину**, не давая `func main` вернуться из функции обычным образом
> - поскольку `func main` формально не вернулась, программа продолжает выполнение остальных горутин
> - программа завершится (крашнется), только когда **все остальные** горутины тоже завершатся сами; если `Goexit()` вызван из потока, не созданного рантаймом Go — тоже будет краш

Практический вывод: `runtime.Goexit()` — это не способ "убить программу целиком", это способ гарантированно прогнать все `defer` текущей горутины и красиво её завершить, при этом не трогая остальные горутины.
