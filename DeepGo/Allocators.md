# Алгоритмы распределения памяти

## Что такое аллокатор?

Аллокатор — это компонент, который выдаёт программе память по запросу. Звучит просто, но у "хорошего" аллокатора на самом деле четыре конкурирующих критерия качества:

- **Скорость работы** — cache-locality (чтобы выделенная память лежала близко в кэше CPU), выдача недавно освобождённых блоков (пока они ещё "тёплые" в кэше, не вымылись оттуда)
- **Масштабируемость** — расширение на несколько CPU, работа как с маленькими, так и с большими участками памяти
- **Потребление памяти** — эффективность структур для хранения метаданных, низкая фрагментация
- **Безопасность** — защита от неправильного использования, защита от атак (например, переполнений буфера)

⚠️ **Важно понимать:** эти критерии друг другу противоречат. Хочешь скорость — жертвуешь чем-то в потреблении памяти. Хочешь безопасность — добавляешь проверки, которые режут скорость. Поэтому либо разработчик аллокатора ищет компромисс, либо даёт пользователю крутилки-настройки под конкретный сценарий.

### Интерфейс аллокатора

Практически любой аллокатор (независимо от реализации) обычно имеет такой контракт:

1. `create` — создаёт аллокатор и отдаёт ему в распоряжение объём памяти
2. `allocate` — выделяет блок нужного размера из своей области
3. `deallocate` — освобождает конкретный блок
4. `free` — освобождает **все** выделенные блоки разом (сама память аллокатора при этом не возвращается ОС)

## Linear Allocator

Самый простой вид аллокатора. Идея: держим указатель на начало блока памяти и второй указатель (или число), который сдвигаем вперёд при каждом выделении.

❌ **Главное ограничение: не поддерживает выборочное освобождение памяти.** Освободить можно только всё сразу через `Free()`.

```go
package main

import (
	"errors"
	"fmt"
	"unsafe"
)

type LinearAllocator struct {
	data []byte
}

func NewLinearAllocator(capacity int) (LinearAllocator, error) {
	if capacity <= 0 {
		return LinearAllocator{}, errors.New("incorrect capacity")
	}

	return LinearAllocator{
		data: make([]byte, 0, capacity), // len=0, cap=capacity — сразу резервируем весь блок
	}, nil
}

func (a *LinearAllocator) Allocate(size int) (unsafe.Pointer, error) {
	previousLength := len(a.data)
	newLength := previousLength + size

	if newLength > cap(a.data) {
		// место кончилось — можно было бы расширить capacity, но это уже другая история
		return nil, errors.New("not enough memory")
	}

	a.data = a.data[:newLength] // просто "отрезаем" ещё size байт от общего куска
	pointer := unsafe.Pointer(&a.data[previousLength])
	return pointer, nil
}

// Deallocate НЕ поддерживается этим типом аллокатора —
// у нас просто нет способа "вернуть" средний блок, не сломав всё после него
// func (a *LinearAllocator) Deallocate(pointer unsafe.Pointer) error {}

func (a *LinearAllocator) Free() {
	a.data = a.data[:0] // сбрасываем len, но capacity остаётся — память переиспользуется
}

func store[T any](pointer unsafe.Pointer, value T) {
	*(*T)(pointer) = value
}

func load[T any](pointer unsafe.Pointer) T {
	return *(*T)(pointer)
}

func main() {
	const MB = 1 << 20
	allocator, err := NewLinearAllocator(MB)
	if err != nil {
		// handling...
	}

	defer allocator.Free()

	pointer1, _ := allocator.Allocate(2)
	pointer2, _ := allocator.Allocate(4)

	store[int16](pointer1, 100)
	store[int32](pointer2, 200)

	value1 := load[int16](pointer1)
	value2 := load[int32](pointer2)
	fmt.Println("value1:", value1)
	fmt.Println("value2:", value2)

	fmt.Println("address1:", pointer1)
	fmt.Println("address2:", pointer2)
}
```

**Когда полезен:** когда ты знаешь, что весь набор объектов живёт и умирает вместе (например, обработка одного запроса/кадра/батча), и не нужно освобождать что-то по отдельности.

## Block Allocator

Идея — разделить большой участок памяти на мелкие блоки **одинакового размера**. Свободные блоки хранятся в связном списке (free list). Когда блок занят — он уходит из этого списка, когда освобождается — возвращается обратно.

### Pool Allocator

Конкретная реализация block allocator'а — пул объектов фиксированного размера.

```go
package main

import (
	"errors"
	"fmt"
	"unsafe"
)

type PoolAllocator struct {
	objectPool  []byte
	freeObjects map[unsafe.Pointer]struct{} // "множество" свободных указателей
	objectSize  int
}

func NewPoolAllocator(capacity int, objectSize int) (PoolAllocator, error) {
	if capacity <= 0 || objectSize <= 0 || capacity%objectSize != 0 {
		return PoolAllocator{}, errors.New("incorrect argumnets")
	}

	allocator := PoolAllocator{
		objectPool:  make([]byte, capacity),
		freeObjects: make(map[unsafe.Pointer]struct{}, capacity/objectSize),
		objectSize:  objectSize,
	}

	allocator.resetMemoryState()
	return allocator, nil
}

func (a *PoolAllocator) Allocate() (unsafe.Pointer, error) {
	if len(a.freeObjects) == 0 {
		return nil, errors.New("not enough memory")
	}

	var pointer unsafe.Pointer
	for freePointer := range a.freeObjects {
		pointer = freePointer // берём любой свободный — порядок тут не важен
		break
	}

	delete(a.freeObjects, pointer)
	return pointer, nil
}

func (a *PoolAllocator) Deallocate(pointer unsafe.Pointer) error {
	if pointer == nil {
		return errors.New("incorrect pointer")
	}

	// ⚠️ потенциально некорректный указатель — тут нет проверки,
	// что pointer вообще принадлежит этому пулу. Передашь чужой — сломаешь состояние
	a.freeObjects[pointer] = struct{}{}
	return nil
}

func (a *PoolAllocator) Free() {
	a.resetMemoryState()
}

func (a *PoolAllocator) resetMemoryState() {
	for offset := 0; offset < len(a.objectPool); offset += a.objectSize {
		pointer := unsafe.Pointer(&a.objectPool[offset])
		a.freeObjects[pointer] = struct{}{}
	}
}

func store[T any](pointer unsafe.Pointer, value T) {
	*(*T)(pointer) = value
}

func load[T any](pointer unsafe.Pointer) T {
	return *(*T)(pointer)
}

func main() {
	const KB = 1 << 10
	allocator, err := NewPoolAllocator(KB, 4)
	if err != nil {
		// handling...
	}

	defer allocator.Free()

	pointer1, _ := allocator.Allocate()
	pointer2, _ := allocator.Allocate()

	store[int32](pointer1, 100)
	store[int32](pointer2, 200)

	value1 := load[int32](pointer1)
	value2 := load[int32](pointer2)
	fmt.Println("value1:", value1)
	fmt.Println("value2:", value2)

	fmt.Println("address1:", pointer1)
	fmt.Println("address2:", pointer2)

	allocator.Deallocate(pointer1)
	allocator.Deallocate(pointer2)
}
```

**Плюс:** в отличие от linear allocator'а — теперь можно освобождать блоки по отдельности. **Минус:** все блоки строго одного размера, для объектов разных размеров нужно несколько пулов или другой подход.

## Stack Allocator

Умная эволюция linear allocator'а — позволяет управлять памятью как стеком (LIFO). При каждом `Allocate` рядом с данными пишем небольшой **header** — сколько байт было выделено. При `Deallocate` смотрим на header и понимаем, сколько байт "откатить" назад.

```go
package main

import (
	"errors"
	"fmt"
	"math"
	"unsafe"
)

const headerSize = 2 // 2 байта под int16 — размер выделенного блока

type StackAllocator struct {
	data []byte
}

func NewStackAllocator(capacity int) (StackAllocator, error) {
	if capacity <= 0 {
		return StackAllocator{}, errors.New("incorrect capacity")
	}

	return StackAllocator{
		data: make([]byte, 0, capacity),
	}, nil
}

func (a *StackAllocator) Allocate(size int) (unsafe.Pointer, error) {
	if size > math.MaxInt16 {
		// header у нас всего 2 байта (int16) — больше 32767 байт за раз не выделить
		// можно увеличить размер header, если нужно
		return nil, errors.New("incorrect size")
	}

	previousLength := len(a.data)
	newLength := previousLength + headerSize + size

	if newLength > cap(a.data) {
		return nil, errors.New("not enough memory")
	}

	a.data = a.data[:newLength]
	header := unsafe.Pointer(&a.data[previousLength])
	pointer := unsafe.Pointer(&a.data[previousLength+headerSize]) // данные сразу после header'а

	*(*int16)(header) = int16(size)
	return pointer, nil
}

func (a *StackAllocator) Deallocate(pointer unsafe.Pointer) error {
	if pointer == nil {
		return errors.New("incorrect pointer")
	}

	header := unsafe.Add(pointer, -headerSize) // "отступаем назад" к header'у
	size := *(*int16)(header)

	previousLength := len(a.data)
	newLength := previousLength - headerSize - int(size)

	a.data = a.data[:newLength]
	return nil
}

func (a *StackAllocator) Free() {
	a.data = a.data[:0]
}

func store[T any](pointer unsafe.Pointer, value T) {
	*(*T)(pointer) = value
}

func load[T any](pointer unsafe.Pointer) T {
	return *(*T)(pointer)
}

func main() {
	const KB = 1 << 10
	allocator, err := NewStackAllocator(KB)
	if err != nil {
		// handling...
	}

	defer allocator.Free()

	pointer1, _ := allocator.Allocate(2)
	defer allocator.Deallocate(pointer1)
	pointer2, _ := allocator.Allocate(4)
	defer allocator.Deallocate(pointer2)

	store[int16](pointer1, 100)
	store[int32](pointer2, 200)

	value1 := load[int16](pointer1)
	value2 := load[int32](pointer2)
	fmt.Println("value1:", value1)
	fmt.Println("value2:", value2)

	fmt.Println("address1:", pointer1)
	fmt.Println("address2:", pointer2)
}
```

⚠️ **Подводный камень:** это именно **стек** — освобождать блоки нужно строго в обратном порядке (LIFO), как и defer в Go, собственно. Если освободить блок "из середины" — сломаешь всё, что было выделено после него.

## Фрагментация памяти: два типа, и почему наши три аллокатора её избежали

Раз уж заговорили про низкий уровень — стоит закрепить, что такое "фрагментация" вообще, потому что дальше это слово будет всплывать постоянно.

Фрагментация бывает двух принципиально разных типов:

- **Internal fragmentation (внутренняя)** — память потрачена _внутри_ уже выделенного блока, но не используется. Попросили 9 байт, а выдали блок на 16 — 7 байт просто пропадают, хотя формально это "твоя" память.
- **External fragmentation (внешняя)** — суммарно свободной памяти хватает, но она раскидана мелкими "дырками" между занятыми блоками, и большой непрерывный запрос удовлетворить нечем, хотя по сумме места достаточно.

Внешняя фрагментация — это именно то, что обычно имеют в виду под "фрагментацией кучи", и это настоящая головная боль. Внутренняя, наоборот, довольно безобидна — если она **предсказуема и ограничена сверху** (см. дальше про size classes), с ней спокойно можно жить.

Теперь пересмотрим наши три "наивных" аллокатора через эту призму — и станет видно, что все три избегают внешней фрагментации **не случайно, а по конструкции**, ценой гибкости:

- **Linear Allocator** — вообще не поддерживает поштучный `Deallocate`, поэтому дыркам физически неоткуда взяться: освобождение всегда происходит всё разом. Внешней фрагментации тут нет **по построению**. Внутренняя теоретически возможна из-за выравнивания (alignment), если округлять каждый блок до границы в несколько байт — но это предсказуемо и мало.
- **Pool Allocator** — все блоки строго одного размера, поэтому любой освобождённый блок **гарантированно подходит** под любой будущий запрос. Дыра никогда не остаётся дырой — она сразу пригодна для переиспользования. Зато внутренняя фрагментация тут может быть заметной: объект 20 байт, блок 32 — эти 12 байт теряются на каждом объекте всегда. Это прямая иллюстрация той самой "waste", которую разберём чуть ниже на size classes.
- **Stack Allocator** — LIFO-дисциплина: освободить можно только последний выделенный блок. Дыру в середине получить физически невозможно — иначе LIFO бы уже нарушился. Цена — негибкость: объекты обязаны жить и умирать строго в обратном порядке своего создания.

Итого: все три "игрушечных" аллокатора решают проблему внешней фрагментации одним и тем же трюком — **сознательно жертвуют гибкостью** (нельзя освобождать по одному / все блоки одного размера / освобождать можно только по LIFO) и получают взамен структурную невозможность появления дыр.

А что если гибкость нужна — как в `malloc`, где можно попросить блок любого размера и освободить его в любой момент в любом порядке? Вот тут внешняя фрагментация становится настоящей, нерешённой проблемой.

## Malloc (General Purpose Allocator)

Классический malloc — все потоки идут за памятью в одно общее место.

```
             ┌────────────┐
             │   Memory   │
             └─────┬──────┘
                    │
             ┌──────┴───────┐
             │  Contention  │
             └──┬────────┬──┘
                │         │
          ┌─────┴──┐ ┌────┴───┐
          │ Thread │ │ Thread │
          └────────┘ └────────┘
```

Несколько потоков (Thread) обращаются к общей памяти (Memory) — из-за этого возникает **contention** (конкуренция за доступ). Отсюда два системных минуса classic malloc:

- нужна синхронизация потоков (locks/atomics на каждое выделение — дорого)
- фрагментация кучи — и вот здесь это уже настоящая, а не игрушечная проблема

Почему именно у malloc фрагментация реальна, а у наших трёх аллокаторов — нет? Потому что malloc обязан поддерживать **произвольные размеры** запросов **и** освобождение **в произвольном порядке**. Представь: выделили подряд блоки A (16 байт), B (200 байт), C (16 байт), потом освободили B — образовалась дыра в 200 байт между A и C. Следующий запрос на 16 байт туда влезет и оставит ещё дыру в 184 байта. Через тысячи таких циклов куча превращается в "швейцарский сыр" — суммарно памяти много, а выделить один сплошной кусок нужного размера не из чего.

### Классические способы борьбы с external fragmentation

Исторически сложилось четыре основных подхода (они не взаимоисключающие — реальные аллокаторы часто комбинируют несколько сразу):

1. **Segregated free lists (сегрегированные списки, они же size classes)** — по сути, обобщение идеи Pool Allocator'а: вместо одного пула с одним размером блока держим много пулов, каждый под свой диапазон размеров. Внешняя фрагментация _внутри_ одного класса невозможна ровно по той же причине, что и в Pool Allocator — все блоки взаимозаменяемы. Плата — внутренняя фрагментация (округление вверх до границы класса), но она заранее известна и ограничена. Именно этот путь выбрали tcmalloc и Go — разберём его дальше в деталях.
2. **Coalescing (сращивание соседних свободных блоков)** — классическая техника в аллокаторах вроде glibc malloc (ptmalloc/dlmalloc). Каждый блок несёт небольшой заголовок ("boundary tag") с размером и флагом "свободен/занят". При освобождении блока аллокатор смотрит на соседей по памяти — если сосед тоже свободен, они сливаются в один блок побольше. Мелкие дыры не накапливаются, а постоянно "затягиваются" обратно в крупные куски.
3. **Buddy allocator (система "близнецов")** — используется, например, в аллокаторе страниц ядра Linux. Память делится на блоки размером степени двойки. Нужен блок — берём ближайший подходящий, если он слишком большой — рекурсивно делим пополам ("близнецы"), пока не получим нужный размер. При освобождении аллокатор проверяет: а свободен ли "близнец" (вторая половина того же деления)? Если да — сливаем их обратно в блок вдвое больше, и так рекурсивно вверх. Красиво тем, что слияние — простая арифметика над адресами, а не сканирование соседей вручную, но своя внутренняя фрагментация тоже есть: округление до степени двойки в худшем случае теряет почти половину.
4. **Compaction (перемещение живых объектов)** — вместо того чтобы жить с дырами и искать в них место, можно периодически **сдвинуть все живые объекты вплотную друг к другу**, полностью убрав дыры, и обновить все указатели, которые на них ссылались. После такой компакции выделение памяти становится тривиальным — тем же bump pointer'ом, что и у нашего Linear Allocator'а. Минус — дорого, и нужно точно знать, где лежит каждый указатель на объект, чтобы его переписать. Вернёмся к этому отдельно, когда посмотрим, почему Go **не** делает так со своей кучей.

## Tcmalloc (Thread-Cached Malloc)

Решение проблемы contention — дать каждому потоку **свой личный кэш**.

```
             ┌────────────┐
             │   Memory   │
             └──────┬─────┘
                     │
             ┌───────┴──────┐
             │  Contention  │
             └──┬────────┬──┘
                │         │
          ┌─────┴──┐ ┌────┴───┐
          │ cache  │ │ cache  │
          └────┬───┘ └───┬────┘
               │          │
          ┌────┴──┐  ┌────┴───┐
          │ Thread │  │ Thread │
          └────────┘  └────────┘
```

Большинство аллокаций обслуживается локальным кэшем потока — **без блокировок**. Contention возникает только тогда, когда кэш потока исчерпан и нужно сходить в общую Memory за пополнением — вот в этот момент и требуется синхронизация.

### Size classes

Кэш каждого потока хранит объекты не произвольного размера, а по **классам размеров**:

```
1 класс → [ 8 ]  → [ 8 ]  → [ 8 ]  → ...
2 класс → [ 16 ] → [ 16 ] → ...
3 класс → [ 32 ] → [ 32 ] → ...
```

Каждый класс отвечает за блоки строго фиксированного размера (8, 16, 32 байта...), объединённые в free list. Когда нужно выделить память — аллокатор просто берёт готовый блок нужного класса, а не ищет свободное место произвольного размера в куче. Это и есть **иерархическая модель хранения данных**.

📌 Эффективность приложения **неявно** зависит от эффективности аллокатора — но об этом дальше редко думают, пока не начинают профилировать.

## Как это устроено в Go

Go запрашивает память у ОС большими кусками — **аренами** (arena), обычно по 64MB (размер может отличаться). Арена делится на **страницы** (page) фиксированного размера — 8KB — которыми уже управляет сам рантайм.

```
Arena (64MB)
┌────────────────────────────────┐
│ Page   Page   Page   Page      │
│ 8KB    8KB    8KB    8KB       │
│                                │
│ Page   Page   Page   Page      │
│ 8KB    8KB    8KB    8KB       │
└────────────────────────────────┘
```

Одна или несколько соседних страниц объединяются в **span** — непрерывный блок памяти под объекты нужного размера (8KB, 16KB, 32KB, 64KB...). Span — это единица, которой оперирует аллокатор Go: чем крупнее нужен объект, тем больше страниц объединяется в span.

```
Arena (64MB)                    Spans
┌───┬───┬───┬───┐
│ P │ P │ P │ P │               ┌────────┐
│8KB│8KB│8KB│8KB│               │  8KB   │
├───┼───┼───┼───┤          ┌────┴────────┴───┐
│ P │ P │ P │ P │          │      16KB       │
│8KB│8KB│8KB│8KB│      ┌───┴─────────────────┴──┐
├───┼───┼───┼───┤      │         32KB           │
│ P │ P │ P │ P │  ┌───┴────────────────────────┴──┐
│8KB│8KB│8KB│8KB│  │            64KB               │
└───┴───┴───┴───┘  └────────────────────────────────┘
```

### Связь с планировщиком GMP

Модель аллокатора Go завязана на планировщик горутин (GMP): у каждого **M** (OS thread) есть свой локальный кэш — аллокации туда идут без блокировок. Contention возникает только когда кэш потока исчерпан и нужно сходить в общую арену за спанами.

```
   G  G      P        G      P
              │                │
   G  M(thread)        G  M(thread)
        │                    │
     cache                cache
        └──────┬───────────┘
           Contention
                │
                ▼
      ┌──────────────────┐
      │       Arena       │
      │  span   span      │
      └──────────────────┘
```

### За счёт чего фрагментация в Go предсказуема

```
1  ⇄ [8KB] ⇄ [8KB] ⇄ [8KB] ⇄ (...)
2  ⇄ [8KB] ⇄ [8KB] ⇄ [8KB] ⇄ (...)
...
35 ⇄ [16KB] ⇄ [16KB] ⇄ [16KB] ⇄ (...)
...
48 ⇄ [32KB] ⇄ [32KB] ⇄ (...)
```

Каждый **spanClass** (пронумерован: 1, 2, 3, ..., 35, ..., 48) закреплён за span'ами объектов фиксированного размера. Внутри класса span'ы объединены в связный список — это позволяет быстро находить свободный блок нужного размера. Именно фиксированный набор классов и заранее известный "потолок потерь" делает фрагментацию **предсказуемой**: память тратится не хаотично, а с чётким шагом округления до ближайшего класса.

**Таблица size classes** (фрагмент):

|class|bytes/obj|bytes/span|objects|tail waste|max waste|min align|
|---|---|---|---|---|---|---|
|1|8|8192|1024|0|87.50%|8|
|2|16|8192|512|0|43.75%|16|
|3|24|8192|341|8|29.24%|8|
|4|32|8192|256|0|21.88%|32|
|5|48|8192|170|32|31.52%|16|
|6|64|8192|128|0|23.44%|64|
|...|||||||
|67|32768|32768|1|0|12.50%|8192|

**Max waste** — худший случай потерь внутри класса: сколько байт "пропадёт впустую", если объект чуть больше предыдущего класса, но округлился вверх до текущего.

**Примеры:**

- `var data [16]byte` → попадает во **2 класс** (16 bytes/obj), попадает впритык → **0% waste**.
- `var data [9]byte` → тоже во **2 класс** (ближайший класс ≥ 9 — это 16), но реально нужно только 9 из 16 → `(16-9)/16 = 43.75% waste`.
- `bool` (1 байт) → попадёт в **1 класс** (8 bytes/obj), используется 1 байт из 8, потеряно 7 — это и есть тот самый 87.50% max waste для 1 класса.

Именно фиксированный набор классов и заранее известный max waste для каждого делает фрагментацию **предсказуемой**: заранее можно посчитать максимум потерь на округление — в отличие от непредсказуемой фрагментации кучи как у классического malloc.

### Почему Go не устраняет фрагментацию через compaction

Мы разобрали четыре классических способа борьбы с external fragmentation, и Go выбрал способ #1 (segregated size classes). Логичный вопрос: а почему не способ #4 (compaction)? Ведь дальше по конспекту мы увидим, что стек в Go **буквально копируется и переезжает** при росте (раздел про Contiguous Stack ниже) — чем не разновидность compaction?

Короткий ответ: это два разных механизма, которые случайно выглядят похоже.

- **Копирование стека** — не про фрагментацию, а про нехватку места. У стека и так нет дыр (LIFO, всё плотно), копирование в блок побольше — это просто "resize", концептуально то же самое, что рост `slice` через `append`.
- **Compaction в GC** — именно про устранение дыр, оставшихся от объектов в куче, освобождённых в произвольном порядке.

Почему тогда copy стека — штука безопасная и дешёвая для рантайма, а компактить кучу Go не берётся? Дело сразу в трёх вещах:

- **Указатели на стеке рантайм видит насквозь.** У Go есть точные "stack maps" — компилятор точно знает, в каком месте кадра лежит указатель, а в каком обычное число. При копировании стека рантайм может безопасно переписать вообще все указатели на новые адреса.
- **С кучей так честно не получится.** Указатель на объект в куче может утечь через `unsafe.Pointer`, быть передан в C-код через `cgo`, или превращён в `uintptr` и сохранён там, куда GC не заглядывает. Раз язык вообще такое разрешает, компилятор не может дать GC железную гарантию "я вижу все ссылки на этот объект и могу их переписать" — а без этой гарантии двигать объект физически опасно.
- **Concurrent GC не любит движущиеся цели.** GC в Go спроектирован работать **параллельно** с самой программой (mutator), чтобы не давать длинных пауз. Двигать объект, пока другая горутина потенциально читает/пишет по этому же адресу, требует очень аккуратных write barrier'ов на каждую операцию с указателем — это резко усложняет и удорожает конкурентный сценарий.

По этим причинам GC в Go — **non-moving**: он находит живые объекты (mark) и переиспользует память мёртвых (sweep), но никогда не двигает живые объекты внутри кучи. Три классические стратегии GC-семейства выглядят так:

|Стратегия GC|Двигает объекты?|Что с фрагментацией|Цена|
|---|---|---|---|
|**Mark-Sweep** (non-moving) — как в Go|Нет|Не устраняется, только заранее ограничивается (size classes)|Sweep дешёвый, но нужна инфраструктура классов размеров|
|**Mark-Compact** (moving)|Да, сдвигает живые объекты друг к другу|Полностью устраняется|Нужно переписать все указатели на объект — дороже, обычно есть пауза|
|**Copying / Semispace** (moving)|Да, копирует живые объекты в другую половину памяти|Полностью устраняется, аллокация — тривиальный bump pointer|Нужно вдвое больше памяти "про запас" на вторую половину|

Получается, что вся история с **size classes / spans**, которую мы разбирали выше — не случайная деталь реализации, а прямое следствие архитектурного выбора: раз GC в Go не может убрать фрагментацию перемещением объектов постфактум, единственный вариант — **не дать ей появиться заранее**, структурно, через сегрегированные классы размеров. Это тот же trade-off, что мы видели у Pool Allocator'а в самом начале — просто теперь понятно, почему он выбран именно для рантайма Go, а не "потому что так исторически сложилось".

### Пример: конкатенация строк и лишние аллокации

```go
package main

import (
	"fmt"
	"testing"
)

var result string
var buffer []byte = make([]byte, 33)

func Concat(b *testing.B) {
	for i := 0; i < b.N; i++ {
		result = string(buffer) + string(buffer)
	}
}

func main() {
	b := testing.Benchmark(Concat)
	fmt.Println(b.AllocsPerOp())       // 3
	fmt.Println(b.AllocedBytesPerOp()) // 176

	// allocated 176 bytes = 48 (не 33) + 48 (не 33) + 80 (не 33+33=66)
	// waste = 15 + 15 + 14 = 44 байта (25% waste)
}
```

Здесь наглядно видно, как округление до size class'а "съедает" память: 33 байта запрашивали, а получили блок на 48 — потому что ближайший подходящий класс именно такой.

### Большие объекты (>32768 байт)

```go
package main

import (
	"fmt"
	"unsafe"
)

// Для блоков больше 32768 байт каждый из них всегда состоит
// из нескольких страниц памяти. Размер страницы в официальном
// стандартном Go runtime (версии 1.22) — 8192 байта.
func main() {
	var data1 [32769]byte
	var data2 [32769]byte

	data1Pointer := unsafe.Pointer(&data1)
	data2Pointer := unsafe.Pointer(&data2)

	fmt.Println("adress:", data1Pointer, data2Pointer)
	fmt.Println("size:", unsafe.Sizeof(data1), unsafe.Sizeof(data2))

	distance := uintptr(data2Pointer) - uintptr(data1Pointer)
	fmt.Println("distance:", distance)
	fmt.Println("waste:", distance-unsafe.Sizeof(data1))
}
```

📌 Полезно иногда держать в голове классы размеров: **чем больше объектов создаёшь — тем больше потенциальный профит от подгонки размера под класс без waste.**

Но: **в большинстве случаев читаемый и понятный код лучше, чем оптимизированный, но менее понятный.** Не стоит зацикливаться на size classes ради каждого мелкого объекта.

## Object Allocation: Escape Analysis

**Escape analysis** — это процесс на этапе компиляции, который определяет, где создаются объекты и как они используются, и на основе этого решает: **выделять объект в стеке или в куче**.

Компилятор Go по умолчанию старается положить локальные переменные функции в её stack frame. Но:

> **Если компилятор не может доказать, что переменная не используется после возврата из функции — он обязан выделить её в куче** (garbage-collected heap), чтобы избежать dangling pointer'ов. Также, если локальная переменная очень большая, может быть выгоднее хранить её в куче, а не в стеке.

Есть конкретные лимиты в компиляторе:

```go
// MaxStackVarSize — максимальный размер переменной, которую положим на стек.
// Для явных объявлений вида "var x T" или "x := ...".
MaxStackVarSize = int64(10 * 1024 * 1024) // 10 MB

// MaxImplicitStackVarSize — лимит для переменных, выделяемых НЕЯВНО:
//   p := new(T)
//   p := &T{}
//   s := make([]T, n)
//   s := []byte("...")
MaxImplicitStackVarSize = int64(64 * 1024) // 64 KB
```

Если переменная превышает соответствующий лимит (или не проходит escape analysis по другим причинам) — она "убегает" (escapes) в кучу.

### Смотрим escape analysis вживую

```go
// go build -gcflags '-l -m'
// -l = disable inlining, -m = print optimization decisions

func getResult() int {
	result := 200
	return result
}
// result: no escape — возвращается по значению, копия остаётся безопасной
```

```go
func getResult() *int {
	result := 200
	return &result
}
// result: escapes to heap — берём адрес и возвращаем наружу,
// компилятор не может гарантировать, что result не переживёт функцию
```

```go
func getResult(number *int) int {
	result := *number + 200
	return result
}
// number: no escape — указатель пришёл снаружи, но мы его никуда не "выпускаем"
```

```go
package main

import "fmt"

func printValue(v interface{}) {
	fmt.Println(v)
}

func main() {
	var num1 int = 10
	var str1 string = "Hello"

	printValue(num1) // num1 escapes to heap
	printValue(str1) // str1 escapes to heap

	var num2 int = 10
	var str2 string = "Hello"

	var i interface{}
	i = num2 // num2 NOT escapes to heap
	i = str2 // str2 NOT escapes to heap
	_ = i
}
```

⚠️ **Неочевидный момент:** использование `interface{}` **не всегда** означает уход в кучу. Тут `num1`/`str1` "убежали" из-за передачи в `printValue` (компилятор не может проследить весь путь value через вызов функции с interface-параметром достаточно хорошо), а `num2`/`str2` — нет, хотя они точно так же "упакованы" в `interface{}`. Разница в том, как именно используется значение дальше — единого простого правила "interface = heap" тут нет, надо смотреть `-gcflags '-m'` в конкретном случае.

### Несколько фактов про escape

- если одно из полей структуры "переезжает" в кучу — **вся структура** переезжает в кучу
- если один из элементов массива "переезжает" в кучу — **все элементы массива** переезжают в кучу
- если один из элементов среза "переезжает" в кучу — **все элементы среза** переезжают в кучу

То есть escape "заразителен" — одна убегающая часть тянет за собой всё целое.

Ещё неочевидная деталь: объект, созданный через `new()`, может оказаться **и в стеке, и в куче** — это тоже решает escape analysis, а не сам факт вызова `new`.

```go
func createPointer() *int {
	value2 := new(int)
	return value2
}

func main() {
	value1 := new(int) // stack — не покидает main, безопасно
	_ = value1

	value2 := createPointer() // heap — указатель "утекает" наружу из функции
	_ = value2
}
```

## Почему выделение в стеке быстрее, чем в куче?

Важная база: **в архитектуре компьютера нет понятий "stack" и "heap"** — есть просто планка оперативной памяти. Деление на stack/heap, навешивание на куски виртуальной памяти этих ролей — это уже дело ОС и рантайма, то есть уровень software, а не hardware.

```
Allocation:  SP += size
┌──────────┬──────┬──────────────────────┐
│   Used   │      │        Unused        │
└──────────┴──────┴──────────────────────┘
                  ↑
            Stack Pointer (SP)

Deallocation:  SP -= size
┌──────────┬───────────────────────────────┐
│   Used   │           Unused              │
└──────────┴───────────────────────────────┘
           ↑
     Stack Pointer (SP)
```

Выделение и освобождение памяти в стеке — это просто **сдвиг указателя стека**: аллокация — `SP += size`, деаллокация — `SP -= size`. Не нужно искать свободный блок подходящего размера, обновлять метаданные free list'а или синхронизироваться с другими потоками. Отсюда и колоссальная разница в скорости по сравнению с кучей.

### Но у стека в Go есть свои накладные расходы

```go
// The minimum size of stack used by Go code
stackMin = 2048 // 2 KB
```

Каждая горутина стартует со стеком **всего 2KB**. Если нужно больше — стек автоматически растёт (в Go он растущий/сегментированный по своей природе).

**Segmented Stack (как было раньше в старых версиях Go)**

```
┌──────────────┐        ┌──────────────┐
│ Current stack│   →    │ Current stack│
│              │        ├──────────────┤
│              │        │ New segment  │
└──────────────┘        └──────────────┘
```

При переполнении текущего стека рантайм выделял **отдельный новый сегмент** и переключался на него. Проблема — **"hot split"** (эффект качелей): если вызов функции постоянно происходит ровно на границе сегмента, программа начинает часто прыгать туда-обратно между сегментами — это дорого.

**Contiguous Stack (как сейчас)**

```
┌──────────────┐        ┌──────────────────┐
│ Current stack│   →    │  New stack        │
│              │        │  (обычно вдвое    │
│              │        │   больше)         │
└──────────────┘        └──────────────────┘
```

Вместо отдельного сегмента рантайм выделяет **новый, более крупный непрерывный** блок (обычно вдвое больше), копирует туда все данные старого стека и обновляет все указатели. Это устраняет hot split, но требует затрат на копирование — именно это и есть "накладные расходы" роста/сжатия стека в Go. Может происходить и сужение стека — когда используется менее ~25% от текущего размера.

⚠️ **Не путай это с compaction в GC** (разбирали разницу в разделе про фрагментацию выше) — тут нет дыр, которые устраняются. Это чистый resize под нехватку места, тот же принцип, что у `append` на слайсах: понадобилось больше — выделили больше и скопировали. А то, что рантайм при этом безопасно переписывает все указатели на стек — возможно только потому, что для стека Go точно знает расположение каждого указателя (stack maps); с кучей, как мы обсуждали, такой роскоши нет.

```go
// Max stack size is 1 GB on 64-bit, 250 MB on 32-bit.
if goarch.PtrSize == 8 {
	maxstacksize = 1000000000
} else {
	maxstacksize = 250000000
}
```

У стека горутины есть верхний предел: **1 GB на 64-бит**, **250 MB на 32-бит**. Превысил — получил `stack overflow`.

### Стек реально "переезжает" при росте

```go
// go run -gcflags '-l' main.go

func process(index int) byte {
	var data [1 << 20]byte
	return data[index]
}

func main() {
	var index int = 100

	pointer := &index
	println("pointer:", pointer)
	process(index)
	println("pointer:", pointer)
}
```

Вывод (адреса будут отличаться на твоей машине):

```
pointer: 0x45d382310720
pointer: 0x45d38233cf20
```

Адрес `index` **меняется** после вызова `process` — потому что внутри `process` понадобился большой массив, стек горутины расширился (был скопирован в новый непрерывный блок), и `index` физически переехал вместе со всем стеком.

**Итого, почему стек быстрее:**

- растёт/уменьшается не так часто, как может показаться
- сам алгоритм выделения на стеке предельно простой (просто сдвиг SP) и дружелюбен к кэшам CPU
- GC не занимается стеками горутин вообще — это не создаёт ему дополнительной работы
- стековая память освобождается не по частям, а целиком, одним блоком — при завершении горутины

## Что это даёт на практике: бенчмарки

### Value vs Pointer из конструктора

```go
package main

import "testing"

// go test -bench=. -benchmem

type Data struct {
	iValue int
	sValue string
	bValue bool
}

//go:noinline
func NewDataByValue() Data {
	return Data{iValue: 100, sValue: "100", bValue: true}
}

//go:noinline
func NewDataByPointer() *Data {
	return &Data{iValue: 100, sValue: "100", bValue: true}
}

func BenchmarkNewByValue(b *testing.B) {
	for i := 0; i < b.N; i++ {
		_ = NewDataByValue()
	}
}

func BenchmarkNewByPointer(b *testing.B) {
	for i := 0; i < b.N; i++ {
		_ = NewDataByPointer()
	}
}
```

Разница на бенчмарке будет видна невооружённым глазом (Value — на стеке, дешевле; Pointer — escape в кучу, дороже + нагрузка на GC). Но **не нужно из этого делать правило** "всегда возвращай значение, а не указатель" — задумываться об этом стоит, только если конструктор вызывается очень часто и создаёт много объектов `Data`.

### Slice как аргумент vs slice как возврат

```go
package main

import "testing"

// go test -bench=. -benchmem

const bufferSize = 10

type ReaderWithSliceArgument struct{}

func (r ReaderWithSliceArgument) Read(p []byte) (int, error) {
	for i := 0; i < bufferSize; i++ {
		p[i] = byte(i)
	}
	return bufferSize, nil
}

type ReaderWithSliceReturn struct{}

func (r ReaderWithSliceReturn) Read(n int) ([]byte, error) {
	p := make([]byte, n) // выделяем внутри — потенциальный кандидат на heap
	for i := 0; i < n; i++ {
		p[i] = byte(i)
	}
	return p, nil
}

func BenchmarkSliceWithArgument(b *testing.B) {
	for i := 0; i < b.N; i++ {
		p := make([]byte, bufferSize)
		reader := ReaderWithSliceArgument{}
		_, _ = reader.Read(p)
	}
}

func BenchmarkSliceWithReturn(b *testing.B) {
	for i := 0; i < b.N; i++ {
		reader := ReaderWithSliceReturn{}
		_, _ = reader.Read(bufferSize)
	}
}
```

Идея паттерна `Read(p []byte)` (как в `io.Reader`) не случайна: буфер выделяет **вызывающая сторона** и переиспользует его между вызовами — вариант с возвратом слайса каждый раз создаёт новый буфер.

### Загадка со вложенным указателем

```go
package main

import "testing"

// go test -bench=. -benchmem

type Data struct {
	pointer *int
}

func BenchmarkIteration1(b *testing.B) {
	for i := 0; i < b.N; i++ {
		var number int
		data := &Data{
			pointer: &number, // инициализация сразу в литерале
		}
		_ = data
	}
}

func BenchmarkIteration2(b *testing.B) {
	for i := 0; i < b.N; i++ {
		var number int
		data := &Data{}
		data.pointer = &number // присвоение отдельной строкой после создания
		_ = data
	}
}
```

⚠️ **Честно говоря, разница в поведении escape analysis здесь неочевидна** (в конспекте пометка "первый идёт в стек, второй — в хип, непонятно почему"). Похоже, что дело в том, как именно escape analysis Go анализирует поток данных: инициализация поля прямо в литерале структуры анализируется иначе, чем присвоение полю через отдельную инструкцию после создания. Если тебе важна точность на конкретной версии компилятора — единственный надёжный способ проверить это не гадание, а `go build -gcflags '-m'` на актуальной версии.

## Object Pool

Паттерн, а не конкретный тип аллокатора: набор уже инициализированных, готовых к использованию объектов.

- когда системе нужен объект — он не создаётся заново, а берётся из пула
- когда объект больше не нужен — он не уничтожается, а возвращается в пул

```go
type Pool struct {
	New func() any
}

func (p *Pool) Get() any  // забирает объект из пула
func (p *Pool) Put(x any) // кладёт объект обратно в пул
```

Это, собственно, идея за `sync.Pool` из стандартной библиотеки Go — снижает количество аллокаций и нагрузку на GC для часто создаваемых/уничтожаемых объектов.

## Arenas (Region-Based Memory Management)

Ещё один способ уменьшить количество аллокаций — арены на уровне пользовательского кода (не путать с внутренними аренами рантайма Go, хотя идея та же). Предназначены для **батчевой обработки данных**: когда много объектов создаётся подряд, и в какой-то момент всё это разом больше не нужно — хочется очистить всё одним махом, не нагружая GC поштучным обходом.

```
┌────────────┐
│chunk (8MB) │
└─────┬──────┘
      ▼
┌────────────┐
│chunk (8MB) │
└─────┬──────┘
      ▼
┌────────────┐
│chunk (8MB) │
└────────────┘
```

Арена состоит из последовательных чанков (по 8MB), в которую можно аллоцировать много объектов подряд. Когда данные больше не нужны — вся арена освобождается **одним вызовом**, GC не приходится обходить каждый объект по отдельности.

```go
// GOEXPERIMENT=arenas go run main.go
package main

import "arena"

type Data struct {
	deposit int
	credit  int
}

func main() {
	a := arena.NewArena()
	defer a.Free()

	value := arena.New[int64](a)
	_ = value

	data := arena.New[Data](a)
	_ = data

	slice := arena.MakeSlice[int32](a, 0, 10)
	_ = slice

	cloned := arena.Clone[*Data](data) // явно копируется в heap — за пределами жизни арены
	_ = cloned
}
```

⚠️ **Arena Problem #1 — arenas не аллоцируют все reference-типы автоматически**

```go
type Data struct {
	value     int
	operaions []int
}

func main() {
	a := arena.NewArena()
	defer a.Free()

	operations := arena.MakeSlice[int](a, 0, 100) // явно создали в арене
	data := arena.New[Data](a)
	data.operaions = operations
	_ = data
}
```

Тут в примере всё сделано правильно — slice явно создан через `arena.MakeSlice`. Но грабли в том, что **это нужно делать руками для каждого reference-типа**: если бы `operations` был создан обычным `make([]int, 0, 100)`, он бы жил в обычной куче, а `Data` — в арене, и время жизни этих двух частей одного объекта банально разъехалось бы.

⚠️ **Arena Problem #2 — append может "выбить" данные из арены в кучу**

```go
func main() {
	mem := arena.NewArena()
	defer mem.Free()

	slice := arena.NewSlice[int](mem, 0, 5)
	slice = append(slice, 1, 2, 3, 4, 5)

	slice = append(slice, 6) // moved to heap!
}
```

Как только `append` выходит за capacity, выделенную в арене — Go под капотом делает то же самое, что и с обычным слайсом: аллоцирует новый, более крупный массив. Но новый массив уже создаётся **в обычной куче**, а не в арене — то есть часть данных незаметно "утекает" мимо арены, и её жизненным циклом уже управляет обычный GC, а не `arena.Free()`.

📌 Экспериментальная фича arenas в итоге не вошла в стандартный Go в этом виде — так что относись к этому больше как к иллюстрации идеи region-based memory management, чем к готовому production-инструменту.

## Главный вывод

**В большинстве случаев читаемый и понятный код будет лучшим решением, чем оптимизированный, но менее понятный.** Всё, что описано выше (size classes, escape analysis, арены) — это инструменты для конкретных hot path'ов, которые ты уже профилировал и знаешь, что там проблема. Не ради того, чтобы применить их везде "на всякий случай".

Финальный пример — что будет, если просто беспрерывно аллоцировать память без GC:

```go
package main

import "fmt"

// go run main.go
// GOGC=off go run main.go

var data []byte

func main() {
	count := 0

	for {
		data = make([]byte, 1<<30) // 1 GB за итерацию
		fmt.Println("allocated GB:", count)
		count++
	}
}
```

С `GOGC=off` GC вообще выключен — программа будет наращивать потребление памяти без остановки, пока не упрётся в лимиты ОС и не упадёт с OOM. Хороший наглядный способ почувствовать, зачем вообще нужен GC.
