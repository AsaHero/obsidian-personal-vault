Горутины сами по себе изолированы — у каждой свой стек, и просто так между ними данными не обменяешься. Channel — это как раз примитив, который решает эту проблему: труба, в которую можно класть значения и из которой можно их доставать.

Основные свойства channel:

- **блокирует/разблокирует горутины** — send и receive могут ждать друг друга
- **типизирован** — `chan int` и `chan string` это разные типы, значения смешивать нельзя
- **работает как FIFO очередь** — что первым положили, то первым и достанут
- **goroutine-safe** — можно писать/читать из разных горутин без доп. синхронизации (но! см. ниже про data race с обычными переменными)

## API канала

```go
var ch chan int // тип "channel of int", nil-канал пока не сделан make

ch = make(chan int) // создаём unbuffered channel
ch <- 1              // send — положить значение в канал
value := <-ch        // receive — забрать значение из канала
close(ch)             // закрыть канал — больше в него никто не пишет
```

Смотри на самый простой пример, чтобы понять блокирующую природу channel:

```go
package main

import (
	"fmt"
	"time"
)

func async(ch chan string) {
	time.Sleep(2 * time.Second)
	ch <- "async result" // send заблокируется, пока кто-то не сделает <-ch
}

func main() {
	ch := make(chan string)
	go async(ch)

	result := <-ch // main блокируется тут на ~2 секунды, ждёт значение
	fmt.Println(result)
}
```

`main` физически не может продолжить выполнение, пока `async` не положит значение в канал — это и есть блокировка, о которой идёт речь.

## "Не общайся через shared memory, общайся через channels"

В Go community есть известный принцип:

> Don't communicate by sharing memory; share memory by communicating

То есть вместо того чтобы городить мьютексы вокруг общей переменной, лучше **передавать владение данными** через channel. Одна горутина кладёт значение (по сути — копию) в канал и перестаёт с ним работать, другая забирает и с этого момента владеет им единолично. В любой момент времени данными реально пользуется только одна горутина — гонки данных просто неоткуда взяться.

## `select` — жду сразу из нескольких каналов

Что делать, если результат может прийти из одного из нескольких источников и не важно, в каком порядке? Для этого есть `select`:

```go
package main

import (
	"fmt"
	"time"
)

func async1() chan string {
	ch := make(chan string)
	go func() {
		time.Sleep(1 * time.Second)
		ch <- "async1 result"
	}()
	return ch
}

func async2() chan string {
	ch := make(chan string)
	go func() {
		time.Sleep(1 * time.Second)
		ch <- "async2 result"
	}()
	return ch
}

func main() {
	ch1 := async1()
	ch2 := async2()

	select {
	case result := <-ch1:
		fmt.Println(result)
	case result := <-ch2:
		fmt.Println(result)
	}
}
```

`select` блокируется, пока хотя бы один из case-ов не станет готов к выполнению. Если готовы сразу несколько — выбор между ними псевдослучайный (это важно, ниже будет пример, который это доказывает).

### ⚠️ `break` и `continue` внутри `select`, который сидит в `for`

Частая путаница:

```go
package main

import "fmt"

func main() {
	data := make(chan int)
	go func() {
		for i := 1; i <= 4; i++ {
			data <- i
		}
		close(data)
	}()

	for {
		value := 0
		opened := true

		select {
		case value, opened = <-data:
			if value == 2 {
				continue // это continue для FOR, не для select!
			} else if value == 3 {
				break // а это break для SELECT, не для for!
			}

			if !opened {
				return
			}
		}

		fmt.Println(value)
	}
}
```

**Подводный камень**: `continue` относится к ближайшему `for`, а `break` — к ближайшему `select`/`switch`/`for`, который стоит непосредственно вокруг него. Так как `select` синтаксически похож на `switch`, `break` внутри `case` просто выходит из `select`, а не из внешнего `for`. Если бы вам реально нужно было прервать `for` изнутри `select`, пришлось бы использовать labeled break (`break Loop`).

## Pub/Sub паттерн (producer/consumer)

Самый частый способ общаться через channel — классический producer/consumer:

```go
package main

import (
	"fmt"
	"sync"
)

func producer(ch chan int) {
	defer close(ch) // закрывает тот, кто пишет — см. правило ниже
	for i := 0; i < 5; i++ {
		ch <- i
	}
}

func consumer(ch chan int) {
	// вот так это выглядело бы руками, через select:
	//
	// for {
	// 	select {
	// 	case value, opened := <-ch:
	// 		if !opened {
	// 			return
	// 		}
	// 		fmt.Println(value)
	// 	}
	// }

	for value := range ch { // syntax sugar ровно для кода выше
		fmt.Println(value)
	}
}

func main() {
	ch := make(chan int)
	wg := sync.WaitGroup{}
	wg.Add(2)

	go func() {
		defer wg.Done()
		producer(ch)
	}()

	go func() {
		defer wg.Done()
		consumer(ch)
	}()

	wg.Wait()
}
```

`for value := range ch` сам выйдет из цикла, когда канал закроют и в нём не останется значений — не нужно вручную проверять `ok`.

## Signals паттерн

Если данные не важны, а важен сам факт события — используем `chan struct{}`:

```go
package main

import (
	"fmt"
	"sync"
)

func notifier(signals chan struct{}) {
	signals <- struct{}{} // struct{}{} — пустая структура, занимает 0 байт
}

func subscriber(signals chan struct{}) {
	<-signals
	fmt.Println("signaled")
}

func main() {
	signals := make(chan struct{})
	wg := sync.WaitGroup{}
	wg.Add(2)

	go func() {
		defer wg.Done()
		notifier(signals)
	}()

	go func() {
		defer wg.Done()
		subscriber(signals)
	}()

	wg.Wait()
}
```

`struct{}` тут используется именно потому, что нам не нужен payload — только сам факт "что-то произошло", и это экономичнее, чем гонять `bool` или `int`.

## Проверка: закрыт канал или нет

```go
value, ok := <-ch
if ok {
	// канал открыт, value — реальное значение
} else {
	// канал закрыт и все значения из него уже вычитаны
}
```

Это стандартная идиома Go: при чтении канал возвращает второе значение `ok` — `true`, если канал открыт и мы реально получили значение, `false` — если канал закрыт и буфер пуст.

## Unbuffered vs Buffered каналы

### Unbuffered (синхронные)

```go
ch := make(chan int)
```

```
   G1 (sender)                    G2 (receiver)
       │                               │
       │──── ch <- val ──▶ 🔒 ◀────── <-ch ────│
       │                               │
   заблокирован, пока        заблокирован, пока
   receiver не готов          sender не готов
```

Send и receive обязаны "встретиться" одновременно: отправитель блокируется, пока какая-то горутина не выполнит чтение, и наоборот. Отсюда и название — **синхронные каналы**.

### Buffered (асинхронные)

```go
ch := make(chan int, 4)
```

```
   G2 (sender)                              G1 (receiver)
       │                                         │
       └──▶ [●][●][ ][ ] ──────────────────────▶ │
             buf, cap=4, qcount=2
```

Здесь отправитель может класть значения в буфер, не дожидаясь читателя — пока в буфере есть место. Отправка заблокируется только когда буфер **полон**, чтение — только когда буфер **пуст**. Отсюда название — **асинхронные каналы**.

### Плюсы/минусы

|               | Unbuffered                                                             | Buffered                                                        |
| ------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------- |
| Синхронизация | Жёсткая гарантия "получатель забрал значение до того, как я продолжил" | Гарантии нет — значение может просто лежать в буфере            |
| Throughput    | Ниже, больше блокировок                                                | Выше, sender не ждёт готового receiver'а                        |
| Отладка       | Баги (deadlock, race) проявляются сразу                                | Баги могут "спрятаться" и вылезти только когда буфер заполнится |
| Когда брать   | Нужен rendezvous / handoff                                             | Нужно сгладить разницу в скорости producer/consumer             |

### `len` и `cap`

```go
ch := make(chan int, 4)
fmt.Println(len(ch)) // сколько элементов сейчас в буфере
fmt.Println(cap(ch)) // размер буфера
```

Эти функции безопасно вызывать из разных горутин без дополнительной синхронизации — рантайм сам это гарантирует.

**Вопрос:** чему равен буфер unbuffered-канала? Ответ — `0`. Формально unbuffered channel это просто buffered channel с `cap == 0`.

## Каналы — это указатели

Channel — это указатель на структуру `hchan` (см. секцию "внутреннее устройство" ниже). Поэтому:

- каналы можно **копировать** — копия и оригинал указывают на один и тот же `hchan`
- если пишешь в копию — это отражается и в оригинале, потому что физически это один и тот же объект

## Кто должен закрывать канал

Правило простое:

1. Канал закрывает тот, **кто в него пишет**.
2. Если писателей несколько — закрывает тот, кто создал и писателей, и сам канал (владелец).

> ⚠️ Никогда не закрывай канал со стороны читателя, никогда не закрывай канал дважды (паника `close of closed channel`) и никогда не закрывай `nil`-канал (тоже паника).

## Что будет, если не закрыть канал

Ничего фатального сразу — канал такой же указатель, как любой другой, и соберётся GC, если на него никто не ссылается. Но архитектурно с каналами часто ловят **goroutine leak**:

```go
package main

import (
	"fmt"
	"log"
	"time"
)

func main() {
	doWork := func(strings <-chan string) {
		go func() {
			for str := range strings { // range никогда не завершится, канал не закрывают
				fmt.Println(str)
			}
			log.Println("doWork exited") // эта строка никогда не напечатается
		}()
	}

	strings := make(chan string)
	doWork(strings)
	strings <- "Test"

	time.Sleep(time.Second)
	fmt.Println("Done")
}
```

Канал `strings` никто не закрывает, поэтому запущенная внутри `doWork` горутина зависает в `range` навечно. Это классический **goroutine leak**: горутина держит свой стек в памяти, и заодно не даёт GC собрать сам канал, так как на него всё ещё есть живая ссылка.

## First-response-wins — ещё один источник утечек

Частый паттерн: спросить у нескольких источников и забрать первый ответ, остальные проигнорировать.

```go
package main

// Первая версия — с проблемой

func request() int {
	ch := make(chan int) // unbuffered!
	for i := 0; i < 5; i++ {
		go func() {
			ch <- i // 4 из 5 горутин навсегда зависнут здесь
		}()
	}

	return <-ch
}
```

Так как канал unbuffered, а читаем мы только один раз — 4 горутины из 5 успешно "выиграют гонку" на блокировку и останутся висеть в `sendq` навсегда. Классический goroutine leak.

**Решение** — сделать канал буферизированным на количество горутин, чтобы никто не заблокировался:

```go
func request() int {
	ch := make(chan int, 5) // буфер на все горутины сразу

	for i := 0; i < 5; i++ {
		i := i // до Go 1.22 нужна была локальная копия — иначе все горутины видели одно и то же i
		go func() {
			ch <- i // теперь запись не блокирует — место в буфере есть у всех
		}()
	}

	return <-ch // берём первый ответ, остальные 4 значения просто останутся в буфере
}
```

> ⚠️ Захват переменной цикла в замыкании — отдельная классическая ловушка Go. В версиях **до 1.22** все горутины из примера выше видели бы одну и ту же переменную `i` (последнее значение), поэтому нужна была локальная копия `i := i`. Начиная с Go 1.22 у каждой итерации `for` — своя переменная, и этот трюк уже не нужен, но полезно про него знать, если работаешь со старым кодом.

## Hanging goroutines (подвисшие горутины)

Горутина, которая навсегда осталась в заблокированном состоянии. Типичные случаи:

- горутина ждёт значение из канала, в который больше никто не напишет и который никто не закроет
- горутина пытается отправить в `nil`-канал или в канал, который больше никто не читает
- горутина заблокировала сама себя мьютексом (например, повторный `Lock()`)
- несколько горутин заблокированы друг на друге через несколько мьютексов (deadlock)

## Однонаправленные каналы

```go
chan<- T // только запись (send-only)
<-chan T // только чтение (receive-only)
```

```go
package main

import "fmt"

func in(in chan<- int) {
	in <- 100
	close(in)
}

func out(out <-chan int) {
	fmt.Println(<-out)
}

func main() {
	var ch = make(chan int, 1)

	in(ch)
	out(ch)
}
```

Зачем это нужно: обычный `chan int` неявно приводится к `chan<- int` или `<-chan int` при передаче в функцию. Это чисто компайл-тайм защита — функция, принимающая `<-chan T`, физически не сможет случайно написать в канал, даже если очень захочет. Компилятор не даст.

Ещё момент, про который легко забыть:

```go
var cch chan chan string // канал, элементы которого — сами каналы string
```

Это не экзотика, а рабочий паттерн: например, request-response через channel, где вместе с запросом ты пересылаешь "канал для ответа".

## Каналы — first-class citizens

Channel в Go — обычное значение, поэтому его можно:

- хранить как поле структуры
- передавать как аргумент функции
- возвращать как результат функции/метода
- использовать как тип элемента другого канала (`chan chan string` выше)

## Приоритизация чтения в `select`

Официального механизма приоритетов в `select` нет, но есть трюк — задублировать case:

```go
package main

import "fmt"

func main() {
	ch1 := make(chan struct{}, 1)
	ch2 := make(chan struct{}, 1)

	close(ch1)
	close(ch2)

	ch1Value := 0.0
	ch2Value := 0.0

	for i := 0; i < 100000; i++ {
		select {
		case <-ch1:
			ch1Value++
		case <-ch1: // тот же ch1 второй раз
			ch1Value++
		case <-ch2:
			ch2Value++
		}
	}

	fmt.Println(ch1Value / ch2Value)
}
```

Output: `1.9585679238837`

`select` выбирает случайный **case**, а не случайный **канал** — если один и тот же канал упомянут в двух case, у него вдвое больше шансов быть выбранным. Отсюда и результат, близкий к 2.

> ⚠️ Это хак, а не гарантированный языком механизм — точных пропорций спецификация не обещает, только "uniform pseudo-random selection среди готовых case". Если реально нужна жёсткая приоритизация, надёжнее сделать вложенные select: сначала non-blocking select по приоритетному каналу, и только если он не готов — обычный select по всем:

```go
select {
case v := <-highPriority:
	handle(v)
default:
	select {
	case v := <-highPriority:
		handle(v)
	case v := <-lowPriority:
		handle(v)
	}
}
```

## Non-blocking чтение/запись

Первая идея, которая приходит в голову — но она сломана:

```go
package main

// ❌ Неправильно — race condition между проверкой и действием

func tryToReadFromChannel(ch chan string) (string, bool) {
	if len(ch) != 0 {
		value := <-ch // между len() и <-ch другая горутина может успеть забрать значение!
		return value, true
	}
	return "", false
}

func tryToWriteToChannel(ch chan string, value string) bool {
	if len(ch) < cap(ch) {
		ch <- value // и тут та же проблема — место могли успеть занять
		return true
	}
	return false
}
```

**Подводный камень**: `len(ch) != 0` и последующий `<-ch` — это две отдельные операции. Если между ними вклинится другая горутина, `<-ch` может неожиданно заблокироваться, хотя вы хотели non-blocking поведение.

Правильный способ — `select` с `default`, это одна атомарная операция:

```go
func tryToReadFromChannel(ch chan string) (string, bool) {
	select {
	case value := <-ch:
		return value, true
	default:
		return "", false
	}
}

func tryToWriteToChannel(ch chan string, value string) bool {
	select {
	case ch <- value:
		return true
	default:
		return false
	}
}

// то же самое можно комбинировать: попробовать прочитать ИЛИ записать
func tryToReadOrWrite(ch1 chan string, ch2 chan string) {
	select {
	case <-ch1:
	case ch2 <- "test":
	default:
	}
}
```

## Проверка "канал закрыт?" — плохая идея

Часто пишут вот такую функцию:

```go
package main

import "fmt"

func IsClosed(ch chan int) bool {
	select {
	case <-ch:
		return true
	default:
		return false
	}
}

func main() {
	ch := make(chan int)
	fmt.Println(IsClosed(ch)) // false
	close(ch)
	fmt.Println(IsClosed(ch)) // true
}
```

Для пустого unbuffered-канала это вроде бы работает. Но стоит дать каналу буфер:

```go
ch := make(chan int, 1)
ch <- 42
```

...и функция сломается: `select` зайдёт в `case <-ch`, **реально заберёт значение 42 из буфера** (канал ведь не закрыт, просто там лежат данные) и вернёт `true`, хотя канал открыт. Плюс у функции появился неприятный побочный эффект — она тихо съела чужое значение.

> ⚠️ Вывод: если вы правильно используете каналы (читаете через `for range` или через `ok` до тех пор, пока канал открыт), вам почти никогда не нужно спрашивать "закрыт ли канал?" снаружи — это уже даёт вам сам факт получения `ok == false`.

## Data race, который не про сам канал

Часто говорят "каналы можно не синхронизировать" — это правда только про операции send/receive/close **над самим каналом**. Вот пример, где это не спасает:

```go
package main

import "sync"

// go run -race main.go покажет DATA RACE

var buffer chan int

func main() {
	wg := sync.WaitGroup{}
	wg.Add(100)

	for i := 0; i < 100; i++ {
		go func() {
			defer wg.Done()
			buffer = make(chan int) // это НЕ операция канала, это запись в обычную package-level переменную
		}()
	}

	wg.Wait()
}
```

Тут 100 горутин конкурентно пишут в **обычную переменную** `buffer` (которая просто хранит указатель на channel). Это классический data race, никак не связанный с внутренней потокобезопасностью самого `hchan` — она защищает только операции над уже созданным каналом, а не присваивание переменной, которая на него ссылается.

## Порядок вычислений: почему код работает 4 секунды, а не 2

```go
package main

import (
	"fmt"
	"time"
)

func FetchData1() chan int {
	ch := make(chan int)
	go func() {
		time.Sleep(time.Second * 2)
		ch <- 10
	}()
	return ch
}

func FetchData2() chan int {
	ch := make(chan int)
	go func() {
		time.Sleep(time.Second * 2)
		ch <- 20
	}()
	return ch
}

func Process(value1, value2 int) {
	// ...
}

func main() {
	start := time.Now()
	Process(<-FetchData1(), <-FetchData2()) // ❌ выполнится за ~4 секунды
	fmt.Println(time.Now().Sub(start))
}
```

**Почему так**: Go вычисляет аргументы функции по порядку слева направо. Сначала целиком вычисляется `<-FetchData1()` — это значит: вызвать `FetchData1()` (сама по себе не блокирует, сразу возвращает канал) и тут же сделать `<-` на нём (а вот это блокирует на 2 секунды). Только **после того**, как первый аргумент полностью посчитан, Go переходит ко второму аргументу — и только тогда стартует вторая горутина через `FetchData2()`. Поэтому второе ожидание начинается на 2 секунды позже первого, и суммарно получается 4 секунды вместо параллельных 2.

**Исправление** — сначала запустить обе горутины (получить оба канала), и только потом читать из них:

```go
func main() {
	start := time.Now()

	ch1 := FetchData1() // горутина стартовала сразу
	ch2 := FetchData2() // и эта тоже, не дожидаясь первой

	Process(<-ch1, <-ch2) // теперь оба ожидания идут параллельно, суммарно ~2 секунды

	fmt.Println(time.Now().Sub(start))
}
```

## `nil`-каналы: зачем они вообще нужны

Read и write на `nil`-канале **блокируются навсегда** (никогда не станут ready). Звучит бесполезно, но именно это свойство используют, чтобы **надёжно выключить конкретный case в `select`**.

Вот пример, где без этого трюка получается недетерминированный баг:

```go
package main

import (
	"fmt"
	"sync"
)

// ❌ Багованная версия

func WaitToClose(lhs, rhs chan struct{}) {
	lhsClosed, rhsClosed := false, false
	for !lhsClosed || !rhsClosed {
		select {
		case _, ok := <-lhs:
			fmt.Println("lhs", ok)
			if !ok {
				lhsClosed = true
			}
		case _, ok := <-rhs:
			fmt.Println("rhs", ok)
			if !ok {
				rhsClosed = true
			}
		}
	}
}

func main() {
	lhs := make(chan struct{}, 1)
	rhs := make(chan struct{}, 1)

	wg := sync.WaitGroup{}
	wg.Add(1)

	go func() {
		defer wg.Done()
		WaitToClose(lhs, rhs)
	}()

	lhs <- struct{}{}
	rhs <- struct{}{}

	close(lhs)
	close(rhs)

	wg.Wait()
}
```

Тут при каждом запуске можно увидеть разный порядок и разное количество строк в выводе — потому что после того, как канал уже закрыт и опустошён, он **всё равно остаётся готов** для чтения (просто отдаёт `ok == false` бесконечно много раз), и `select` продолжает случайно выбирать этот case снова.

**Правильная версия** — как только канал закрылся, обнуляем саму переменную канала, а не только флаг:

```go
func WaitToClose(lhs, rhs chan struct{}) {
	lhsClosed, rhsClosed := false, false
	for !lhsClosed || !rhsClosed {
		select {
		case _, ok := <-lhs:
			fmt.Println("lhs", ok)
			if !ok {
				lhsClosed = true
				lhs = nil // теперь этот case никогда больше не станет ready
			}
		case _, ok := <-rhs:
			fmt.Println("rhs", ok)
			if !ok {
				rhsClosed = true
				rhs = nil
			}
		}
	}
}
```

> ⚠️ В исходном конспекте тут была опечатка (`lhsClosed = nil` вместо `lhs = nil`) — это не скомпилировалось бы, так как `lhsClosed` типа `bool`. В `nil` нужно обнулять именно сам канал.

Теперь `select` не будет ловить ложные срабатывания: `nil`-канал никогда не готов, поэтому пропускается.

Ещё один показательный пример, где `nil` даёт **детерминированный**, а не случайный результат:

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 1)
	for done := false; !done; {
		select {
		default:
			fmt.Println(3)
			done = true
		case <-ch:
			fmt.Println(2)
			ch = nil
		case ch <- 1:
			fmt.Println(1)
		}
	}
}
```

Output:

```
1
2
3
```

Разберём по шагам:

1. Канал пуст и не `nil` → готов только case `ch <- 1` (в буфере есть место) → печатает `1`, кладёт значение в буфер
2. Канал теперь непустой → готов только case `<-ch` (место занято, send больше не ready) → печатает `2`, обнуляет `ch = nil`
3. Канал теперь `nil` → ни send, ни receive никогда не станут ready → единственный готовый вариант — `default` → печатает `3`, выходим из цикла

На каждом шаге ready ровно один case, поэтому рандома тут нет вообще — вывод всегда одинаковый.

## Channels vs Mutex — когда что использовать

|Используй **channels**, когда...|Используй **mutex**, когда...|
|---|---|
|Нужно передать владение данными (ownership transfer)|Нужно защитить общий кэш|
|Нужно распределить вычисления между воркерами|Нужно защитить общее изменяемое состояние|
|Нужно передать результат асинхронной операции||

Грубое правило: если данные логически "переезжают" от одной горутины к другой — channel. Если несколько горутин одновременно **владеют** одними и теми же данными и просто по очереди их трогают — mutex.

# Внутреннее устройство channel

Тип `chan T` — это указатель на структуру `hchan` из рантайма Go:

```go
type hchan struct {
	qcount    uint           // сколько элементов сейчас реально лежит в очереди
	dataqsiz  uint           // размер циклического буфера (то, что возвращает cap())
	buf       unsafe.Pointer // указатель на массив из dataqsiz элементов
	elemsize  uint16
	closed    uint32         // флаг "канал закрыт"
	elemtype  *_type         // тип элемента канала
	sendx     uint           // индекс, куда писать следующий элемент
	recvx     uint           // индекс, откуда читать следующий элемент
	recvq     waitq          // очередь горутин, ожидающих чтения
	sendq     waitq          // очередь горутин, ожидающих записи

	// lock защищает все поля hchan, а также некоторые поля
	// у sudog, заблокированных на этом канале.
	lock mutex
}
```

### Особенности

1. Channel — это указатель на объект `hchan`.
2. `make(chan T)` возвращает указатель на этот объект (отсюда и copy semantics, о которых говорили выше).
3. Все операции (`<-`, `ch <-`, `close`) на самом деле работают с полями этой структуры через указатель.

Кстати, почему `closed` — это `uint32`, а не `bool`: в Go атомарные операции (`sync/atomic`) гарантированно работают начиная с 32-битных значений, и рантайму нужно уметь **атомарно**, без захвата `lock`, проверять флаг `closed` на быстром пути (fast path) операций отправки/чтения.

## Как устроен буфер внутри

```go
ch := make(chan int, 3)
```

```
struct hchan {
┌──────────┐        buf ──▶ [ 0 ][ 1 ][ 2 ]
│ buf      │──────────────────┘
├──────────┤
│ sendx = 0│   циклический буфер на 3 элемента,
├──────────┤   sendx/recvx показывают, куда писать
│ recvx = 0│   и откуда читать следующее значение
├──────────┤
│ qcount=0 │
├──────────┤
│  lock 🔒 │
└──────────┘
```

`buf` указывает на выделенный циклический буфер из 3 ячеек, `sendx` и `recvx` — индексы для записи и чтения. Сразу после `make` канал пуст, поэтому оба индекса равны `0`.

## Как происходит потокобезопасное чтение/запись

Всё завязано на одном `lock` внутри `hchan` — это не `sync.Mutex`, а низкоуровневый рантайм-мьютекс, но идея та же:

```
   G1 (writer)          lock 🔒          buf: [0]   [1]   [2]
       │                                      │      │      │
       │──── захватывает lock ───────────────▶│      │      │
       │──── пишет значение в buf[sendx] ─────▶ [██]  │      │
       │──── sendx++, qcount++ ───────────────┘      │      │
       │──── отпускает lock ──────────────────────────────────
       │
                                          (G2-читатель ждёт своей
                                           очереди захватить lock)
```

Писатель (G1) захватывает `lock`, чтобы безопасно записать значение в буфер. Пока `lock` удержан, никакая другая горутина (в т.ч. читатель G2) не может одновременно менять состояние канала — это и защищает от гонки данных на внутренних полях `hchan`.

### Что если буфер полон, а мы пишем

Пишущая горутина встаёт в очередь `sendq` в статусе `Waiting`. Рядом с ней в очереди хранится `elem` — указатель на значение, которое она хочет отправить. Будит её **читающая** горутина: она читает значение из циклического буфера, затем проверяет `sendq` — если там кто-то ждёт, забирает его `elem`, кладёт значение в освободившееся место буфера и переводит горутину-писателя в статус `Runnable`, возвращая её в очередь планировщика.

> Похожая механика есть и у мьютексов — только там вместо локальных `sendq`/`recvq` одна общая `waitq`.

### Что если буфер пуст, а мы читаем

Симметрично: читающая горутина встаёт в `recvq` в статусе `Waiting`, рядом хранится указатель на то, куда положить полученное значение. Когда появляется писатель, он **сначала** смотрит именно в `recvq` — если там кто-то ждёт, пишет значение **напрямую по этому указателю**, минуя буфер вообще, и будит горутину-читателя. Это оптимизация direct handoff: копирования через буфер не происходит, если получатель уже стоит и ждёт.

## Гонка close + pending sender = паника

Последний скользкий момент:

```go
package main

import "time"

func main() {
	ch := make(chan int)
	go func() {
		ch <- 1 // заблокируется, встанет в sendq
	}()

	time.Sleep(500 * time.Millisecond) // даём горутине время встать в очередь

	close(ch)
	<-ch

	time.Sleep(100 * time.Millisecond)
}
```

Что тут происходит: горутина блокируется на `ch <- 1`, потому что канал unbuffered и никто пока не читает — она попадает в `sendq` вместе с указателем на своё значение. Через 500мс `main` вызывает `close(ch)`. `close()` будит **все** горутины, ожидающие и в `sendq`, и в `recvq` — но для тех, кто ждал именно **отправки**, пробуждение означает панику `send on closed channel`, потому что отправка в закрытый канал запрещена языком.

> ⚠️ Важно: паника случится в той горутине, которая делала `ch <- 1`, а не в `main`. Но необработанная паника в **любой** горутине убивает весь процесс целиком — поймать её локально и продолжить работу остальной программы не получится без `recover()` прямо в этой горутине.
