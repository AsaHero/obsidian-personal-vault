[[19. SIMD|Закрывая тему параллелизма]], мы насчитали четыре способа получить больше вычислений с одного кристалла — но один практический вопрос остался за скобками. Когда на кристалле не одно ядро, а несколько ([[18. Multicore|18. Multicore]]), как они вообще достучатся до памяти?

## Шина одна, ядер много

Вспомним [[8. RAM#RAM целиком|Data Bus и Address Bus]] из конспекта про RAM: это общие провода — в любой момент времени на них может быть выставлено только одно значение. Пока мы собирали процессор с [[9. CPU|одним ядром]], это не было проблемой: ядро одно, шина ему не с кем делить.

```
┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐
│ Core 0 │  │ Core 1 │  │ Core 2 │  │ Core 3 │
└───┬────┘  └───┬────┘  └───┬────┘  └───┬────┘
    │           │           │           │
    └─────┬─────┴─────┬─────┴─────┬─────┘
          │   Data Bus / Address Bus   │
          └──────────────┬──────────────┘
                          │
                       ┌──▼──┐
                       │ RAM │
                       └─────┘
```

С [[18. Multicore|многоядерностью]] на ту же самую шину и ту же самую RAM теперь претендуют несколько ядер одновременно. Шина — общий ресурс, а не резиновая: пока один Read Enable/Write Enable цикл идёт для Core 0, остальные три ждут своей очереди. Чем больше ядер, тем чаще они друг друга блокируют — и весь выигрыш от многоядерности начинает съедаться этим ожиданием.

## Первая идея: своя память у каждого ядра

Мы уже знаем способ не ходить в RAM за каждым значением — [[12. DRAM|12. DRAM]] закончился мыслью, что кэш процессора — это та же самая SRAM из [[6. Memory|защёлок]], только физически рядом с ядром и без накладных расходов DRAM (precharge, саморазрушительное чтение, refresh).

Дадим **каждому ядру собственный приватный кэш** — назовём его **L1** — построенный из той же SRAM. Большая часть чтений и записей теперь оседает в L1 и вообще не выходит на общую шину: обращения к ней нужны только когда нужного значения в L1 ещё нет (**промах**, cache miss).

```
┌────────┐        ┌────────┐        ┌────────┐        ┌────────┐
│ Core 0 │        │ Core 1 │        │ Core 2 │        │ Core 3 │
│   L1   │        │   L1   │        │   L1   │        │   L1   │
└───┬────┘        └───┬────┘        └───┬────┘        └───┬────┘
    │                 │                 │                 │
    └─────────┬───────┴────────┬────────┴────────┬────────┘
              │      Data Bus / Address Bus       │
              └───────────────┬────────────────────┘
                               │
                            ┌──▼──┐
                            │ RAM │
                            └─────┘
```

## Проблема: L1 маленький, а данных много

L1 — самая быстрая память в системе, но именно поэтому она и самая маленькая: несколько десятков килобайт на ядро — предел того, сколько SRAM физически влезает вплотную к ALU и регистрам, не раздувая кристалл. Реальные программы и наборы данных этот объём превышают на порядки. Как только рабочий набор данных ядра не помещается в L1, промахи снова становятся частыми — и трафик на общую шину возвращается.

Хуже того: если несколько ядер работают с одним и тем же большим массивом данных (например, все читают один и тот же участок памяти), каждое из них промахивается по отдельности и независимо тащит те же самые байты с шины в свой собственный L1 — шина обслуживает одни и те же данные N раз подряд, по одному разу на ядро.

## Решение: ещё один уровень, теперь общий

Добавим второй, более крупный уровень кэша — **L2**, тоже обычно приватный на ядро, но заметно больше L1 (сотни килобайт — единицы мегабайт) и чуть медленнее. А поверх него — **L3**, один-единственный кэш, общий сразу на **все** ядра кристалла, ещё больше (единицы-десятки мегабайт) и ещё медленнее L2, но всё равно на порядок быстрее RAM.

```
┌────────┐        ┌────────┐        ┌────────┐        ┌────────┐
│ Core 0 │        │ Core 1 │        │ Core 2 │        │ Core 3 │
│   L1   │        │   L1   │        │   L1   │        │   L1   │
│   L2   │        │   L2   │        │   L2   │        │   L2   │
└───┬────┘        └───┬────┘        └───┬────┘        └───┬────┘
    │                 │                 │                 │
    └────────┬────────┴────────┬────────┴────────┬────────┘
              │            L3 (общий)              │
              └───────────────┬─────────────────────┘
                               │
                       Data Bus / Address Bus
                               │
                            ┌──▼──┐
                            │ RAM │
                            └─────┘
```

Раз L3 общий, данные, которые нужны сразу нескольким ядрам, попадают в него один раз — и дальше все ядра берут их оттуда, не гоняя каждое своё отдельное обращение до самой RAM.

## Иерархия — компромисс размера и скорости

| Уровень | Типичный размер           | Общий или приватный | Порядок задержки |
| ------- | -------------------------- | -------------------- | ----------------- |
| L1      | десятки КБ на ядро          | приватный             | ~1 нс              |
| L2      | сотни КБ — единицы МБ на ядро | приватный             | ~3–10 нс           |
| L3      | единицы — десятки МБ         | общий на все ядра     | ~10–40 нс          |
| RAM     | гигабайты                   | общая                | ~50–100 нс         |

> Цифры — порядок величины, не спецификация конкретного процессора: у каждого поколения и производителя они свои. Суть неизменна: чем ближе к ядру, тем меньше и быстрее; чем дальше, тем больше и медленнее.

Каждый уровень — это ставка: чем он ближе к ядру, тем он быстрее, но тем он и меньше. Иерархия работает, потому что *большинство* обращений программы приходятся на небольшой, часто используемый набор данных — тот самый принцип локальности, который мы уже упоминали в [[12. DRAM|12. DRAM]].

Но теперь L1 у каждого ядра — свой собственный, приватный. Что если два разных ядра закэшируют в своих приватных L1 одну и ту же ячейку памяти — а потом одно из них её изменит? Прежде чем ответить на этот вопрос, нужно сперва разобраться, чем именно кэш хранит данные — не байтами, как RAM, а кусками покрупнее. Переходим к [[21. Cache Lines|кэш-линиям]].
