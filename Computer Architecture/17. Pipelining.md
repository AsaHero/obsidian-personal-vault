В [[15. Binary Counter|прошлый раз]] мы собрали Binary Counter, который перебирает 2-битное число `00 → 01 → 10 → 11` и через [[4. Binary Decoder|декодер]] поднимает ровно одну линию — Fetch, Decode, Run или Write. Пока активна, скажем, линия Run, линии Fetch, Decode и Write выключены — вся остальная схема простаивает без дела.

## Один шаг — одна активная линия

Именно так и устроена наша схема из [[9. CPU|9. CPU]]: следующая инструкция даже не начинает Fetch, пока предыдущая целиком не пройдёт все четыре шага.

| Такт        | 1     | 2      | 3      | 4     | 5     | 6      | 7      | 8     |
| ----------- | ----- | ------ | ------ | ----- | ----- | ------ | ------ | ----- |
| **Instr A** | Fetch | Decode | Run    | Write |       |        |        |       |
| **Instr B** |       |        |        |       | Fetch | Decode | Run    | Write |

Instr B ждёт все 4 такта, хотя схема Fetch, например, свободна уже начиная с такта 2 — её никто не трогает.

## Конвейер: перекрываем шаги

Идея: пока Instr A выполняет Run, схема Fetch уже пустует — почему бы не начать Fetch для Instr B прямо сейчас, не дожидаясь, пока A дойдёт до Write?

| Instruction | 1     | 2      | 3      | 4      | 5      | 6      | 7      |
| ----------- | ----- | ------ | ------ | ------ | ------ | ------ | ------ |
| **A**       | Fetch | Decode | Run    | Write  |        |        |        |
| **B**       |       | Fetch  | Decode | Run    | Write  |        |        |
| **C**       |       |        | Fetch  | Decode | Run    | Write  |        |
| **D**       |       |        |        | Fetch  | Decode | Run    | Write  |

Это и называется **конвейером (pipeline)**: то же самое разбиение на 4 этапа, что уже стоит внутри процессора, но теперь на каждом этапе одновременно занята работа над своей инструкцией — как на автомобильном заводе, где на каждой станции конвейера в любой момент стоит своя машина на своей стадии сборки, а не одна машина едет через весь завод в одиночестве, пока следующая ждёт у ворот.

> ⚠️ Чтобы это заработало по-настоящему, мало просто разрешить всем четырём линиям декодера гореть одновременно — нужно ещё продублировать промежуточные регистры между этапами, иначе Decode для B затрёт то, что Fetch только что положил туда для C. Тот же приём мы уже видели: временный регистр между ALU и финальной записью в [[11. Instruction Cycle#Временный регистр|11. Instruction Cycle]] — там он разделял Run и Write одной инструкции, здесь та же идея разделяет соседние инструкции.

## Суперскалярность и внеочередное исполнение

Реальные процессоры суперскалярные: конвейер у них не в 4, а в 15–20 и больше ступеней (у некоторых архитектур — за 30). Каждая ступень короче — значит, каждая успевает устояться за меньшее время, и Clock можно тактовать быстрее. Чем глубже конвейер, тем больше инструкций одновременно «в полёте», каждая на своей ступени.

Но не все инструкции одинаково быстрые: сложение — один-два такта, деление или загрузка из медленной памяти — сотни. Если жёстко держать порядок программы, быстрая инструкция после медленной будет простаивать в очереди без всякой на то причины. Поэтому процессор умеет **выполнять инструкции не в том порядке, в котором они записаны в коде** (out-of-order execution) — если следующая инструкция не зависит от результата ещё не завершившейся, её можно пропустить вперёд и выполнить раньше.

Конвейер ускоряет одну и ту же последовательность инструкций, выполняя сразу несколько её кусков одновременно на одном ядре. Но что, если просто взять и построить рядом ещё один такой же процессор на том же кристалле? Переходим к [[18. Multicore|многоядерности]].
