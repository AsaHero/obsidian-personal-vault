У каждого ядра — свой приватный L1 ([[20. Cache Hierarchy|20. Cache Hierarchy]]), и кэш хранит данные целыми линиями ([[21. Cache Lines|21. Cache Lines]]). Теперь зададим конкретный вопрос: Core 0 и Core 1 оба читают переменную `X` по адресу `A` — у каждого в своём L1 теперь лежит копия той же линии с тем же значением. Пока всё согласовано. Дальше Core 0 пишет в `X` новое значение — прямо в свою копию линии в своём L1, ведь мы для того и городили кэш, чтобы не ходить в RAM на каждую операцию.

**А что теперь в L1 у Core 1?** Всё та же старая копия — никто её не трогал и не предупреждал. Если Core 1 прочитает `X`, он молча получит устаревшее значение и даже не заподозрит подвоха. Это и есть **проблема когерентности кэша**: у нескольких приватных копий одних и тех же данных нет ничего, что держало бы их синхронными друг с другом.

## Первая попытка: писать сразу в RAM

Наивное решение — **write-through**: каждая запись в кэш немедленно дублируется в RAM. Тогда хотя бы RAM всегда содержит свежее значение.

Проблема очевидна сразу: копия `X` у Core 1 лежит в его собственном L1, а не в RAM. Обновление RAM никак не трогает то, что уже закэшировано на Core 1 — та копия как была устаревшей, так и осталась. Write-through решает не ту задачу: он держит в порядке RAM, а не чужие кэши.

## Решение: ядра слушают шину

Чтобы Core 1 вообще узнал об изменении, кто-то должен ему сообщить. Добавим **snooping** — каждое ядро постоянно слушает общую шину и следит за адресами, которые по ней проезжают, даже если сам их не запрашивал.

Соединим это с write-through: когда Core 0 пишет `X`, адрес `A` всё равно едет по шине в RAM — но теперь все остальные ядра это видят. Core 1, заметив на шине запись по адресу, который есть в его собственном L1, **аннулирует** свою копию (помечает её Invalid). Следующее обращение Core 1 к `X` — это гарантированный промах, который честно сходит за свежим значением. Стухшие данные больше не читаются молча — это уже рабочий протокол когерентности с инвалидацией (write-invalidate).

## Новая проблема: шина опять забита

Мы вернулись к тому, с чего начинали в [[20. Cache Hierarchy|20. Cache Hierarchy]]: write-through гонит по общей шине **вообще каждую запись каждого ядра**, всегда — кэш перестаёт защищать шину от перегрузки, ровно то, ради чего его и городили.

## Решение: write-back и dirty-бит

Переходим на **write-back**: запись оседает только в локальном L1, помечая линию **dirty** («грязная», расходится с RAM) — в RAM она уедет позже, лениво, при вытеснении или по явному запросу. Но если данные о записи больше не едут по шине автоматически, как тогда Core 1 узнает, что нужно инвалидировать свою копию?

Решение — разделить *данные* и *уведомление*. По шине едет не сама записываемая величина, а короткий сигнал **invalidate**: «я сейчас меняю адрес `A`, у кого есть — сбросьте копию». Это дёшево — сигнал не тащит с собой 64 байта линии, только адрес. Core 0 после этого спокойно пишет к себе в L1 без выхода на шину заново.

## Ещё одна лишняя трата: когда делиться не с кем

Если линия `X` вообще никогда не была нужна никому, кроме Core 0, ему всё равно приходится слать invalidate на каждую запись — просто чтобы соблюсти протокол, хотя слушать некому. Добавим ядру способ *знать*, что копия у него единственная, и в этом случае писать вообще без всякого сигнала на шину.

## MESI: четыре состояния на кэш-линию

Каждая кэш-линия в каждом приватном кэше помечается одним из четырёх состояний:

| Состояние | Смысл |
| --------- | ----- |
| **M** — Modified  | Единственная копия во всей системе; расходится с RAM (dirty); при вытеснении обязателен write-back |
| **E** — Exclusive | Единственная копия, но совпадает с RAM (clean); можно писать локально, без выхода на шину — тихий переход в M |
| **S** — Shared    | Такая же копия есть ещё хотя бы у одного ядра; все совпадают с RAM; запись требует сначала разослать invalidate |
| **I** — Invalid   | Копии нет или она аннулирована; любое обращение — гарантированный промах |

Имя протокола — просто первые буквы этих состояний: **M**odified, **E**xclusive, **S**hared, **I**nvalid.

## Переходы между состояниями

| Событие                                    | Из состояния | В состояние | Что при этом происходит на шине |
| ------------------------------------------- | ------------- | ------------ | -------------------------------- |
| Промах на чтение, ни у кого больше нет копии | I             | E            | запрос линии из RAM              |
| Промах на чтение, копия есть у другого ядра  | I             | S            | оба ядра теперь Shared           |
| Чужой промах на чтение моей линии            | E или M       | S            | если было M — сначала write-back |
| Запись в Exclusive-линию                     | E             | M            | ничего, тихо, без шины           |
| Запись в Shared-линию                        | S             | M            | invalidate всем остальным копиям |
| Чужая запись (снятый invalidate)             | S, E или M    | I            | своя копия сбрасывается          |

## Пример: X глазами Core 0 и Core 1

Проследим тот самый сценарий с самого начала, теперь с полным протоколом:

1. Ни у кого нет `X` в кэше — линия отсутствует, считаем её I у обоих.
2. **Core 0 читает `X`.** Промах, копии больше ни у кого нет → RAM отдаёт линию, Core 0 ставит **E**.
3. **Core 1 читает `X`.** Промах на Core 1; snooping видит, что Core 0 уже держит линию → Core 0 понижается **E → S**, Core 1 получает копию и тоже ставит **S**. Оба совпадают с RAM.
4. **Core 0 пишет в `X`.** Линия у Core 0 в S, не в E — значит, кто-то ещё может держать копию. Core 0 шлёт invalidate по шине → Core 1 переходит **S → I** → Core 0 переходит **S → M**, пишет локально.
5. **Core 1 снова читает `X`.** Его копия I — промах. Snooping видит: линия у Core 0 в состоянии M. Core 0 отдаёт своё свежее (грязное) значение напрямую Core 1 и одновременно переходит **M → S**; Core 1 тоже становится **S** — уже с правильным, актуальным значением.

Ни на одном шаге никто не прочитал устаревшие данные — именно это и было целью всей цепочки решений.

> Реальные процессоры чаще используют не сам MESI, а его расширения — **MOESI** (AMD) добавляет состояние Owned, чтобы отдавать грязные данные соседу напрямую, не дожидаясь write-back в RAM; **MESIF** (Intel) добавляет Forward, чтобы среди нескольких Shared-копий явно выбрать одну, кто отвечает на будущие запросы. Идея та же, деталей больше — сюда не спускаемся.

Протокол безупречно следит за *корректностью*: ни одно ядро никогда не прочитает устаревшее значение. Но у той же самой линии-как-минимальной-единицы, которая сделала это возможным, есть неожиданная обратная сторона — она может испортить скорость там, где корректность вообще не была под вопросом. Переходим к [[23. False Sharing|false sharing]].
