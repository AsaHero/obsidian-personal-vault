[[22. Cache Coherence|MESI]] безупречно решает задачу корректности: ни одно ядро никогда не читает устаревшие данные. Но у решения есть цена, о которой протокол ничего не знает, — она спрятана не в логике MESI, а в том, *чем* он оперирует: [[21. Cache Lines|целой кэш-линией]], а не отдельным байтом.

## Два счётчика, одна линия

Представим два независимых счётчика, `counterA` и `counterB` — каждый обновляет только своё, отдельное ядро (Core 0 трогает только `counterA`, Core 1 — только `counterB`), и логически между ними нет вообще никакой связи, ни один не читает и не пишет данные другого.

```go
var counterA int64  // трогает только Core 0
var counterB int64  // трогает только Core 1
```

Компилятор и аллокатор памяти про эту связь тоже ничего не знают — они просто размещают две соседние переменные подряд в памяти, как получится. Если `counterA` и `counterB` оказались достаточно близко друг к другу (64-байтная линия — это, например, восемь `int64` подряд), они оба попадают в **одну и ту же кэш-линию**:

```
Кэш-линия (64 байта):
┌───────────┬───────────┬──────────────────────────┐
│ counterA  │ counterB  │      остальные 48 байт     │
│  8 байт   │  8 байт   │                            │
└───────────┴───────────┴──────────────────────────┘
```

## MESI не видит разницы между байтами внутри линии

Из [[22. Cache Coherence|прошлого конспекта]]: запись помечает состояние **всей линии**, invalidate аннулирует **всю линию**. Протоколу физически неоткуда узнать, что Core 0 менял только первые 8 байт, а до остальных 56 (включая `counterB`) даже не дотрагивался — единица его работы жёстче: линия целиком, изменилась или нет.

Прогоняем ту же последовательность событий, что и в [[22. Cache Coherence#Пример: X глазами Core 0 и Core 1|прошлом примере]], только оба ядра «пишут в X» одновременно и постоянно, каждое в свою половину линии:

1. Core 0 пишет `counterA` → его копия линии переходит в **M**, копия Core 1 инвалидируется целиком (**S → I**) — хотя `counterB` внутри неё не менялся ни на бит.
2. Core 1 тут же пишет `counterB` → он промахивается (его копия только что стала I), тащит линию заново, пишет, его копия становится **M**, а копия Core 0 инвалидируется в ответ.
3. Core 0 снова пишет `counterA` → опять промах, опять полный цикл invalidate в обратную сторону.

Линия начинает **пинг-понговать** между кэшами двух ядер на каждую отдельную запись, хотя ни одно ядро ни разу не прочитало и не изменило чужие данные. Это и есть **false sharing** («ложное разделение»): данные логически не общие, но физически делят одну линию, и протокол когерентности честно обрабатывает это как настоящий конфликт.

## Корректно, но медленно

Никакого бага в смысле неправильных значений здесь нет — `counterA` и `counterB` всегда посчитаются верно, MESI это гарантирует. Проблема исключительно в скорости: вместо того чтобы обе записи спокойно оседали в приватных L1 (быстро, без выхода на шину), каждая запись теперь порождает полный цикл invalidate + промах + повторную загрузку линии — то самое обращение к более медленным уровням иерархии ([[20. Cache Hierarchy|20. Cache Hierarchy]]), которого кэш должен был как раз избегать. На практике это может быть на порядок медленнее, чем если бы `counterA` и `counterB` вообще ничего не знали друг о друге физически, а не только логически.

## Лечение: развести по разным линиям

Раз причина — случайное соседство в памяти, а не что-либо логическое, решение чисто механическое: **раздвинуть** горячие независимые переменные так, чтобы они гарантированно попадали в разные кэш-линии — например, добавив между ними выравнивание/padding до размера линии (64 байта). Тогда запись в одну из них больше не задевает состояние линии другой, и пинг-понг прекращается.

Вот и вся цепочка, которую породила многоядерность: общая шина стала [[20. Cache Hierarchy|узким местом]] → приватные кэши сняли нагрузку с шины, но кэш хранит [[21. Cache Lines|целые линии]], а не байты → несколько приватных копий одной линии рискуют разойтись → [[22. Cache Coherence|MESI]] держит их синхронными за счёт инвалидации по адресу → а тот же самый механизм, работающий линиями, может исподтишка испортить производительность там, где никакого настоящего конфликта данных вообще не было. Каждое решение снимало предыдущую проблему и аккуратно порождало следующую — ровно так и устроено реальное железо.
